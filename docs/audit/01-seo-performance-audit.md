# Pots & Planters — SEO & Performance Audit

**Версия:** 1.0 · **Дата фиксации:** 17 октября 2026 г.  
**Сайт:** https://potsandplanters.ae/  
**Текущая платформа:** OpenCart 2.3, PHP 7.4.33  
**Назначение:** зафиксировать исходное состояние и требования к миграции на Laravel 13 + Next.js + Filament.  
**Статус:** завершённый технический аудит по доступным выгрузкам; не является полным краулингом и не включает Google Search Console.

## 1. Краткий вывод

Текущий магазин имеет **приличную серверную скорость и хорошие показатели Lighthouse на десктопе**, но мобильный каталог заметно медленнее: **LCP 6,78 с** на категории и **7,40 с** на категории с фильтром. Ключевые SEO-риски — отсутствие полноценной XML-карты сайта, отсутствие постоянного перенаправления `www → apex`, непоследовательные URL/canonical товара и практически пустая таблица товарных SEO-алиасов. Есть проблемы с полнотой и согласованностью данных каталога.

**Главный принцип миграции:** нельзя автоматически считать существующие URL «мусорными» и заменить их новыми slug. Сначала необходимо получить реестр **фактически доступных** адресов и карту `старый URL → новый URL`, включая товары, категории, информационные страницы и блог.

## 3. Техническое SEO

### 3.1 Хост, протокол, HTTP

- `http://potsandplanters.ae/` → `302` → HTTPS; аналогично для `www`. Для постоянного перехода следует использовать `301` или `308`.
- `https://potsandplanters.ae/` → `200`.
- `https://www.potsandplanters.ae/` → `200`: дублирующий хост без редиректа на канонический.
- `/index.php` и `/index.php?route=common/home` → `200`: потенциальные альтернативные адреса главной; проверять canonical и индексацию.
- Тестовый несуществующий URL корректно отвечает `404`.
- Главная: HTTP TTFB **211 мс** в серверном замере. HTTPS, HTTP/2 и gzip доступны.
- HTML отвечает с `cache-control: no-store, no-cache, must-revalidate`. Для публичного каталога это ограничивает HTTP-кеширование; при этом нельзя применять общий публичный кеш к корзине и персональным данным.
- В ответе устанавливается cookie `currency=RUB` на UAE-магазине. Требуется проверить валюту отображения, цены, настройки магазина и реальные сценарии; сам факт cookie ещё не доказывает неверные цены.

### 3.2 Robots и sitemap

- `robots.txt` доступен, содержит правила закрытия служебных маршрутов и параметров сортировки.
- Директива `Sitemap:` **закомментирована**.
- `/sitemap.xml` возвращает пустой документ с HTTP 200; это не рабочая карта сайта.
- Для `rdrf`-параметров фильтрации в проверенном robots.txt нет отдельного правила; вопрос индексации комбинаций фильтров требует SEO-политики, а не безусловного запрета всего подряд.

**Для новой платформы:** валидный sitemap index или XML sitemap со всеми индексируемыми canonical URL, актуальным `lastmod` при достоверном изменении, ссылка из robots, исключение корзины/checkout/личного кабинета/неиндексируемых комбинаций фильтров.

### 3.3 HTML и метаданные — выборка из четырёх страниц

| Страница | Title / H1 | Canonical | JSON-LD | Изображений без непустого alt |
|---|---|---|---|---:|
| Главная | `Pots & Planters \| Main`; **H1 отсутствует** | canonical в HTML не найден | Нет | 44 из 82 |
| `/outdoor-pots` | `Outdoor Pots & Planters`; H1 есть | `/outdoor-pots` | Нет | 21 из 38 |
| `/outdoor-pots?rdrf[attr][22][]=Black` | Title и description совпадают с категорией; H1 есть | `/outdoor-pots` | Нет | 21 из 38 |
| Товар `product_id=3481` | Название товара; H1 есть | `/index.php?route=product/product&product_id=3481` | Нет | 31 из 41 |

Примечание: пустой alt у декоративной картинки допустим. Цифры отражают **потенциальные** проблемы, не автоматический список нарушений доступности.

У проверенного товара `og:url` = `/outdoor-pots?product_id=3481`, а canonical — технический адрес. Требуется определить единственный публичный канонический URL для каждого товара. У фильтрованной категории canonical ведёт на базовую категорию: это может быть корректно для неиндексируемых фильтров, но должно быть **осознанным единым правилом**, а не случайным эффектом Dream Filter.

### 3.4 Структурированные данные

В четырёх проверенных HTML не обнаружены скрипты `application/ld+json`. На новом сайте предусмотреть:

- `Organization` / `OnlineStore` на уровне сайта, с проверенными реквизитами.
- `BreadcrumbList` для категорий и товаров.
- `Product` + `Offer` **только** при наличии корректных цены, валюты, доступности и соответствующего содержимого страницы.
- Не придумывать рейтинг/отзывы и не выводить неподтверждённые значения в разметку.

### 4.3 Категории

В SQL семь категорий с нулём прямых привязок товаров: Fiberstone Planters, Fiberstone Firepit, Fiberstone Tables, Fiberstone Home, Ceramics, Fiberstone, Fiberconcrete. **Нулевая прямая привязка не означает, что страница бесполезна:** категория может быть родительской, содержать текст, дочерние разделы или ссылки на PDF. Решение `оставить / объединить / редирект / noindex / 404` принимать после проверки структуры, трафика и внутренних ссылок.

Категория `Christmas Sale` содержит 37 товаров: при миграции отделить товарную таксономию от промоакций, но сохранить или перенаправить старый адрес по содержательному назначению.

### 4.4 Фильтры, опции и качество атрибутов

- Используется **Dream Filter**; формат запроса `rdrf[attr][22][]=Black`. Стандартная таблица фильтров пустая, фильтрация опирается на другие данные/модуль.
- 20 товаров имеют опции, 176 записей значений; обнаружена опция `Color Plastic` типа `radio`.
- В `oc_product_related` нет связей: автоматические рекомендации можно разработать заново, не предполагая, что текущий магазин хранит ручные связи.
- Атрибут `Size` смешивает `S/M/L/XL` и размеры в сантиметрах; встречаются значения вроде `H:180sm`. Нужна нормализация отображаемых характеристик и отдельных фасетов фильтрации.
- В отчёте атрибут `Usage` привязан к **1539 различным product_id**, что превышает 396 товаров в `oc_product`. Запрос считал ID из `oc_product_attribute` **без JOIN с `oc_product`**: вероятны осиротевшие связи, но это гипотеза до проверки.

**Контрольный SQL перед импортом:**

```sql
SELECT COUNT(*) AS orphan_attribute_rows,
       COUNT(DISTINCT pa.product_id) AS orphan_product_ids
FROM oc_product_attribute pa
LEFT JOIN oc_product p ON p.product_id = pa.product_id
WHERE p.product_id IS NULL;
```

Нужен импорт с очисткой сиротских связей и журналом исключений, но **без изменения старой БД**.

### 4.5 Медиа

`image/catalog`: **737 МБ**, в том числе **1586 JPG**, **598 PNG** (а также 17 HTML и 1 ICO по расширениям). Крупнейший файл PNG — **11,64 МБ**. Это объём хранилища, а не размер загрузки отдельной страницы.

**Требование:** сохранить исходники, генерировать WebP/AVIF и адаптивные размеры асинхронно, хранить соответствие исходного пути и нового media ID, использовать `srcset`/`sizes`, корректные `width`/`height`, приоритет LCP-изображения, lazy-load только ниже первого экрана. PDF-каталоги учитывать отдельно от картинок.

Лабораторный серверный отклик в Lighthouse (`server-response-time`) — примерно **182–242 мс**. Проблема преимущественно проявляется после ответа сервера: изображения, CSS, JS, приоритеты загрузки и работа браузера. Однако точный вклад каждого фактора в LCP требует анализа трассировок.

### 5.3 Основные направления оптимизации

1. **Изображения:** уменьшить передаваемый вес, обеспечить подходящие размеры и форматы; для LCP-элементов проверить preload/`fetchPriority` и отсутствие ненужной ленивой загрузки.
2. **JS:** убрать неиспользуемые библиотеки и скрипты, разделить код по маршрутам, оставить интерактивность клиентскими островками. В отчётах выявлен заметный объём потенциально неиспользуемого JS.
3. **CSS / критический путь:** сократить ресурсы, блокирующие первый рендер; исключить загрузку глобальных стилей сторонних виджетов без необходимости.
4. **Фильтрация:** серверная выборка и URL-параметры, доступная мобильная панель, обновление результатов без загрузки избыточного JS.
5. **Доступность:** именованные элементы управления, контраст, иерархия заголовков, навигация клавиатурой, состояния фокуса.
6. **Best Practices:** отдельно устранить ошибки консоли и замечания по внешним ресурсам; не трактовать балл 73–77 как конкретную уязвимость без разбора отдельных аудитов.

**Интерпретация:** `INP` нельзя вывести из одного лабораторного Lighthouse; для него нужны полевые данные. `TBT` — лабораторный прокси, а не замена INP. Lighthouse SEO 100 не отменяет проблемы URL, sitemap и метаданных.

## 7. Требования к новой платформе

**Предлагаемый стек:** Next.js (SSR/серверные компоненты для индексируемого контента), Mantine для интерактивного UI, Laravel 13 API, Filament, MariaDB, Redis/Horizon, Docker Compose, Dokploy. Это **архитектурное предложение**, а не факт, установленный аудитом.

- SEO-логика должна быть независима от React-клиентского рендера: HTML с title, description, H1, canonical, OG, JSON-LD и контентом доступен без выполнения JS.
- Адреса и редиректы — управляемая часть данных, а не набор случайных правил в компонентах. Nginx `map` допустим для статической карты; динамические редиректы можно реализовать в приложении с контролем производительности.
- Фильтры должны работать на нормализованных атрибутах и не создавать бесконтрольное число индексируемых страниц.
- Состояние корзины и checkout не должно попадать в общий публичный кеш.
- Генерация медиа и AI — фоновые задачи, а не блокировка HTTP-запроса.
- Все этапы миграции должны быть воспроизводимы и проверяемы автоматически.

## 8. Целевые показатели и метод проверки

| Метрика | Цель для новой версии |
|---|---:|
| Lighthouse Performance Mobile | ≥ 90 |
| Lighthouse Performance Desktop | ≥ 95 |
| Лабораторный LCP | ≤ 2,5 с |
| Лабораторный TBT | ≤ 200 мс |
| CLS | ≤ 0,1 |
| TTFB | ≤ 800 мс |
| Lighthouse Accessibility | ≥ 95 |
| Lighthouse Best Practices | ≥ 95 |
| Lighthouse SEO | 100 |

Это **проектные цели**, а не гарантия результата. Сравнивать одинаковые типы страниц и одинаковые профили Lighthouse, предпочтительно по **медиане минимум трёх прогонов** на сценарий. После запуска дополнительно анализировать полевые LCP, INP, CLS по 75-му процентилю при достаточном объёме данных.

## 9. Открытые вопросы и обязательные проверки до запуска

1. **URL:** полный crawl и список старых товарных ссылок, включая SEO Pro и параметризованные адреса; GSC/серверные логи при наличии.
2. **Контент:** какие пустые категории нужны пользователям, какие PDF-каталоги должны сохраниться, что индексируется в блоге.
3. **Данные:** причина 20 отсутствующих описаний; реальные осиротевшие `oc_product_attribute`; качество цен, валют и остатков.
4. **Checkout:** фактически используемые способы оплаты, доставки, налоги, скидки, письма, гостевые заказы, интеграции.
5. **Релиз:** стратегия заморозки записи/дельта-импорта заказов и товаров, DNS/SSL, rollback, наблюдение за 404 и заказами.
6. **Performance:** повторные замеры, проверка LCP-элемента и трассировок, реальные данные после релиза.
