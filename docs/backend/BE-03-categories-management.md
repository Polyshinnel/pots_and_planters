# BE-03 — Categories Management: Laravel + Filament + API + Next.js

## Цель
Реализовать второй законченный вертикальный срез Pots & Planters 2.0: категории управляются в Filament, выдаются Laravel API и используются публичным Next.js. Товары, фильтры, корзина, PDF и Solutions пока остаются на текущих источниках. Никакого редизайна.

## Перед началом
Прочитай `BE-01-backend-architecture-audit-report.md`, ТЗ/реализацию BE-02 и актуальный репозиторий. Аудит — проект архитектуры, а не доказательство реализованных таблиц. Выясни фактические контракты `frontend/src/types/catalog.ts`, `frontend/src/config/catalog.ts`, `frontend/src/data/catalog.mock.ts`, `frontend/src/data/home.mock.ts`, `frontend/src/lib/catalog/*`, страницы `/shop`, `/shop/[category]`, homepage и существующие SEO metadata. Не предполагай, что текущие ключи категории совпадают со slug: в аудите `categoryIds` используют внутренние ключи вроде `outdoor`, а URL — `outdoor-pots`. Зафиксируй таблицу соответствия.

## Объём и границы
- Три существующих публичных маршрута: `/shop/outdoor-pots`, `/shop/indoor-pots`, `/shop/artificial-plants`.
- Сохранить текущие публичные названия, тексты, изображения, SEO, URL и порядок по фактическому коду; не сочинять контент.
- Категории OpenCart сверх этих трёх **не удалять и не импортировать без источника**. Допустить расширение модели, но не выводить неизвестные legacy категории в публичную навигацию.
- Не создавать сейчас Product/Category pivot, ProductResource, сложный media library или универсальный CMS. Предусмотреть будущие связи в архитектуре, но не создавать неиспользуемые сущности.
- `/shop` как статическая индексная страница продолжает использовать BE-02 page SEO; SEO динамических категорий — из Category.

## 1. Модель и миграции
Создать `categories` с внутренним BIGINT PK и стабильным публичным ключом/ID, `slug` UNIQUE, `name`, `heading` (H1), описанием/intro в структуре, совместимой с существующим UI, изображением и alt, SEO title/description/OG image, `status` (draft/published/archived), `sort_order`, timestamps. Допустимо `parent_id` nullable с проверкой циклов, если реально полезно для будущего OpenCart; не усложнять текущую плоскую публичную навигацию. Выбрать понятное разделение `public_id`/`code`/`slug` с учётом уже используемых `categoryIds`; публичные идентификаторы не должны меняться при изменении slug. Существующие записи не должны потерять ссылочную идентичность. Для изображений использовать уже существующий подход BE-02, если он подходит; не плодить несовместимые способы хранения. Публичные URL изображений должны быть корректны в Docker и на production.

Правила: draft/archived не доступны в публичном API; публикация требует необходимых данных; сортировка детерминированная (`sort_order`, затем ID); `slug` валидируется и уникален; безопасное удаление (для опубликованных — архивирование, не hard delete); slug опубликованной категории нельзя менять незаметно: пока нет реестра редиректов, запретить изменение slug опубликованной записи либо обеспечить явный корректный permanent redirect, без цепочек. Не удалять/перезаписывать существующие данные при повторных seed.

## 2. Начальные данные
Создать идемпотентный seeder/upsert **только отсутствующих** трёх публичных категорий. Перенести исходные значения из актуального frontend, не перетирать ручные правки в Filament при повторном запуске. Избегать выдуманных категорий, характеристик, продуктов, цен. Для старых category IDs/keys создать документированное стабильное соответствие с API DTO. Если изображения находятся в `frontend/public`, выбрать аккуратную стратегию переноса в управляемое Laravel storage без битых URL и без дублирования на каждом seed; проверить реальное наличие файлов.

## 3. Filament
Создать `CategoryResource` с таблицей (название, slug, статус, порядок, updated_at), формой: название, read-only stable ID/code, slug, H1, intro/SEO-текст, изображение + alt, status, sort_order, SEO title/description, OG image. Предпросмотр изображений, валидация upload MIME/size, управление порядком. SEO блок должен использовать **готовый переиспользуемый Google Search Preview из BE-02**, а не новую копию. Preview строит canonical `/shop/{slug}` на production origin, обновляется реактивно и не обещает точного результата Google. Учитывать, что у draft preview может быть slug, но публичная страница недоступна. Авторизация — как в BE-02; не ослаблять доступ.

## 4. Laravel API
- `GET /api/v1/categories` — только опубликованные категории, порядок, публичные DTO; не выдавать внутренние storage paths и админские поля.
- `GET /api/v1/categories/{slug}` — опубликованная категория либо 404.
- Списки по принятому BE-01 контракту `{data: [...]}`, одиночный `{data: {...}}`. camelCase, публичные идентификаторы-строки, совместимость с TypeScript `Category` через минимальный явный адаптер. В DTO должны быть сведения, нужные для плиток, заголовков, intro и SEO; canonical вычислять на frontend из актуального slug.
- При ошибке DB/API не подменять результат моками и не возвращать фальшивый 404; корректная диагностика без секретов.
- Выбрать `no-store` на первом срезе или кеш с проверяемой инвалидизацией после сохранения в Filament. Изменение должно становиться видимым без пересборки Next.js.

## 5. Next.js — точечное переключение
- Подключить категории к `/shop`, `/shop/[category]`, category tiles главной и другим местам, где отображаются **сведения о категории**. Найти все прямые импорты категории из mock/config, документировать и переключить там, где это безопасно.
- Не сломать `CatalogRepository`, фильтры `material/color/size/usage`, сортировку, пагинацию и `Product` mock: создать явный mapping между новыми API category IDs и текущими mock product category IDs; **не менять идентификаторы в mock товарах массово**.
- Если блоки Home/About/Solutions используют категории в иной структуре, сделать небольшой адаптер, не переделывая страницы и не переключая несвязанные сущности.
- Не превращать UI в Client Component ради получения категорий. Использовать существующий server API helper и серверный рендеринг.
- Для `/shop/[category]` серверные title/description/OG из API Category; корректный canonical; опубликованная категория с нулём товаров всё равно отображается как существующая категория, неизвестная/неопубликованная — 404. Сбой API — ошибка, не 404.
- Сохранить BE-02 SEO индексной `/shop`, другие static page metadata и все robots-правила. Не менять существующие URL и redirects.
- Если категория скрыта, убрать её из публичных плиток/навигации, но не разрушать доступность mock-товаров других категорий. Никаких фиктивных fallback.

## 6. Тесты и приёмка
1. Идемпотентный seed; ручные правки в Filament сохраняются после повторного seed.
2. API возвращает только published, правильный порядок, корректный DTO и 404 на неизвестный/draft slug.
3. Изменение имени/H1/описания/SEO в Filament сразу видно на соответствующей странице и в серверном HTML metadata без build.
4. Замена изображения и alt видна на плитке, OG image валиден публично.
5. Изменение порядка меняет порядок плиток; draft/archived не появляются в списке.
6. Google Search Preview работает в форме категорий через **общий компонент BE-02**.
7. Все три категории открываются, mock-товары, фильтры, сортировка, пагинация, ссылки на товары и Enquiry Cart продолжают работать как прежде.
8. Неверный slug -> 404, отказ API -> наблюдаемая ошибка, без fallback на mock.
9. Проверить `/shop` metadata из BE-02 и category-specific metadata отдельно; не допускать конфликтов с root layout.
10. Laravel tests, TS check, Next production build, desktop/mobile smoke. Не запускать миграции на production без отдельного подтверждения.

## Результат и отчёт
Предоставить список миграций/файлов, ER-решение, карту старых ключей к API, исходные значения трёх категорий, контракты API, описание seed и медиа, список точек frontend, которые переведены на API, и список тех, что пока сознательно оставлены на mock. Приложить результаты тестов и конкретный сценарий проверки в Filament. Не утверждать, что весь каталог переведён на backend: товары пока mock.
