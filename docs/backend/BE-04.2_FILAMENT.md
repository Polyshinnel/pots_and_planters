# BE-04.2 — Filament Catalogue Management

**Проект:** Pots & Planters 2.0  
**Этап:** BE-04.2  
**Статус:** ТЗ согласовано к реализации; фактический код этапа ещё не проверен  
**Язык админки:** согласно существующим соглашениям репозитория; публичный контент — английский.

## 1. Цель и границы

Реализовать полноценное управление PDF-каталогами в существующей административной панели Filament 5: список, создание, редактирование, публикация, категории, загрузка и предпросмотр обложки, загрузка приватного PDF, безопасная замена и удаление файлов. Опора на реализованные `Catalogue`, `CatalogueManager`, `Category`, `catalogues`, `catalogue_category` и проверки BE-04.1a.

**Не входит:** публичный API (BE-04.3), подключение Next.js и удаление frontend mocks (BE-04.4), отправка заявок и скачивание PDF (BE-07), изменение публичного дизайна, production-миграции.

## 2. Обязательная предварительная проверка (read-only)

Перед изменениями изучить `docs/common/PROJECT_CONTEXT.md`, `docs/common/ROADMAP.md` (или фактические пути в репозитории), `Catalogue`, `CatalogueManager`, `Category`, тесты `CataloguesTest`, существующие Filament resources и их Pages, включая `CategoryResource.php`, настройки disks/storage, политики доступа и схему загрузок. Проверить `git status` и локальные изменения. Не считать отчёт предыдущего этапа заменой проверки кода.

Кратко зафиксировать существующие conventions Filament 5: навигация, поля, валидация, notifications, таблицы, actions, авторизация, отображение медиа. Повторно использовать готовые компоненты. Не перезаписывать ручные правки, особенно `CategoryResource.php`.

Если обнаружено противоречие между текущим кодом и ТЗ, сначала описать его и выбрать минимально совместимое решение; при риске потери данных или нарушении архитектуры остановиться и запросить согласование.

## 3. Функциональные требования

### 3.1. Resource и список

- Создать `CatalogueResource` и нужные Pages в структуре, принятой проектом.
- Список: название, slug/public_id при необходимости, статус, связанные категории, `sort_order`, дата изменения; поиск по названию/slug, фильтр по статусу и категориям (если поддерживается без чрезмерной сложности).
- Предусмотреть редактирование порядка в согласованном с существующим Filament стиле. Сохранить детерминированный порядок; не вводить отдельную систему ранжирования.
- Действия создания, редактирования и удаления — с подтверждением для разрушительных операций и с соблюдением существующей авторизации.
- Не показывать приватные пути как публичные ссылки.

### 3.2. Форма каталога

- Поля, соответствующие реальной схеме: title, slug, description, cover alt, status (`draft`, `published`, `archived`), sort_order, PDF, cover, категории (multiple).
- `public_id` генерируется на backend, не редактируется и не перегенерируется.
- Категории — существующие записи; связь через pivot по внутренним FK. В публичном контракте впоследствии использовать `public_id`, а URL-фильтр строить по slug.
- Не допускать публикацию без существующего PDF на `local`, обложки на `public` и минимум одной существующей категории. Ошибки отображать в форме понятным образом.
- Сохранение атрибутов и pivot должно проходить через `CatalogueManager`, а не через независимые пути, обходящие инварианты BE-04.1a.
- Учесть редактирование уже опубликованной записи: не допускать частично сохранённого состояния и не уничтожать старые файлы при неуспехе.

### 3.3. PDF: приватность

- Использовать существующий приватный диск `local`; не создавать публичный symlink, route, signed URL или action, выдающий PDF без авторизации.
- Upload: проверка MIME/содержимого по возможностям Laravel, расширение PDF, допустимый размер (сначала выяснить действующие лимиты PHP/nginx и согласовать значение с ними; не придумывать лимит молча), безопасное имя файла, путь внутри выделенного каталога хранения.
- Административное отображение: имя/размер и факт наличия; если требуется открытие файла администратором, только через существующую проверенную авторизацию. Публичная выдача PDF не реализуется.
- Не доверять присланному пути файла и не разрешать traversal или произвольные внешние URL.

### 3.4. Обложка: публичный файл

- Использовать диск `public`, существующую настройку URL и безопасный префикс каталога.
- Принимать только поддерживаемые форматы изображений, валидировать файл и размер с учётом текущей конфигурации; показывать предпросмотр и редактируемый alt.
- Не ломать URL существующих обложек и не удалять файл, пока на него ссылаются другие записи.

## 4. Жизненный цикл файлов и согласованность

Реализовать явно и проверить следующие сценарии:

1. **Создание:** файл загружен → валидирован и помещён в контролируемое хранилище → запись сохранена через менеджер → при неудаче удаляются только новые неиспользуемые файлы.
2. **Замена:** старый файл сохраняется доступным до успешного commit записи с новым путём; при ошибке старый путь и файл остаются действующими; новый неиспользуемый файл очищается.
3. **Удаление/очистка:** после успешного commit удалять старые файлы только если на них больше нет ссылок; учитывать общий путь и конкурентные операции. Нельзя удалять файл до фиксации БД.
4. **Удаление записи:** связанные файлы удаляются только после успешного удаления записи и при отсутствии других ссылок; очистка не должна нарушать откат БД.
5. **Сбой файловой операции:** логировать проблему, не заявлять об успешной очистке, не удалять текущий используемый файл; предусмотреть безопасную повторную очистку или явно описать остаточный риск.

Учесть, что DB-транзакции не охватывают файловую систему, а callbacks после commit сами по себе не гарантируют выполнение при падении процесса. Выбрать минимально надёжную схему с учётом существующей инфраструктуры; не добавлять очереди/новые таблицы без обоснования и согласования. Не делать неограниченную фоновую очистку всех файлов диска.

**Важно:** если стандартный Filament FileUpload автоматически переносит/удаляет файл до `CatalogueManager::save()`, адаптировать поток так, чтобы не нарушать требования выше. Проверить это на реальном коде, а не предполагать.

## 5. Безопасность и ограничения

- Сохранять модельные проверки BE-04.1a и блокировки категорий; Filament не должен обходить `CatalogueManager` для сохранения/публикации.
- Существующая защита удаления категории рассчитана на Eloquent model delete; массовый query-builder delete/прямой SQL вне штатного пути. Не добавлять DB-триггеры.
- Не менять `CategoryResource.php`, если нет необходимости; при необходимости отдельно объяснить изменение и сохранить пользовательский diff.
- Использовать действующую авторизацию Filament и правила доступа к storage; не открывать публичный доступ к PDF.
- Не добавлять фиктивные каталоги, цены, даты, документы или сидеры с выдуманным контентом.
- Не менять API, Next.js, существующие маршруты, SEO и публичный дизайн.
- Не запускать production-миграции, не делать массовую очистку реального storage.

## 6. Реализация небольшими проверяемыми шагами

**Шаг A — интеграция Filament.** Resource, Pages, список, форма без опасной файловой очистки. Проверить создание draft, редактирование и выбор нескольких категорий. Не допускать обхода менеджера.

**Шаг B — загрузчики и публикация.** PDF на `local`, обложка на `public`, валидаторы, preview, корректные ошибки публикации. Проверить, что приватный PDF не раскрывается.

**Шаг C — lifecycle.** Замена, удаление, откат, неиспользуемые файлы, повторно используемые пути, failure handling. Не удалять старые файлы раньше commit.

**Шаг D — тесты и финальная проверка.** Выполнить backend suite, целевые Filament-тесты, Pint на затронутых файлах, `git diff --check`, проверить `git status`. Не форматировать целиком чужие файлы ради устранения старых замечаний.

## 7. Критерии приёмки

- Администратор может создать draft, изменить поля, прикрепить PDF и обложку, назначить несколько категорий, опубликовать, архивировать, сортировать и удалить каталог.
- Нельзя опубликовать запись с отсутствующим файлом, неверным диском или без категории; UI показывает понятную ошибку.
- PDF физически хранится приватно и не доступен по публичному URL; обложка имеет корректный публичный preview.
- Все операции сохранения/публикации проходят через бизнес-логику, сохраняя `public_id` и связи.
- Замена/удаление не уничтожает старые файлы до commit; при rollback сохраняются старые данные и файлы; чужие используемые файлы не удаляются.
- Тестами подтверждены успешные и ошибочные сценарии, включая отсутствие файлов, ошибку сохранения и файловую очистку.
- Пользовательские незакоммиченные изменения не затронуты; нет незапрошенного рефакторинга.
- API/Next.js/BE-07 не реализовывались в рамках этого этапа.
