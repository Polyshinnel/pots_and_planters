# BE-04.3 — Public Catalogues API

**Проект:** Pots & Planters 2.0  
**Этап:** BE-04.3 / Laravel API  
**Статус:** техническое задание, реализация не подтверждена  
**Следующий этап:** BE-04.4 — Next.js integration

## 1. Цель

Предоставить публичный read-only endpoint каталога PDF-документов для существующих страницы `/catalogues` и домашнего слайдера. Возвращать только опубликованные, корректные каталоги в стабильном порядке. PDF-файлы остаются приватными; скачивание после сохранения заявки — исключительно BE-07.

## 2. Исходный контекст и границы

- Существующие категории имеют внутренний PK, стабильный `public_id`, URL slug и отдельный идентификатор фильтра; в аудите: `outdoor` → `outdoor-pots`, `indoor` → `indoor-pots`, `artificial` → `artificial-plants`.
- В текущем этапе **не** менять Filament, схему БД, frontend, mock-репозиторий, пользовательские формы и механизм выдачи PDF. Не выполнять production-миграции.
- Перед работой проверить фактический код и `docs/common/PROJECT_CONTEXT.md`, `docs/common/ROADMAP.md`: отчёт предыдущих этапов не заменяет инспекцию репозитория.

## 3. Контракт API

### GET `/api/v1/catalogues`

- Без аутентификации, read-only.
- По умолчанию возвращает только `published`, в порядке `sort_order ASC`, затем по стабильному дополнительному ключу (например, внутреннему PK ASC), чтобы порядок был детерминированным.
- Не возвращает `draft` и `archived`.
- `?category=<slug>` фильтрует по **slug** существующей категории, а не по `public_id` или значению фильтра `outdoor`.
- Один каталог, принадлежащий нескольким категориям, возвращается в списке **один раз**.
- Для неизвестного корректного slug — пустой список с HTTP 200; некорректные параметры валидировать предсказуемо согласно существующему стилю API (например, HTTP 422). Не допускать SQL-инъекций и необработанных исключений.
- Учитывать статус категории: сверить действующую семантику публикации категорий и исключать из публичной фильтрации неопубликованные категории; не вводить новую семантику без согласования.
- Формат оболочки ответа (`data`, meta и пр.) взять из действующих `/api/v1` endpoints. Не придумывать несовместимый формат.

### DTO одной записи

| Поле | Содержание |
|---|---|
| `id` | `Catalogue.public_id` — стабильный внешний идентификатор |
| `slug` | публичный slug каталога |
| `title` | название |
| `description` | описание, nullable в соответствии с моделью |
| `coverImage` | публичный URL обложки с корректным origin |
| `coverAlt` | alt-текст обложки |
| `categoryIds` | массив стабильных `Category.public_id` (если существующий frontend-контракт требует другие ID, согласовать адаптацию на BE-04.4) |
| `categories` | категории для отображения тегов: минимум идентификатор, название, slug; сверить текущий UI и API категорий перед окончательным форматом |

**Запрещено выдавать:** `pdf_path`, `pdf_url`, `Storage::url()` для приватного диска, signed/download URLs, абсолютные пути storage, временные ссылки, внутренние служебные поля и персональные данные. Нельзя формировать публичный маршрут к PDF в обход BE-07.

## 4. Правила выборки

1. Использовать Eloquent query, явные условия публикации и eager loading категорий (`with(...)`) во избежание N+1.
2. Проверить, какие гарантии корректности уже обеспечены при публикации. Не выполнять потенциально дорогую проверку наличия PDF на диске для каждой строки списка без доказанной необходимости; отсутствие файлов после публикации — отдельная операционная проблема. При этом не показывать записи, которые по данным БД не удовлетворяют опубликованному состоянию.
3. Не дублировать строки при many-to-many фильтре: предпочтительно `whereHas` / `whereRelation`.
4. Обложку преобразовывать в URL через публичный диск и действующую конфигурацию приложения; не раскрывать приватные storage paths.
5. Стабильный порядок категорий в DTO, без неявной зависимости от порядка pivot/SQL.
6. Не вводить пагинацию, поиск или новые параметры без проверки существующего frontend-контракта и согласования. Если текущие каталоги требуют пагинацию — зафиксировать это как отдельный вопрос до реализации.

## 6. Тесты и проверки

Добавить feature tests на тестовой БД, используя factories/явное создание данных по принятым в проекте паттернам и `Storage::fake()` при необходимости:

1. Без фильтра: только опубликованные каталоги, корректный порядок и стабильный tie-break.
2. Фильтр по slug: совпадения; unknown slug → `200` и пустой список; multiple categories не дают дубликатов.
3. Категории в DTO: правильные идентификаторы, slugs, названия, порядок; проверить статус категорий в соответствии с существующими правилами.
4. Контракт DTO: `public_id` как `id`, корректный публичный URL обложки, nullable description и alt.
5. Security: ни в одном объекте ответа нет PDF-путей, PDF URL, временных download links или внутренних файловых данных.
6. Empty state: отсутствие опубликованных записей возвращает успешный пустой ответ.
7. Query count / eager loading: проверка, подтверждающая отсутствие N+1 при нескольких каталогах (выбрать устойчивый к тестовой среде способ).
8. Ошибочные параметры: согласованная валидация и отсутствие 500 для пользовательского ввода.
9. Regression: существующие тесты категорий и каталогов проходят.

Запустить полный backend suite в доступном Docker/test окружении, Pint для изменённых файлов и `git diff --check`. Не запускать миграции production.

## 7. Критерии приёмки

- `GET /api/v1/catalogues` возвращает опубликованные каталоги и поддерживает `category=<slug>`.
- Порядок стабилен; записи не дублируются.
- DTO соответствует утверждённым публичным полям и действующему формату API.
- PDF и приватные файловые пути нигде не раскрываются.
- Ошибки обрабатываются явно, нет mock fallback.
- Все новые и регрессионные тесты проходят.
- Не изменены Next.js, Filament, публичный дизайн, логика скачивания и посторонние незакоммиченные файлы.
