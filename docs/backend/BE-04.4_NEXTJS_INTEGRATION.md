# BE-04.4 — Next.js Catalogues Integration

**Проект:** Pots & Planters 2.0  
**Статус:** техническое задание, реализация не подтверждена  
**Зависимости:** BE-04.1/04.1a/04.2/04.3 реализованы по отчётам; браузерная проверка Filament выполнена пользователем.

## 1. Цель

Заменить mock-источник каталогов реальным `GET /api/v1/catalogues` во всех текущих потребителях Next.js, включая `/catalogues` и домашний слайдер, без изменения публичного дизайна, маршрутов, SEO и поведения модального окна заявки. PDF остаются приватными; отправка заявки и скачивание — BE-07.

## 2. Перед началом: read-only сверка

1. Изучить `docs/common/PROJECT_CONTEXT.md`, `docs/common/ROADMAP.md`, актуальный `git status` и diff, включая ручные правки. Ничего не сбрасывать и не форматировать вне scope.
2. Проверить `frontend/src/lib/catalog/repository.ts`, `frontend/src/types/catalog.ts`, `frontend/src/app/catalogues/page.tsx`, `catalogues.mock.ts`, домашний слайдер, форму/модальное окно и все импорты catalog fixtures. Найти все потребители через поиск по репозиторию.
3. Прочитать фактический JSON и реализацию `GET /api/v1/catalogues` в backend (controller/resource/tests). Не угадывать поля, envelope, nullable, URL обложек, фильтрацию и сортировку.
4. Изучить существующие `serverApiFetch`, `API_INTERNAL_URL`, DTO/адаптеры категорий и принятые правила cache/revalidation и ошибок. Уточнить, где используется category `public_id`, а где slug.
5. При расхождении ТЗ с кодом сообщить и предложить минимальное решение; не перестраивать архитектуру.

## 3. Контракт и границы

- Источник истины — Laravel `GET /api/v1/catalogues`; фильтр `?category=<category-slug>` (например `outdoor-pots`, `indoor-pots`, `artificial-plants`). Значения `outdoor`, `indoor`, `artificial` — `public_id` категорий, не URL slug.
- Каталог может относиться к нескольким категориям. Сохранять корректность тегов и фильтра, без дублирования карточек.
- Публичный DTO каталога содержит стабильный идентификатор, slug, title, description, публичную обложку и alt, идентификаторы/данные опубликованных категорий — точные имена и вложенность сверить по API. Не добавлять PDF path, download URL, внутренние storage-пути.
- API вызывается сервером Next.js через существующий `serverApiFetch`/`API_INTERNAL_URL`; не раскрывать внутренний адрес в клиентском bundle. Не использовать отдельный mock-fallback.
- Не менять backend API, Filament, DB, дизайн, тексты интерфейса без необходимости, SEO маршруты и другие модули. Не добавлять зависимости без причины.

## 4. Реализация по шагам

### Шаг A — DTO и repository

**Изменения:** ввести/адаптировать типы ответа API и преобразование в текущую UI-модель, сохраняя существующие потребительские контракты по возможности. Заменить чтение `catalogues.mock.ts` на серверный API-вызов. Использовать существующую инфраструктуру fetch и её поведение ошибок. Валидировать/нормализовать nullable-поля только на основании реального API. Не выдумывать данные или изображения при отсутствии полей.

**Приёмка:** каталог берётся только из API; ошибки не превращаются в пустые mock-списки; приватные поля не появляются в UI DTO.

### Шаг B — страница `/catalogues`

**Изменения:** сохранить существующую разметку, карточки, порядок, модальное окно и query `category`. Передавать category slug серверному API, не подменять его category `public_id`. При отсутствии фильтра отображать все опубликованные каталоги. Неизвестный slug должен давать предсказуемый пустой результат, а не скрытую подмену данных. Существующий список категорий остаётся из реального API категорий.

**Приёмка:** `/catalogues`, `/catalogues?category=outdoor-pots`, `indoor-pots`, `artificial-plants` работают с данными API; many-to-many корректен; query сохраняется при взаимодействии; текущие маршруты и SEO не сломаны.

### Шаг C — домашний слайдер

**Изменения:** подключить тот же серверный репозиторий, без дублирования mock-логики. Сохранить существующий UI, ограничения количества и порядок, если они определены в коде; не изобретать новые бизнес-правила.

**Приёмка:** слайдер показывает опубликованные каталоги из API; при отсутствии данных отображает предусмотренное честное пустое состояние, без фиктивных карточек.

### Шаг D — ошибки, кеширование, чистка

**Изменения:** обеспечить явное поведение при недоступности API (существующий error boundary/серверная ошибка/состояние ошибки — выбрать согласно архитектуре). Не маскировать ошибку пустой выдачей. Проверить актуальность после изменений в Filament: использовать существующую политику SSR/cache/revalidation, не вводить произвольный длительный cache. Удалить неиспользуемые mock-импорты и fixtures только каталожного модуля после проверки всех потребителей; не трогать product mocks. Если файл нужен другим модулям, не удалять его преждевременно.

**Приёмка:** API failure наблюдаем, нет скрытого fallback; опубликованные изменения появляются согласно согласованной политике кеша; не осталось активных mock-потребителей каталога.

## 5. Форма заявки и безопасность

- Оставить существующий модальный сценарий и честное уведомление о ещё не подключённой доставке PDF. Не показывать фиктивный success и не предлагать рабочее скачивание.
- Не передавать в браузер PDF storage path, приватные API credentials или `API_INTERNAL_URL`.
- Не добавлять endpoint выдачи PDF; реализация заявок и gated download остаётся BE-07.

## 7. Критерии завершения

- `/catalogues` и домашний слайдер используют реальный Laravel API.
- Фильтр `category=<slug>` и many-to-many работают; нет дубликатов.
- UI, маршруты, SEO и модальная форма не изменили согласованного поведения.
- Нет скрытого fallback на mock, не затронуты product mocks.
- Нет публичного доступа к приватным PDF или фиктивного успеха заявки.
- Пройдены доступные проверки, известные ограничения перечислены.
