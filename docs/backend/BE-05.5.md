# BE-05.5 — News: финальная приёмка и актуализация документации

**Проект:** Pots & Planters 2.0  
**Этап:** BE-05.5  
**Тип:** проверка, точечные исправления только по подтверждённым дефектам, документация  
**Статус:** ТЗ; выполнение не подтверждено

## 1. Цель

Независимо проверить вертикальную интеграцию News: MariaDB → Laravel → Filament 5 → `/api/v1` → Next.js 16, включая импорт семи исторических публикаций, RichEditor, live preview, SEO и обработку ошибок. Зафиксировать результаты и остаточные ограничения. Не считать модуль завершённым без фактических проверок.

## 2. Контекст и обязательные решения

Перед работой прочитать `PROJECT_CONTEXT.md`, `ROADMAP.md`, задания/отчёты BE-05.1–BE-05.4 и актуальный код. Репозиторий — источник истины; учитывать незакоммиченные и ручные изменения. Стек не менять. Публичный дизайн не менять.

- Источник исторических материалов — проверенный snapshot из семи существующих mock-публикаций, не новые придуманные тексты.
- Для INDEX 2025 каноническая обложка — `5_new.png`.
- Новости редактируются в Filament RichEditor; категории управляются отдельно.
- Slug автоматически предлагается из title, допускает ручную правку и изменение после публикации; автоматические redirects не вводить.
- SEO исторических статей — из существующих mock-данных; SEO архива `/news` — из Page SEO API.
- Google Search Preview переиспользуется; News Live Preview — отдельный инструмент.
- Новые опубликованные slug должны работать без пересборки Next.js.
- Sitemap не входит в BE-05; не добавлять.
- Runtime mock fallback запрещён.
- Production-миграции, production-импорт и деплой без отдельного разрешения запрещены.

## 3. Этап A — read-only сверка и матрица приёмки

**Цель:** установить фактическое состояние перед проверками.

1. Проверить `git status --short`, diff и локальные инструкции запуска; не затирать изменения BE-05.2–05.4.
2. Сверить миграции, модели, sanitizer, DTO, API, Filament Resources, preview, импортёр, frontend repository, маршруты, SEO и тесты с фактическим кодом.
3. Составить матрицу «требование → файл/тест → результат»; отличать реализованное от реально проверенного.
4. Убедиться, что импорт исторических записей в обычную локальную БД не выдаётся за production-импорт.

**Приёмка:** есть список подтверждённых компонентов, рисков и проверок без несанкционированных изменений.

## 4. Этап B — end-to-end функциональность

**Цель:** проверить Filament → БД → API → SSR.

На изолированной тестовой БД и тестовом storage проверить:

- Создание категории, создание черновика новости, редактирование RichEditor, обложки, alt, excerpt, SEO и даты.
- Draft не виден в публичном API/SSR; после публикации статья появляется в `/news` и `/news/{slug}` без frontend rebuild.
- Редактирование заголовка и slug: автоматическая генерация не перезаписывает вручную заданный slug; новый адрес работает, старый без специально настроенного редиректа возвращает 404.
- Изменения текста, обложки, даты и SEO отражаются в API и SSR.
- Архивация скрывает статью; неизвестные slug возвращают 404.
- Деактивация категории не удаляет статьи, но соблюдает публичную политику видимости; удаление категории со статьями запрещено.
- Live Preview показывает **несохранённые** значения, в том числе RichEditor HTML, дату, категорию, обложку и excerpt; Google Search Preview остаётся независимым.
- Обработка недоступного API, 5xx, некорректного DTO и отсутствия медиа не подменяет данные mock-значениями и не симулирует успех.

Если браузерные проверки невозможны, явно отметить это и не называть их пройденными. Не изменять рабочую БД ради тестов.

**Приёмка:** результаты каждого сценария записаны, проблемы воспроизводимы.

## 5. Этап C — семь исторических публикаций и импорт

**Цель:** подтвердить точное сохранение исходного контента.

1. Сопоставить все семь записей fixture с frontend mock/snapshot: `public_id`, slug, title, excerpt, дата, SEO, alt, тело, inline-ссылки, обложка.
2. Проверить изображение `5_new.png`, остальные шесть обложек и корректные публичные URL, отсутствие внутренних storage paths.
3. Проверить порядок статей №6 и №7 с датой `2025-10-30`, не придумывая время публикации.
4. Проверить dry-run по умолчанию, явное подтверждение записи, повторный запуск без дубликатов и защиту редакторских изменений.
5. Проверить SHA-256/целостность исходных изображений и отсутствие непроверенных исторических утверждений, добавленных при импорте.
6. Проверить корректные inline-ссылки Greenpact/Ficus/Jumeirah; не переносить ошибочные labels из неиспользуемого `externalLinks`.

**Приёмка:** 7/7 сопоставлены, импорт идемпотентен и безопасен.

## 6. Этап D — безопасность и SEO

**Цель:** убедиться в безопасности RichEditor и корректности индексируемых страниц.

- Проверить allowlist sanitizer при сохранении и выдаче: `script`, обработчики `on*`, `javascript:`/опасные URI, iframe и небезопасные атрибуты удаляются; допустимые абзацы, заголовки, списки, выделения и ссылки сохраняются.
- Проверить совместимость реального HTML RichEditor с frontend SSR и preview; отсутствие двойного экранирования и XSS.
- Проверить внешние ссылки, `rel`/`target`, URL обложек и отсутствие приватных путей в DTO и HTML.
- Для `/news` проверить Page SEO API; для `/news/{slug}` — title, description, canonical, Open Graph, Twitter и NewsArticle JSON-LD; дата должна соответствовать подтверждённой календарной дате, не выдумывать `dateModified`.
- Проверить unknown/draft/archived slug, canonical и отсутствие индексации непубличного контента.
- Проверить отсутствие runtime импортов `news.mock.ts` в публичном News-пути.

**Приёмка:** проверенные тестами сценарии безопасности и SEO, без изменения существующего публичного дизайна.

## 7. Этап E — регрессия и визуальная проверка

- Запустить backend News tests и полный backend suite через Docker **только** с `potsandplanters_test`; перед запуском проверить фактическое подключение к тестовой БД.
- Запустить frontend typecheck, имеющиеся тесты (News и затрагиваемые catalog/product/enquiry/forms), `NODE_ENV=production` build.
- Выполнить SSR smoke для `/news`, всех семи slug, новой записи после сборки, 404 и ошибок API.
- Проверить адаптивность архива и статьи, изображения, ссылки, типографику и preview на desktop/mobile, если доступен браузер; не менять дизайн без запроса.
- Запустить Pint на изменённых PHP-файлах, `git diff --check`; отсутствие frontend lint script отметить как ограничение, не создавать его только ради BE-05.5.
- Не выполнять тесты против production или общей рабочей БД.

**Приёмка:** приложены реальные команды, результаты, число тестов/assertions, результаты smoke и список непроверенных пунктов.
