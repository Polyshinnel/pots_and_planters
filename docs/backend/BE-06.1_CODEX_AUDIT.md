# BE-06.1 — Contacts & Showrooms: read-only аудит

## Контекст
Проект Pots & Planters 2.0. Прежде чем приступать к работе, прочитай `PROJECT_CONTEXT.md` и `ROADMAP.md` в репозитории. Если документы отсутствуют или расходятся с кодом, явно зафиксируй это. Репозиторий — источник истины о реализации.

Стек: Next.js 16, React 19, TypeScript, Mantine 9; Laravel 13, PHP 8.4, Filament 5; MariaDB, Redis, Horizon. Публичный сайт на английском. Технический отчёт — на русском.

BE-05 завершён и принят владельцем. BE-06 касается контактов и шоурумов. Из handoff известны три точки: DEVA HARMONY TRADING (Al Quoz, Dubai), Real Touch Flowers (Jebel Ali, Dubai), Design House Projects (Riyadh). Это ориентиры для поиска в существующем коде, а не разрешение придумывать адреса, телефоны, часы или координаты.

## Цель
Подготовить проверенный по коду план вертикальной реализации BE-06 (MariaDB → Laravel → Filament → API → Next.js → тесты), чтобы Header, Footer и Contacts использовали единый источник данных. На данном этапе **ничего не реализовывать**.

## Жёсткие ограничения
- Только read-only: не редактировать файлы, не создавать миграции, не выполнять команды, изменяющие БД, storage или состояние репозитория. Не запускать миграции, сидеры, форматирование, автопочинку или деплой.
- Не менять публичный дизайн, маршруты, SEO и поведение пользователей.
- Не вводить скрытый fallback на mock при сбое API.
- Не менять утверждённый стек, не добавлять зависимости и не проектировать абстрактный UI framework.
- Учитывать существующие незакоммиченные и ручные изменения; сообщить `git status --short`, не очищая рабочее дерево.
- Не смешивать BE-06 с BE-07: отправка contact form, сохранение заявок и Telegram относятся к BE-07. В BE-06 только инвентаризация формы и её контрактов.
- Production операции запрещены без отдельного разрешения.

## Задачи аудита

### 1. Карта текущего frontend
Найти и перечислить с точными путями:
- страницы `/contacts` и возможные связанные маршруты;
- Header, Footer, мобильное меню, общие layout-компоненты;
- все места вывода телефонов, email, адресов, WhatsApp, карт, ссылок на маршруты, часов работы, названий шоурумов;
- формы обратной связи и их текущие зависимости (без реализации отправки);
- источники данных: inline literals, fixtures/mock, config, API, server/client components, кэширование;
- существующие тесты для контактов, layout и форм.

Указать фактические поля каждой точки и отличия между отображением в Header/Footer/Contacts. Не заполнять неизвестные значения догадками.

### 2. Карта backend и Filament
Проверить существующие модели, таблицы, миграции, settings, Filament Resources/Pages, API routes/controllers/resources, media handling и SEO для контактов. Определить, какие компоненты можно повторно использовать, включая общий Google Search Preview. Проверить соглашения по опубликованности, сортировке, slug, nullable полям, DTO, валидации и тестам.

### 3. SEO и пользовательское поведение
Зафиксировать действующие URL, metadata, canonical, JSON-LD (если есть), текстовые блоки и ссылки на карте. Выяснить, как формируются `tel:`, `mailto:`, WhatsApp и внешние ссылки; отметить, какие значения необходимо сохранить без изменений. Проверить, не используется ли контактная информация в других разделах сайта.

### 4. Архитектурное предложение
На основе фактического кода предложить минимальную модель единого источника данных:
- разделить глобальные контакты компании и отдельные showroom records **только если это оправдано найденными данными**;
- описать поля, nullable/required, сортировку, статус публикации и возможную локализацию без преждевременного усложнения;
- предложить Filament UX с повторным использованием существующих паттернов;
- описать минимальные публичные read-only `/api/v1` endpoints и типизированные DTO;
- определить серверную загрузку Next.js, поведение при пустой выдаче и ошибке API, требования к кэшированию;
- показать, как обеспечить согласованность Header/Footer/Contacts без дублирования источников;
- указать, требуется ли Google Search Preview для SEO страницы Contacts и где уже управляется SEO статических страниц.

Не считать предложенную схему утверждённой: выделить вопросы, требующие решения владельца.

### 5. План реализации
Составить последовательность BE-06.2 (MariaDB/Laravel/Filament/API), BE-06.3 (Next.js), BE-06.4 (тесты и приёмка). Для каждого этапа дать цель, конкретные файлы/компоненты для изменения, ограничения, тесты и измеримые критерии приёмки. Не писать код.

## Формат отчёта
1. Git status и границы аудита.
2. Таблица найденных источников контактных данных: место, путь файла, источник, поля, замечания.
3. Текущая backend/Filament/API инфраструктура.
4. Матрица текущих контактов и шоурумов (только подтверждённые значения).
5. Риски для дизайна, SEO, SSR, API и форм BE-07.
6. Рекомендуемая минимальная схема и API с аргументацией.
7. Поэтапное ТЗ BE-06.2–BE-06.4 с критериями приёмки.
8. Открытые вопросы к владельцу — только те, на которые нельзя ответить из репозитория.
9. Итог: **аудит завершён / не завершён**, без утверждений о реализации BE-06.

## Критерии приёмки BE-06.1
- Ни один файл и ни одно состояние среды не изменены.
- Все выводы о существующем коде подкреплены путями файлов, по возможности строками.
- Найдены все основные точки использования контактных данных.
- Установлена граница между BE-06 и BE-07.
- Есть конкретный минимальный план реализации, без вымышленных контактных данных и без изменения публичного дизайна.
- Отмечены противоречия документации и репозитория.

После аудита остановись и представь отчёт. **Не приступай к BE-06.2 без отдельного подтверждения.**
