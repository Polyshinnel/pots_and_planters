# BE-06.2 — Contacts & Showrooms: MariaDB → Laravel 13 → Filament 5 → API

## Назначение
Реализовать backend управления контактами и шоурумами Pots & Planters 2.0. Это **только BE-06.2**: frontend, формы заявок и production не изменять. После завершения остановиться, представить отчёт и ждать подтверждения BE-06.3.

## Источники истины и обязательный старт
1. Прочитать `PROJECT_CONTEXT.md`, `ROADMAP.md`, результат BE-06.1 и текущий код репозитория. Сначала `git status --short`, затем read-only сверка существующих моделей, миграций, Filament ресурсов, API, DTO, тестов и Docker Compose команд.
2. Репозиторий — источник истины для текущей реализации; не предполагать, что пути, классы или тестовые команды совпадают с этим документом. Не затирать ручные изменения и не проводить посторонний рефакторинг.
3. При существенном противоречии или риске потери данных остановиться и сообщить, не выбирать решение молча.

## Подтверждённые решения владельца
- DEVA HARMONY TRADING — основная компания и главный шоурум; её контакты используются как primary. Real Touch Flowers и Design House Projects — дополнительные шоурумы.
- **Все значения** существующего `frontend/src/data/contacts.mock.ts` подтверждены владельцем как актуальные, включая написание адресов, контакты, Instagram и порядок. Не нормализовать отображаемые тексты по догадке.
- Глобальный WhatsApp: `https://api.whatsapp.com/send/?phone=971585802562&text&type=phone_number&app_absent=0`. Сохранить URL без самовольного изменения query-параметров.
- Не добавлять часы работы, геокоординаты, специальные Maps URL и медиа, если они отсутствуют в подтверждённом fixture. Header остаётся без изменений.
- Contacts Page SEO уже управляется Page SEO Resource и общим `SeoSearchPreview`; не дублировать SEO-редактор.
- BE-07 отвечает за `POST /api/v1/enquiries`, Telegram, сохранение форм и gated PDF. В BE-06.2 не касаться этих механизмов.

## Архитектура — базовый вариант
1. `showrooms`: отдельные записи с явным идентификатором, отображаемыми полями и статусом публикации; порядок `sort_order`, затем `id`. Выбрать минимальную схему, соответствующую реально используемым полям fixture и существующим Laravel-паттернам. Телефонов/email может быть несколько: сохранить исходный порядок, подписи и href. Не терять поля при преобразовании.
2. `site_contact_settings` или аналогичная singleton-настройка: `primary_showroom_id` (ссылка на DEVA), `whatsapp_url` (nullable). Не копировать телефоны и email DEVA в настройки — primary вычисляется из указанного шоурума. Избежать возможности нескольких конкурирующих singleton-записей.
3. Выдавать публично только опубликованные шоурумы. Primary должен ссылаться на опубликованную запись. Определить и тестировать поведение, если primary не задан, скрыт или удалён: **не назначать другой шоурум primary автоматически**. Вернуть явный `primary: null` либо другой документированный безопасный контракт; не отдавать draft через primary.
4. Для draft допустимы неполные поля, для published обеспечить необходимые значения (имя, адрес и прочие реально обязательные публичные поля). Проверки должны быть на серверной стороне, а не только в Filament. Не добавлять поля «на будущее» без оснований.
5. API `GET /api/v1/contacts`: один согласованный JSON envelope `{ "data": { "primary": ..., "whatsappUrl": ..., "showrooms": [...] } }` (имена уточнить по принятым DTO conventions). Включить `primary` как полноценный объект или ссылку на элемент списка — выбрать один ясный контракт, документировать его. Никаких внутренних PK, draft, storage paths, административных полей в публичном DTO. Для отсутствующих optional значений — явные `null`/пустые массивы по контракту. `Cache-Control: no-store`, как в существующих публичных endpoint, если это подтверждено кодом.
6. Не делать скрытый fallback на fixture. Пустая БД — валидный пустой ответ, а не ошибка и не подстановка контактов.

## Этап A — схема и модели
**Цель:** минимальная управляемая модель без дублирования primary.
- После аудита предложить точный список таблиц/полей и кратко объяснить хранение множественных телефонов/email (JSON или связанные строки, исходя из кода и требований; не создавать универсальную EAV-систему).
- Миграции обратимые; внешние ключи и ограничения согласованы с удалением/скрытием primary. Без автоматического изменения production.
- Модельные методы/scopes для published и стабильного порядка; централизованная валидация публикации.
**Приёмка:** схемы достаточно для всех подтверждённых значений fixture, при удалении/скрытии primary нет утечки draft или неявного переключения.

## Этап B — Filament
**Цель:** редактирование контактов без разработчика.
- Ресурс Showrooms: создание, редактирование, draft/published, сортировка, проверка URL/email/телефонов, ясные подписи, необязательные поля. Поддержать повторяющиеся телефоны/email без потери порядка.
- Отдельный простой экран настройки `primary_showroom` и `whatsapp_url` (или минимальный singleton resource согласно текущим Filament паттернам). Ограничить primary опубликованными шоурумами либо при публикации обеспечить непротиворечивость.
- Не менять существующие SEO ресурсы и общий Google Search Preview. Не строить абстрактный редактор контактов для будущих модулей.
**Приёмка:** редактирование и публикация работают, неверные URL/email и неполная публикация отвергаются, singleton нельзя случайно размножить.

## Этап C — API и DTO
**Цель:** один предсказуемый read-only источник для frontend.
- Типизированный DTO в `backend/app/Data` по образцу существующих сущностей; контроллер, маршрут `/api/v1/contacts`.
- `primary` связан с указанным опубликованным шоурумом; `showrooms` отсортированы и не содержат drafts; WhatsApp может быть null. Не раскрывать внутренние атрибуты.
- Сохранить отображаемые строки и href контактов. Не генерировать координаты, не утверждать точность Google Maps pin.
**Приёмка:** корректные envelope, сортировка, nullable, published filtering, empty state и no-store; ошибки сервера не маскируются.

## Этап D — перенос подтверждённых данных
**Цель:** безопасная подготовка записей, не трогая production.
- Подготовить идемпотентный способ переноса **строго** трёх утверждённых шоурумов из актуального fixture и указанного WhatsApp URL (например, отдельная команда/сидер с явным запуском). До записи показать dry-run/план и отличия от существующих данных.
- Не перезаписывать вручную изменённые значения при повторном запуске. Если безопасное сопоставление не доказано, остановиться с конфликтом.
- **Не запускать импорт в production.** Разрешены только изолированные тестовые БД/окружения по правилам проекта. Если отсутствует безопасное окружение — ограничиться тестами и dry-run.
**Приёмка:** перенос повторяем, сохраняет все поля/порядок и не выдумывает значений; production не затронут.

## Этап E — проверки
- Использовать команды тестирования из репозитория, только безопасное тестовое окружение Docker Compose. Проверить миграции/rollback на тестовой БД, Laravel tests (API + Filament + существующая suite), Pint/форматирование, `git diff --check`.
- Тест-кейсы: 3 published; draft исключён; sort_order/id; primary DEVA; primary hidden/deleted; empty DB; null WhatsApp; множественные телефоны/email; URL validation; запрет некорректной публикации; идемпотентный импорт; отсутствие внутренних полей.
- Не запускать production deploy/migrate/seed/import. Не менять frontend, дизайн, `/contacts`, `/about`, Header, Footer, формы или SEO.
