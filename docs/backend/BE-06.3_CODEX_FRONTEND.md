# BE-06.3 — Contacts & Showrooms: Next.js Integration

## Статус и цель
BE-06.2 принят владельцем после тестов и ручной проверки: тестовый импорт выполнен, `/api/v1/contacts` возвращает три утверждённых шоурума, DEVA — primary, WhatsApp подтверждён, Filament проверен. Это ТЗ только для BE-06.3. Цель: заменить runtime fixture контактов на API во всех потребителях Next.js без изменения публичного дизайна, маршрутов, SEO и поведения форм.

## Подтверждённый контракт
`GET /api/v1/contacts` возвращает `{data:{primary: Showroom|null, whatsappUrl:string|null, showrooms:Showroom[]}}`. Showroom: `id`, `name`, `description` (может быть nullable), `address`, `city`, `country`, `phones:[{label,href}]`, `emails:string[]`, `instagram:{handle,url}|null`; другие поля — только если реально поддержаны API. Публичный ID — строка, не внутренний PK. `primary` — полный объект DEVA HARMONY TRADING. Showrooms упорядочены backend. Не делать дополнительную сортировку, меняющую порядок.

Подтверждены три шоурума: DEVA HARMONY TRADING (primary), Real Touch Flowers, Design House Projects. Использовать значения из API, не копировать их в production TS. Подтверждённый WhatsApp — `https://api.whatsapp.com/send/?phone=971585802562&text&type=phone_number&app_absent=0`, но получать его из API, не хардкодить. Пустой/null URL означает отсутствие WhatsApp CTA.

## Ограничения
- Стек Next.js 16, React 19, TypeScript, Mantine 9. Только существующие подходы `serverApiFetch`, `API_INTERNAL_URL`, `no-store`, типизированные DTO; без новых зависимостей.
- Не изменять backend, БД, Filament, импортёр и production. Если нужна backend-правка, сначала сообщить и остановиться.
- Не менять Header/мобильное меню: там только навигация Contacts. Не менять дизайн, стили, текст, порядок, ссылки и UX без необходимости.
- Сохранить `/contacts`, `/about`, canonical `/contacts`, Page SEO API, метаданные, OG, существующие маршруты и внешние ссылки. Не добавлять LocalBusiness/Organization JSON-LD или отдельное SEO шоурумов.
- Не включать отправку форм, Telegram, `/api/v1/enquiries` и gated PDF: это BE-07. Не имитировать успешную отправку.
- Не создавать скрытый fallback на mock, `siteConfig`, захардкоженные контакты, пустой успешный DTO или stale cache при ошибке API.
- `contacts.mock.ts` допускается только как тестовый fixture, если нужен тестам. В runtime не должно остаться импортов.

## Этап 1. Типы и серверный клиент
- Создать/адаптировать точный TypeScript DTO для API envelope; проверить nullable и пустые массивы.
- Добавить серверную функцию получения контактов через существующий `serverApiFetch` с явной обработкой HTTP/сетевых ошибок и без кэширования. Не импортировать server-only код в client components.
- Если UI использует старую форму типов, выполнить узкое преобразование DTO в view props без потери label/href, порядка, отсутствующих email/Instagram и URL. Не генерировать новые номера, email или Instagram URLs, если API уже содержит их.
- Сохранить существующую логику Google Maps Search по адресу там, где directionsUrl отсутствует; не изобретать координаты или подтверждённый pin.

## Этап 2. Серверная граница глобального shell
- Исследовать реальную структуру `RootLayout`, `SiteShell` (client), `HomeLayout`, Footer, FloatingActions. Выбрать минимальную server-side точку загрузки и передавать сериализуемые props в client компоненты. Избегать дублирующих запросов в одном дереве, где возможно; допускается React request memoization только при проверенной совместимости и без межзапросного stale-cache.
- При ошибке API на глобальном shell: явно логировать ошибку на сервере и показывать нейтральное состояние **без контактных значений** (например, скрыть только контактный блок Footer и WhatsApp action, сохранив навигацию и основной контент). Это *не* замена API на mock и не выдача пустого результата за успешный. Продумать различие «API успешно вернул пустые данные» и «API недоступен». Не допускать падения всех маршрутов из-за Footer.
- Страница `/contacts` должна иметь явное видимое состояние недоступности данных при ошибке API (с сохранением остальной страницы/формы согласно существующему UX), без выдуманных телефонов; успешный пустой список должен иметь отличимое корректное поведение. Использовать минимальные изменения, не редизайн.
- Проверить, что SSR на всех страницах реально отражает обновлённые данные после изменения в Filament без production rebuild.

## Этап 3. Потребители
- `/contacts`: primary и showrooms из API; форма и CTA без изменений. Отсутствие primary не подменять первым showroom, если это не согласовано; отобразить отсутствие основных контактов корректно.
- `/about`: showrooms из того же источника, пустой список — прежнее скрытие секции.
- `SiteFooter`: primary и showrooms из API; сохранить текущую структуру, телефоны/email/Instagram только там, где они уже отображались.
- `FloatingActions` и проектные CTA: брать WhatsApp URL из API, если null — оставлять согласованный альтернативный переход `/contacts#project-enquiry` и не показывать ложную WhatsApp кнопку. Найти все реальные места использования `siteConfig.whatsappUrl` и `project-contact.ts`; не менять бизнес-логику корзины и заявок.
- Header оставить визуально и функционально неизменным.
- Проверить главную, каталоги, товары, корзину и другие общие shell-варианты; никакой клиентский импорт server-only модуля.

## Критерии приёмки
- Все runtime-потребители контактов используют API, включая Footer, Contacts, About и WhatsApp CTA.
- Отображаются ровно опубликованные showrooms, в API-порядке; primary — DEVA; необязательные поля корректно обрабатываются.
- Контакты в Filament меняют SSR без пересборки frontend; нет hardcode/mock fallback.
- API outage не приводит к падению всего сайта и не маскируется фиктивными данными; на Contacts есть явное состояние ошибки.
- Header, дизайн, формы, SEO, URL и внешние ссылки сохранены.
- Тесты и smoke подтверждены, изменения ограничены BE-06.3.
