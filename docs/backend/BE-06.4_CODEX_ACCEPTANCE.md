# BE-06.4 — Финальный аудит и приёмка Contacts & Showrooms

## Цель
Независимо проверить реализацию BE-06.2 и BE-06.3 в **актуальном репозитории** и подтвердить сквозную интеграцию MariaDB → Laravel → Filament → API → Next.js. Не объявлять модуль завершённым до проверки фактов и ручной приёмки владельцем.

## Обязательный контекст
Прочитай `PROJECT_CONTEXT.md`, `ROADMAP.md`, предыдущие ТЗ BE-06 и текущий `git status --short`. Существующие незакоммиченные файлы и ручные изменения сохраняй. При расхождениях документации и кода приоритет у фактического кода, но явно зафиксируй расхождения.

## Границы
- Сначала **read-only аудит** diff, маршрутов, DTO, серверной загрузки, контекстного provider, компонентов и тестов.
- Допустимы минимальные исправления **только выявленных дефектов BE-06** после их документирования; не делай посторонний рефакторинг.
- Не меняй утверждённый Header, публичный дизайн, тексты, маршруты, SEO, формы и поведение BE-07.
- Никаких production-миграций, production-import, production-deploy, записи в production и тестовых уведомлений пользователям.
- Все операции с БД только в проверенном тестовом окружении. До любых записей явно установи фактическое соединение и имя БД.
- Не вводи mock fallback при ошибках API; не возвращай фиктивные контактные данные.

## Подтверждённые бизнес-правила
- DEVA HARMONY TRADING — основной showroom/primary; Real Touch Flowers и Design House Projects — дополнительные.
- Подтверждённые значения исходного contacts fixture сохраняются, включая написание адресов, телефоны, email, Instagram и порядок.
- WhatsApp: `https://api.whatsapp.com/send/?phone=971585802562&text&type=phone_number&app_absent=0`.
- Часы работы, координаты и новые ссылки не добавлять. Header не изменять.
- API: `GET /api/v1/contacts`, envelope `{ data: { primary, whatsappUrl, showrooms } }`.
- При пустой базе: `primary: null`, `whatsappUrl: null`, `showrooms: []`.

## Этап A — Read-only ревизия
1. Зафиксируй git status и полный перечень изменений BE-06.2/06.3, отдельно перечисли чужие/ручные изменения.
2. Проследи схему и ограничения `showrooms`, `site_contact_settings`, модели, сериализацию JSON-полей, валидацию публикации, стабильный public ID, primary только опубликованного showroom.
3. Проверь Filament CRUD, настройки singleton, права доступа, валидацию, порядок, защиту от дублирования и случайного удаления primary.
4. Проверь импортёр `contacts:import-confirmed`: dry-run без записи, `--apply` только по явному флагу, повторный запуск, конфликты без перезаписи, сохранение утверждённых данных. Не применяй импорт повторно без необходимости.
5. Проверь API: published-only, сортировка, null/empty, DTO без внутренних PK, storage paths и секретов, `Cache-Control: no-store`.
6. Проследи все frontend-потребители: `/contacts`, `/about`, Footer на обычном и Home layout, FloatingActions, Home, Product, Cart/Enquiry, Catalogues, `project-contact`, siteConfig и мобильные компоненты. Не ограничивайся поиском одного имени fixture.
7. Проверь границы server/client, сериализуемость props, отсутствие `server-only` импорта в client, отсутствие повторной сортировки и скрытого fallback. Убедись, что контактные данные в глобальном layout не оказываются закэшированы или зафиксированы на build-time.
8. Проверь сохранение `tel:`, `mailto:`, Instagram, направления Google Maps, fallback CTA `/contacts#project-enquiry`, безопасных `target`/`rel`.
9. Проверь сохранение SEO `/contacts`: Page SEO API, canonical, OG/Twitter, H1, отсутствие непроверенной JSON-LD. Не изменяй `/private-policy` в этом этапе.
10. Составь таблицу: требование → файлы → результат → доказательство → риск.

- Backend Laravel full suite, тесты Contacts API, Filament и importer.
- Pint для затронутых файлов; общий Pint отдельно, существующие style issues фиксируй без массовых исправлений.
- Frontend TypeScript typecheck; доступные Contacts, catalog, product, enquiry, forms suites.
- `NODE_ENV=production` Next.js production build.
- `git diff --check` и поиск runtime mock/захардкоженных контактных данных.
- При падении тестов отдели регрессию BE-06 от ранее существовавшей проблемы; ничего не скрывай.

## Этап C — Сквозная проверка и негативные сценарии
На локальном/staging тестовом окружении с реальным API:
1. Подтверди `/api/v1/contacts`: три опубликованных шоурума, DEVA primary, точные значения и порядок.
2. SSR `/`, `/contacts`, `/about`, `/catalogues`, `/cart` и другие фактически затронутые маршруты: статусы, HTML, Footer, ссылки, canonical, OG, отсутствие приватных URL.
3. Подтверди, что **изменение в Filament или тестовой БД** отражается в API и SSR без Next.js rebuild. Используй только безопасную временную тестовую правку с фиксацией исходного значения и гарантированным восстановлением. Если нет безопасного способа, не изменяй данные и обозначь проверку как не выполненную.
4. Проверка смены primary: только на тестовой БД, с восстановлением; primary меняется в API и всех потребителях. Проверь поведение при снятии публикации primary.
5. Empty API: страница Contacts показывает empty-состояние, About корректно скрывает секцию, Footer остаётся работоспособным, нет mock.
6. Ошибка API (503/недоступность): Contacts отображает ошибку и форму; глобальный shell и навигация не падают; CTA не получает ложный WhatsApp URL; сбой явно наблюдаем/логируем без раскрытия секретов.
7. Проверка переходов и доступности ссылок (как минимум атрибуты в SSR; браузерные проверки при наличии инструмента).
8. Отдельно отметь, если browser-level интерактивность не проверялась.
