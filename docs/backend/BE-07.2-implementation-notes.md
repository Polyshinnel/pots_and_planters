# BE-07.2 implementation notes

## Scope implemented

- `POST /api/v1/enquiries` persists supported enquiries in MariaDB and returns success only after the transaction commits.
- A one-day idempotency record stores hashes of the key and normalized payload. Replays return the original public enquiry ID; a changed payload returns `409`.
- The same transaction creates an outbox event and snapshots every enabled Telegram recipient's signed `BIGINT` chat ID. Delivery rows are durable and independent per recipient; this stage does not dispatch or send them.
- Telegram settings and recipient tables are present for BE-07.3/07.4. Bot token and proxy password use Laravel's encrypted cast. No settings screen, proxy client, Telegram API request, or delivery job is included here.
- `TelegramSettingsManager` validates proxy host/port and paired Basic-auth credentials, preserves existing secrets when edit forms submit blank secret fields, and keeps proxy endpoints as host-only values.
- Payloads are limited to 64 KiB; the endpoint is limited to 5/minute and 30/hour per client IP. Honeypot and discriminated field validation reject invalid input without storing it.

## Compatibility and deferred dependencies

- The repository has no authoritative product model or product table yet (BE-08). `product_enquiry` and `cart_enquiry` requests therefore return `404 resource_unavailable`; client-provided names, attributes, and prices are never persisted as product snapshots. Re-enable those types after BE-08 provides server-side product/SKU resolution.
- `catalogue_download` validates a published catalogue and saves its DB-backed title/public ID snapshot. A download grant and PDF response are deferred to BE-07.4.
- `notificationStatus` reports `skipped_disabled`, `pending_no_recipients`, or `pending`. Requests are stored even when Telegram notifications are disabled or no recipients exist.
- Idempotency keys expire after 24 hours. Expired rows are removed on reuse; routine cleanup/retention scheduling is an operations follow-up.

## Operational/security follow-up

- Do not expose this endpoint to real form submissions until the Privacy Policy accurately describes server-side collection, retention, Telegram recipients, and any proxy/provider processing. The current policy says form contents are not transmitted.
- The application still needs BE-07.3 admin controls and BE-07.4 dispatcher/recovery, retry/backoff, HTTP proxy transport, and Telegram tests. No real Telegram requests are part of this stage.
- Only test-database migrations through the configured Docker test suite are in scope. Production migration/import/deploy remains unperformed.
