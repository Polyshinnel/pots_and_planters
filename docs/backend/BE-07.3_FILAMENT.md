# BE-07.3 — Filament: заявки и Telegram Settings

**Проект:** Pots & Planters 2.0  
**Статус:** техническое задание; реализация не начата  
**Основание:** PROJECT_CONTEXT.md, ROADMAP.md, BE-07_ENQUIRIES_TELEGRAM_UPDATED.md, отчёт Codex по BE-07.1 и BE-07.2.

## 1. Цель и границы

Реализовать административный интерфейс Filament 5 для обработки уже сохраняемых заявок и отдельную страницу **Telegram Settings** для управления настройками Telegram, HTTP proxy Squid и несколькими получателями. Работать с существующей схемой BE-07.2, не проектировать её заново без необходимости.

**В BE-07.3 не входят:** реальная отправка сообщений Telegram, Test Connection/getMe, Send Test Message, dispatcher/Horizon jobs/retry, PDF grants, подключение frontend-форм, изменение Privacy Policy и production deploy. Эти действия относятся к BE-07.4/07.5. Не добавлять работающие кнопки, обещающие ещё не реализованные действия.

## 3. Enquiries: список и карточка

Создать ресурс Filament для существующих заявок с доступом только для администраторов по действующему паттерну авторизации.

**Список:** идентификатор, тип (`contact`, `product_enquiry`, `catalogue_download`, `cart_enquiry`), статус, время создания, безопасно отображаемые контактные сведения и индикатор состояния уведомления (если схема это позволяет). Фильтры по типу, статусу, диапазону дат; поиск по явно разрешённым полям. Не включать PII в URL, query string или подробные технические логи. Учитывать пагинацию и стабильную сортировку (новые сверху).

**Карточка:** read-only исходные данные заявки и серверный snapshot; отделять подтверждённые сервером сведения каталога от непроверенных клиентских идентификаторов товаров. Для отсутствующих/неподдерживаемых типов показывать понятное состояние, не придумывать данные. Контактные сведения показывать только авторизованным администраторам. Пользовательский текст выводить безопасно, без HTML-исполнения. Не позволять редактировать исходный payload, snapshot или idempotency key.

**Жизненный цикл:** статусы `new`, `in_progress`, `completed`, `cancelled` — сначала проверить соответствие существующей модели. Реализовать допустимые переходы через сервис/доменную операцию, а не прямое произвольное редактирование полей. Сохранять историю: заявка, старый/новый статус, администратор, timestamp; поддержать внутренние заметки с автором и временем (если схема BE-07.2 не содержит этого — минимально расширить БД и покрыть тестами). Не допускать изменения истории из интерфейса. Запретить обычное удаление заявок, массовое удаление и массовый экспорт PII; не добавлять массовые изменения статусов без необходимости.

**Доставка:** read-only блок outbox и per-recipient deliveries с состояниями, количеством попыток, временем и безопасным описанием ошибки; если доставка ещё не осуществлялась — явно указать это. Не раскрывать токены, proxy credentials, приватные PDF paths и raw exception traces. Не добавлять ручной retry в BE-07.3: фактический retry — BE-07.4.

## 4. Отдельная страница Telegram Settings

Создать отдельную страницу **Telegram Settings** в административной навигации Filament (не внутри ресурса заявок и не в публичных Contacts). Доступ — только `is_admin`; серверная авторизация обязательна, скрытия меню недостаточно. Переиспользовать существующий `TelegramSettingsManager` и таблицы BE-07.2.

**Настройки:**
- `notifications_enabled` — глобальный переключатель;
- Bot Token — masked/password field; encrypted at rest; пустое поле при редактировании означает «оставить существующий»; явная смена и при необходимости отдельное подтверждённое действие очистки;
- `proxy_enabled` — переключатель использования HTTP proxy Squid;
- proxy host и port (`1..65535`), необязательный username, masked proxy password; пустой пароль при редактировании не стирает прежний;
- при отключённом proxy сохранённые реквизиты не удаляются автоматически; при включении обязательные поля валидируются;
- понятные индикаторы «токен настроен», «пароль прокси настроен» без вывода самих значений.

Не принимать произвольный URL Telegram API, proxy URL или пользовательские схемы; фиксированный Telegram API endpoint остаётся в коде. Сохранить существующие проверки host/port и защиту от SSRF; не допускать секретов в URL, логах, flash messages, исключениях, публичном API и HTML-атрибутах с реальными значениями. Не дублировать логику шифрования в Filament. При ошибке сохранения показывать безопасное сообщение; изменения должны быть атомарными.

**Важно:** в этом этапе только сохранение и редактирование настроек. Кнопки `Test Connection` и `Send Test Message` не выводить как действующие до BE-07.4. Можно оставить обозначенное место в интерфейсе без неработающих элементов.

## 5. Получатели Telegram на странице настроек

На странице Telegram Settings разместить управляемый список получателей: `name`, `chat_id`, `enabled`, создание, редактирование, включение/отключение и безопасное удаление/архивирование согласно существующей схеме.

- `chat_id` — signed 64-bit integer, кроме нуля. Принимать положительные значения личных чатов и отрицательные групп/супергрупп (`-100...`). Не использовать unsigned, float и JavaScript Number для преобразования больших ID; передавать и валидировать строкой до серверного приведения с проверкой диапазона.
- Уникальность `chat_id` обеспечить на уровне БД и корректно отображать конфликт в Filament; учитывать soft delete, если используется.
- Отключённые получатели остаются видимыми администраторам, но не выбираются для новых уведомлений на следующем этапе.
- Удаление/изменение получателя не должно менять исторические recipient/chat_id snapshots уже созданных доставок. Если FK препятствует удалению, использовать безопасное отключение или soft delete, а не каскадное уничтожение истории.
- Поддержать несколько получателей и пустой список; отсутствие активных получателей явно показывать как диагностическое состояние, но не блокировать сохранение заявок.
- Не реализовывать тестовую отправку получателю до BE-07.4.

## 6. Безопасность и совместимость

- Только Laravel 13, PHP 8.4, Filament 5, MariaDB; существующий стек без новых зависимостей без необходимости.
- Сохранять `POST /api/v1/enquiries`, контракт идемпотентности и transactional outbox BE-07.2 без регрессий.
- Не менять публичный дизайн Next.js, маршруты, SEO, frontend-формы или корзину.
- Не включать скрытые mock fallback и не создавать фиктивные заявки/уведомления.
- Защитить от mass assignment, IDOR, HTML injection, CSRF и случайного раскрытия PII; права проверять сервером для страниц и действий.
- Существующие события доставки и snapshots считать историческими данными: не переписывать их при изменении настроек.
- Production-миграции, production deploy и реальные Telegram-запросы запрещены без отдельного разрешения.

## 7. Тестирование

Обязательные автоматические проверки на тестовой БД:

1. Администратор видит список и детали заявок; неадминистратор и гость не получают доступ ни к странице, ни к действиям.
2. Фильтры, сортировка и поиск; отображение всех четырёх типов без выдуманных данных; безопасный рендер HTML/спецсимволов из пользовательских полей.
3. Смена статуса и создание истории с actor/timestamp; внутренние заметки; запрет редактирования snapshots и удаления заявки.
4. Telegram Settings: чтение/сохранение флагов, токена, proxy host/port/credentials; пустое секретное поле сохраняет прежнее значение; зашифрованное хранение и отсутствие раскрытия секретов в ответах/логах.
5. Получатели: положительный ID, отрицательный ID и `-100...`, ноль, границы signed BIGINT, невалидный ввод, дубликаты, несколько записей, enabled/disabled, удаление без потери исторических deliveries.
6. Пустой список получателей, отсутствие токена, proxy on/off; в BE-07.3 нет исходящих HTTP-запросов Telegram.
7. Regression: существующие Enquiries API tests (в отчёте BE-07.2 — 16/97), полный применимый Laravel suite, Pint для затронутых файлов, `git diff --check`. Проверить и описать, какие проверки действительно запущены.
8. При возможности — browser-level smoke Filament; если не выполнялся, явно отметить ограничение.

Не использовать реальный Telegram API в тестах. Не выполнять production operations.
