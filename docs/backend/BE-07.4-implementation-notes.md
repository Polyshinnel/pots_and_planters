# BE-07.4 — Telegram delivery and gated PDF

**Статус:** реализовано; автоматические проверки выполняются через HTTP fake. Ожидает ручной приёмки владельца.

## Реализация

- Существующий `POST /api/v1/enquiries` и его транзакционный outbox сохранены. Новая миграция добавляет lease/dispatch-reservation поля per-recipient доставки и таблицу `catalogue_download_grants`.
- Scheduler каждую минуту запускает `enquiries:dispatch-telegram`. MariaDB остаётся источником истины: dispatcher выбирает только due-доставки, резервирует их на 120 секунд перед Redis dispatch и снимает резерв при ошибке enqueue. Потерянный job подбирается после reservation timeout; доставка в `sending` повторно подбирается после 60-секундного lease. Job атомарно захватывает строку через `SELECT ... FOR UPDATE`, присваивает UUID lease и увеличивает attempts. Повторные/параллельные jobs не отправляют строку со статусом `sent` и не проходят действующий lease.
- Каждая доставка — отдельная работа с сохранёнными name/chat ID, включая отрицательные signed BIGINT. Новый список получателей не меняет уже созданные snapshots. Новые заявки с выключенными уведомлениями получают `skipped_disabled`; без активных адресатов — `pending_no_recipients`. Ни один из этих случаев не создаёт Telegram job. Если уведомления выключили или токен исчез после enqueue, job фиксирует `skipped_disabled` / `skipped_missing_token`. Последующее включение настроек само по себе не запускает старые пропущенные события.
- Retry: максимум 8 HTTP попыток на доставку; 429 использует `parameters.retry_after`, 5xx и сетевые исключения повторяются с экспоненциальной задержкой и jitter (верхний предел 6 часов), прочие 4xx завершаются `failed`. Horizon остаётся с `tries=1`; повторы контролирует приложение. `php artisan enquiries:retry-failed-telegram [--event=<outbox_event_id>]` сбрасывает terminal failed deliveries, но не отправляет заново подтверждённые `sent` строки.
- Telegram-клиент обращается только к фиксированному HTTPS Bot API host. При активном proxy использует HTTP proxy URI Squid и Basic auth; автоматического direct fallback нет. Параметры и секреты заново читаются из БД при каждом job, тесты используют тот же клиент и Laravel HTTP fake. Ошибки хранят только безопасные коды и короткие статические пояснения. Сообщение содержит тип, публичный reference, имя, телефон, email и имеющиеся company/role/message/catalogue title; ограничено 3500 символами. Token и proxy credentials не входят в payload jobs или диагностические поля.
- Telegram Settings получил Test Connection (`getMe`), выбор активного recipient и Send Test Message; оба действия проверяют `is_admin`, ограничены общим лимитом 5 вызовов в минуту на пользователя и не создают заявку/outbox. Ошибки UI не раскрывают ответ API, токен или proxy URI.
- Для catalogue download после проверки published-каталога и существующего безопасного `local` PDF заявка и grant фиксируются в транзакции. Bearer token — 256 случайных бит, хранится только SHA-256, действует 15 минут. Он передаётся в JSON-ответе, но запрос скачивания передаёт его только как `Authorization: Bearer`; `X-Catalogue-Enquiry` привязывает запрос к публичному UUID заявки. Grant можно использовать повторно до срока истечения, чтобы пережить оборванную загрузку. Повторный POST с тем же idempotency key/payload выдаёт новый grant без новой заявки; предыдущие grants остаются действительны до собственного срока истечения, поэтому конкурентный replay не инвалидирует уже выданный token. Идемпотентный ключ, как и до BE-07.4, действует 24 часа.
- `GET /api/v1/catalogues/download` повторно проверяет hash, expiry, revoke, связь grant → enquiry → catalogue, статус published, безопасный relative path и наличие файла; отвечает потоковым PDF с `Content-Disposition: attachment`, `no-store/no-cache`, `nosniff`. Невалидный/чужой/недоступный grant — 404; просроченный — 410. PDF path не входит в DTO/ответ заявки. Endpoint ограничен 10 запросами в минуту на IP.

## API контракт для BE-07.5

Существующий `POST /api/v1/enquiries` сохраняет envelope и поля ответа. Для `catalogue_download` к `data` добавляется:

```json
{
  "downloadGrant": {
    "token": "<64 lowercase hex characters>",
    "expiresAt": "<ISO-8601 timestamp>",
    "downloadPath": "/api/v1/catalogues/download",
    "enquiryHeader": "X-Catalogue-Enquiry"
  }
}
```

Получив подтверждённый ответ, клиент выполняет `GET /api/v1/catalogues/download` с `Authorization: Bearer <token>` и `X-Catalogue-Enquiry: <data.enquiryId>`. Token нельзя помещать в URL. Повтор POST использует исходные `Idempotency-Key` и payload; успешный replay (HTTP 200) выдаёт новый grant token. Изменённый payload возвращает прежний `409 idempotency_conflict`. Заявка не создаётся и grant не выдаётся, если PDF отсутствует или каталог не опубликован. Подключение клиентских форм остаётся в BE-07.5.

## Проверки и ограничения

- Целевые тесты проверяют dispatch нескольких snapshots с положительным/отрицательным ID, устойчивость при enqueue failure, expired lease, отправку и отсутствие повторной отправки sent job, Telegram 429/403/503, административные HTTP fake действия, отсутствие фиктивных заявок, hash-only grant, idempotency rotation/conflict, streaming содержимое, повторную загрузку, expiry и исчезнувший файл.
- В автоматических тестах вызовы Telegram выполняются только через `Http::fake()` и включён `Http::preventStrayRequests()`. Реальные Telegram-запросы не выполнялись.
- MariaDB может гарантировать только локальную сериализацию, не exactly-once на стороне Telegram. Если Telegram принял запрос, но worker погиб до фиксации `sent`, после окончания lease возможен дубликат.
- Проверку фактической маршрутизации через Squid и browser-level Filament smoke нужно выполнить вручную после настройки доступного тестового proxy. Автоматические fake-тесты подтверждают общий клиентский путь и UI, но не доступность конкретного Squid из runtime-сети.
- Политика Privacy Policy остаётся обязательным условием перед включением публичных форм; BE-07.5 и frontend не менялись. Production migrations/deploy и реальные отправки не выполнялись.

## Ручная проверка после локальной приёмки

1. Применить миграции только в локальной/staging БД и добавить encrypted bot token, включённые notifications, Squid host/port и необязательные proxy credentials в Telegram Settings. До сохранения реального токена сначала проверить подключение на отдельном тестовом боте.
2. Добавить тестовый личный чат или группу, проверить Test Connection и Send Test Message. При проверке группы убедиться, что Bot имеет право писать; проверить и положительный ID, и `-100...` supergroup ID как строку.
3. Создать тестовую заявку только после согласования Privacy Policy. Проверить row в `enquiries`, event и per-recipient snapshots в `enquiry_outbox_events` / `enquiry_deliveries`; дождаться Horizon и убедиться, что успех фиксирует `sent` и Telegram message ID.
4. Для локальной диагностики dispatcher: `php artisan enquiries:dispatch-telegram`; очередь проверять через Horizon. Для ручного retry одной заявки: `php artisan enquiries:retry-failed-telegram --event=<ID>`, затем снова запустить dispatcher.
5. Запросить каталог, повторить POST с тем же ключом и payload и проверить, что выдаётся новый токен без второй заявки. Скачать файл с bearer и enquiry headers; повторить загрузку, затем проверить просроченный токен и отключение каталога.
6. Проверить сбой Squid в изолированной среде: доставка должна остаться retryable/failed согласно ответу транспорта, прямой fallback не должен выполняться. Не вводить production токены или адреса в автоматические тесты.
