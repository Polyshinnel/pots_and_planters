# BE-07.4 — Telegram Delivery, Horizon и Gated PDF

**Проект:** Pots & Planters 2.0  
**Статус:** техническое задание для Codex; реализация не подтверждена  
**Основание:** PROJECT_CONTEXT.md, ROADMAP.md, BE-07_ENQUIRIES_TELEGRAM_UPDATED.md и отчёты владельца о BE-07.1–07.3.

## 1. Цель и границы

Реализовать фактическую надёжную отправку уведомлений Telegram по сохранённым заявкам через Redis/Horizon, с опциональным HTTP proxy Squid и несколькими получателями, а также защищённую выдачу приватных PDF после успешной заявки `catalogue_download`.

**Не входит:** подключение frontend-форм (BE-07.5), реализация товарного каталога (BE-08), изменение публичного дизайна, production deploy/migration, автоматическое изменение Privacy Policy. Не менять утверждённые API/SEO/маршруты без обоснования.

## 3. BE-07.4a — надёжная доставка

- Сохранение заявки и outbox уже транзакционное: переиспользовать, не создавать второй механизм записи. Dispatcher периодически находит неотправленные/зависшие события в MariaDB, безопасно резервирует их и ставит работы в Redis; при недоступности Redis записи остаются для следующего запуска. Указать конкретную стратегию блокировки, lease, восстановления и идемпотентности.
- Для каждого recipient snapshot — отдельная delivery, не пересчитывать адресатов из текущего списка при повторной доставке; уникальность event + chat_id (или существующий эквивалент). Новые/отключённые получатели не должны задним числом менять события.
- Пер-адресная обработка: `pending/sending/sent/failed` либо эквивалент, попытки, timestamps, sanitized error и Telegram message_id. Исключить одновременное выполнение одной доставки, не отправлять повторно после подтверждённого `sent`.
- Настроить ограниченные попытки, exponential backoff с jitter (при необходимости), таймауты, Telegram 429 `retry_after`, обработку 5xx, сетевых сбоев и постоянных 4xx. Не делать бесконечных циклов, не менять глобально Horizon `tries=1` без необходимости. Документировать операционный способ повторной постановки окончательно failed доставок и ограничения Telegram exactly-once (после неизвестного исхода возможен дубль).
- Если notifications_enabled=false, token отсутствует или активных адресатов нет — заявка сохраняется, состояние явно диагностируется, фоновые задания не шлют сообщения. Уточнить в коде и документации семантику повторной отправки при последующем включении.
- Формат уведомления: тип и ID заявки, минимально необходимые контакты, достоверные snapshots. HTML/Markdown экранировать либо использовать безопасный plain text, ограничить размер; не раскрывать токены, proxy credentials, приватные пути и лишние PII.

## 4. BE-07.4b — Telegram HTTP client и Squid

- Использовать настройки из существующего `TelegramSettingsManager`, encrypted casts; Bot API endpoint фиксирован, только HTTPS. Настройки читать на момент отправки, учитывая долгоживущие Horizon workers.
- Proxy выключен: прямой запрос. Proxy включён: HTTP Squid host:port, необязательная Basic auth; **никакого автоматического direct fallback** при сбое прокси. Не передавать токены/пароли в query string, исключения и логи; проверить запрет SSRF и валидацию host/port.
- Реализовать админские действия **Test Connection** (`getMe`) и **Send Test Message** конкретному получателю на существующей странице Telegram Settings. Серверная авторизация `is_admin`, throttling, безопасные сообщения о результате; тест не создаёт заявку или outbox событие. При включённом proxy тесты обязаны использовать proxy.
- Отдельно проверить положительные и отрицательные signed BIGINT chat_id, включая `-100...`; не конвертировать в float или JS Number.

## 5. BE-07.4c — защищённый PDF grant

- Выдавать grant только после успешного сохранения `catalogue_download` с серверно подтверждённым опубликованным каталогом и существующим приватным PDF. Выбрать минимальную устойчивую модель (например, случайный криптостойкий bearer token, хранить только hash; TTL по умолчанию 15 минут), зафиксировать политику истечения, повторного использования и отмены.
- Grant привязан к enquiry и catalogue; токен нельзя угадать или применить к другому PDF. Не включать `pdf_path` и внутренний storage URL в публичные DTO. Запрос скачивания проходит через Laravel с повторной проверкой правомочности grant, срока, каталога и файла; отвечать корректными 404/410 или согласованными безопасными ошибками без утечек.
- Учитывать потерю ответа после сохранения заявки: повторный `POST` с тем же idempotency key и тем же payload возвращает тот же enquiry и **восстановимый доступ к PDF** без второй заявки. Повтор с другим payload — 409. Выбрать и задокументировать безопасный способ перевыпуска/возврата grant; не сохранять bearer token в открытом виде.
- Не блокировать PDF из-за сбоя Telegram/Redis. При ошибке записи заявки — не выдавать PDF. Избежать гонки между проверкой grant и скачиванием; при одноразовом grant явно решить сценарий оборванной загрузки. Для устойчивости допустим краткоживущий многократный grant с ограничениями и тестами.
- Использовать приватный диск и streaming download, корректные Content-Type/Content-Disposition и no-store/no-cache. Проверить защиту от path traversal и отсутствие публичных ссылок на PDF. Если выбран endpoint с токеном в URL, минимизировать риск утечки через access logs/referrer; предпочтительно передавать bearer token в заголовке и не логировать его.
- Frontend интеграция скачивания остаётся в BE-07.5; в этом этапе предоставить документированный API контракт, тесты и пример запроса без изменения публичного UI.

## 6. Безопасность и совместимость

- Laravel 13 / PHP 8.4 / MariaDB / Redis / Horizon / Filament 5. Новые зависимости только при доказанной необходимости.
- Сохранить `POST /api/v1/enquiries`, существующую идемпотентность, response envelope, server snapshots, Filament history и `/catalogues?category=<slug>`.
- Не хранить PII и секреты в логах/очередях сверх необходимого, ограничить доступ к технической диагностике; маскировать HTTP failures.
- Не отправлять реальные сообщения и не выполнять реальные запросы к Telegram во время автоматических тестов. Production-операции запрещены без отдельного разрешения.
- Известное ограничение: `product_enquiry` и `cart_enquiry` сейчас возвращают 404 до BE-08; не исправлять его подменой клиентских данных. Сбой CataloguesApiTest (`category[]=oops`) зарегистрировать и перепроверить, но не включать несвязанный рефакторинг.
- Privacy Policy `/private-policy` требует согласования до включения реальных форм в BE-07.5.

## 7. Тесты и критерии приёмки

**Доставка:** успешная отправка, несколько recipients, отрицательные chat_id, отключённый recipient, отсутствие recipients/token, выключенные notifications; независимость доставок; dispatcher повторно без дублей; Redis недоступен и восстановлен; конкурентные jobs; crash/expired lease; 429 retry_after, 5xx, timeout, permanent 4xx; `sent` не повторяется; настройки proxy меняются без stale worker config; proxy on/off и Basic auth; proxy failure без direct fallback; маскирование PII/secrets.

**Filament:** только admin запускает getMe/test send; throttling; тестовые запросы используют те же proxy settings; не создают enquiries; тесты HTTP fake.

**PDF:** заявка + grant, опубликованный/неопубликованный каталог, отсутствующий файл, поддельный/истёкший/чужой grant, повторная выдача, параллельные запросы, идемпотентный повтор после потери ответа, 409 на изменённый payload, streaming/no-cache и отсутствие утечки приватного пути; сбой Telegram/Redis не блокирует скачивание.

**Регрессия:** профильные API/Filament/каталожные тесты и полный Laravel suite на `potsandplanters_test` через Compose; Pint для затронутых PHP-файлов, `git diff --check`. Зафиксировать результаты и отдельно существующий дефект `CataloguesApiTest category[]=oops`, если воспроизводится. По возможности browser smoke Filament, иначе честно указать отсутствие.
