# BE-07.5 — Frontend integration and handoff

**Status: implemented and automatically verified; owner approval and final manual acceptance are pending.** This does not close BE-07.

## Changes

- Added a typed browser adapter for `POST /api/v1/enquiries`. It sends the existing contact/catalogue payloads, validates persisted response data and the catalogue grant shape, reads the backend `error.fields` validation envelope, and handles 409, 404, 422, 429, 5xx, malformed responses, and network failures without logging payloads or secrets.
- A valid submit creates one cryptographically random `Idempotency-Key`; retries with the same unchanged payload reuse that key while the form is mounted. A changed payload gets a new key. A catalogue replay after an expired grant uses the preserved key to ask the server for a fresh grant.
- Catalogue download starts only after the API confirms persistence. The browser fetches the fixed download path with `Authorization: Bearer` and `X-Catalogue-Enquiry`, requests `no-store`, checks the PDF content type, and downloads a Blob. The token stays in component memory and is never placed in a URL, link, HTML, local storage, or logs. Download retry and expiry states distinguish a saved enquiry from a failed download.
- Public contact and catalogue submissions are disabled by default behind `NEXT_PUBLIC_ENQUIRIES_ENABLED=false`. This gate is required because the public Privacy Policy still says form content is not transmitted. An English approval draft records confirmed data flows and marks owner decisions that remain unresolved; the public policy was not published or changed. Enable the build flag only after the policy is approved and published.
- Product and cart enquiries remain unavailable pending BE-08. Removed the development payload preview and local “details checked” state that could be mistaken for submission. The existing cart storage and routes remain intact; unavailable product/cart forms cannot submit.
- Corrected `CataloguesApiTest` to assert the API’s existing `error.code` / `error.fields` envelope for `category[]=oops` and invalid slug input. The endpoint already returned the expected 422; the test had been asserting Laravel’s default `errors` shape.
