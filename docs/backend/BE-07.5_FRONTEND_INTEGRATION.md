# BE-07.5 — Frontend Integration & Final Verification

**Проект:** Pots & Planters 2.0  
**Статус:** ТЗ к выполнению; реализация не начата  
**Предшествующие этапы:** BE-07.1 аудит; BE-07.2 API/outbox; BE-07.3 Filament; BE-07.4 Telegram/PDF — реализованы по отчётам Codex, полная ручная приёмка отложена.

## 1. Цель

Подключить существующие публичные формы `contact` и `catalogue_download` к реальному Laravel `POST /api/v1/enquiries`, обеспечить надёжное поведение при ошибках и защищённое скачивание PDF; выполнить сквозные проверки и подготовить итоговую ручную приёмку BE-07. Не активировать неподдерживаемые товарные сценарии.

## 2. Обязательная подготовка — read-only сверка

Перед изменениями прочитать `PROJECT_CONTEXT.md`, `ROADMAP.md`, `docs/backend/BE-07.2-implementation-notes.md`, `BE-07.3-implementation-notes.md`, `BE-07.4-implementation-notes.md` и фактические маршруты, DTO, формы, тесты. Проверить текущее рабочее дерево, включая незакоммиченные файлы. Не предполагать, что отчёт и код идентичны. Зафиксировать фактические поля, response envelope, коды ошибок, формат `downloadGrant`, требования к `X-Catalogue-Enquiry`, допустимые CORS/SSR способы скачивания. При расхождениях остановиться с вопросами, не подменять контракт догадками.

## 3. Ограничения

- Стек: Next.js 16, React 19, TypeScript, Mantine 9; Laravel 13, Filament 5, MariaDB, Redis/Horizon.
- Не менять публичный дизайн, существующие маршруты, SEO, Google Search Preview и работающие компоненты без необходимости.
- Никаких mock fallback, фиктивного успеха или скачивания до подтверждённой записи заявки.
- Не выполнять production-миграции, импорт, deploy и реальные Telegram-отправки.
- Локальная приёмка не зависит от Squid: proxy не удалять и не обходить при включении; его живую проверку перенести на staging после получения сетевого адреса.
- Не выводить PII, idempotency key, grant token, Bot Token, proxy password в логи, URL, аналитику, исключения или клиентскую телеметрию.

## 4. Этап BE-07.5a — API-адаптер и контракты

**Цель:** централизованная типизированная отправка форм.

**Изменения:**
1. Использовать существующие `frontend/src/components/forms/` и `frontend/src/lib/forms/`, общие компоненты и существующий механизм API. Добавить минимальный типизированный адаптер для `POST /api/v1/enquiries` с проверкой response shape.
2. Учитывать фактический backend-контракт (не придумывать поля). Для `contact` передавать имя, телефон, email, необязательную компанию, обязательное сообщение и разрешённый источник страницы. Для `catalogue_download` — контактные поля, UUID каталога, роль и дополнительную роль при `other`.
3. Генерировать один криптографически стойкий idempotency key на логическую попытку отправки; сохранять его для повторов при неопределённом результате, не генерировать новый при простом retry. Новый ключ — только для новой заявки или после явно завершённого сценария. Уточнить по backend-коду заголовок/формат ключа.
4. Обрабатывать 422 с полевыми ошибками; 409 с явным конфликтом; 404 для недоступного каталога; 429 с понятным ограничением частоты; 5xx/503 и сетевые ошибки с возможностью повторить. Не очищать введённые поля при ошибке.
5. Не выдавать клиенту успех, пока сервер не подтвердил сохранение. Предотвращать двойной submit; не скрывать ошибку API.

**Приёмка:** typecheck, тесты маппинга полей, idempotency, 2xx/409/422/404/429/503/network и проверки отсутствия mock fallback.

## 5. Этап BE-07.5b — Contact и Catalogue Download UI

**Цель:** подключить существующие формы без визуального редизайна.

**Изменения:**
1. `contact`: существующая клиентская валидация, реальный submit, success только после ответа API, понятный retry и сохранение данных при ошибках.
2. `catalogue_download`: серверное сохранение заявки до доступа к файлу. Использовать `data.downloadGrant` и ID заявки в подтверждённом ответе, строго по реальному DTO.
3. Выполнять `GET /api/v1/catalogues/download` с `Authorization: Bearer <token>` и `X-Catalogue-Enquiry: <enquiryId>`. Не помещать token в query string, pathname, HTML-ссылку или localStorage. Выбрать безопасный браузерный способ загрузки (fetch/blob либо минимальный server proxy) по фактической сетевой архитектуре, избегая логирования токена и непреднамеренного кэширования.
4. Обрабатывать отсутствие grant, отказ доступа, истечение срока, отсутствие файла и сетевой обрыв; различать «заявка сохранена, но скачивание не удалось» и «заявка не сохранена». При повторном POST с тем же ключом/payload получать новый grant без дублирования заявки. Не создавать бесконечные автоматические повторы.
5. Сохранять фильтр `/catalogues?category=<slug>`, модальные окна, фокус/доступность, существующие CTA, SEO и SSR.

**Приёмка:** успешная отправка, восстановление после обрыва, повторное скачивание, ошибки grant и отсутствие приватных путей/токенов в URL и логах; существующие regression tests.

## 6. Этап BE-07.5c — Товарные сценарии и корзина

**Цель:** не вводить пользователя в заблуждение до BE-08.

**Изменения:**
1. `product_enquiry` и `cart_enquiry` сейчас получают 404 на backend без авторитетной модели товаров. Не активировать отправку и не показывать фиктивный success. Сохранить существующие маршруты и UI, использовать честное состояние недоступности, не менять дизайн без согласования.
2. Не считать клиентские SKU, цены, названия, характеристики и наличие достоверными. Не внедрять временный серверный каталог.
3. Корзина остаётся в `localStorage`; при любой ошибке или недоступности отправки позиции не удаляются и не очищаются молча.
4. Задокументировать зависимость товарных сценариев от BE-08 и требование отдельного решения перед их включением.

**Приёмка:** отсутствие ложного успеха; неизменность корзины и сохранение существующих пользовательских маршрутов.

## 7. Этап BE-07.5d — Privacy Policy и регрессионный дефект

**Цель:** устранить противоречия перед приёмом реальных PII.

**Изменения:**
1. Найти действующую страницу `/private-policy` и её источник контента. Подготовить точечное обновление публичного текста **на английском**: фактические типы собираемых данных, цель обработки заявок, Telegram-уведомления, доступ к данным, сроки хранения и контакт по вопросам данных — только на основании подтверждённой политики проекта. Не придумывать сроки, юридические основания или обещания. Если обязательные положения не согласованы — представить текст на утверждение и не включать реальные формы до согласования.
2. Сохранить маршрут `/private-policy` и существующее cookie-поведение.
3. Воспроизвести дефект `CataloguesApiTest::test_empty_results_and_invalid_category_parameters_have_predictable_responses` (`category[]=oops`). Найти минимальную причину, исправить валидацию без изменения легального контракта `/api/v1/catalogues`; добавить/уточнить regression test. Не делать посторонний рефакторинг.

**Приёмка:** согласованный Privacy Policy опубликован до live submit; тест `category[]=oops` и полный backend suite проходят либо причины любого оставшегося сбоя явно зафиксированы.
