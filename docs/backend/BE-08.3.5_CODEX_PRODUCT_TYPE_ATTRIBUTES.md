## 1. Цель и результат

Связать уже реализованные справочники **Product Types** и **Attributes** через конфигурацию набора характеристик типа товара:

- один Attribute может быть назначен многим Product Types;
- один Product Type содержит несколько Attributes;
- для каждого назначения отдельно настраиваются **required**, **filterable**, **sort_order**;
- конфигурация управляется администратором **внутри редактирования Product Type** в Filament;
- без создания Product и без сохранения значений характеристик товаров.

Это подготовка схемы для BE-08.4.3 и фильтров; `required` и `filterable` пока **метаданные назначения**, не поведение публичного каталога.

## 2. Границы и инварианты

- Сохранять утверждённый стек: Laravel 13, PHP 8.4, Filament 5, MariaDB 11.8 (по Compose); не менять публичный Next.js, SEO, маршруты, дизайн и API.
- Использовать существующие модели `ProductType`, `Attribute`, существующую проверку `is_admin` и принятый UX BE-08 справочников.
- Не создавать `products`, product values/selections, category filter config, public API, DTO, SSR, импорт OpenCart, Product Resource, Product Enquiry или Cart Enquiry.
- Не добавлять `AttributeOption` в pivot: options остаются дочерними элементами Attribute и не назначаются типу отдельно.
- Не изменять тип Attribute, его options, правила code, имена таблиц и существующие миграции.
- Не удалять и не пересоздавать существующие справочники/данные; миграция только **добавляет** таблицу связей.
- Физическое удаление ProductType/Attribute в Filament остаётся запрещённым. Удаление **назначения** (detach) допустимо только как явное действие администратора и не удаляет сам Attribute.
- Ни production, ни staging не трогать. Миграции запускать только в явно подтверждённой изолированной dev/test БД.

## 3. Этап A — схема и Eloquent

Добавить **одну** миграцию `product_type_attribute` (сверить имя и порядок миграций с актуальным репозиторием):

| Поле | Требование |
| --- | --- |
| `product_type_id` | BIGINT FK → `product_types.id`, NOT NULL |
| `attribute_id` | BIGINT FK → `attributes.id`, NOT NULL |
| `is_required` | boolean NOT NULL, default `false` |
| `is_filterable` | boolean NOT NULL, default `false` |
| `sort_order` | integer NOT NULL, default `0` |
| timestamps | если соответствуют существующим Laravel/Filament паттернам; выбрать единообразно |

Ограничения:

- DB `UNIQUE(product_type_id, attribute_id)` или составной PK, чтобы исключить дубли назначения, включая конкурентные запросы.
- Индексы для обратной связи и выборки по `product_type_id`/`sort_order`; не создавать избыточные дублирующие индексы.
- FK с безопасной политикой удаления: **RESTRICT/NO ACTION**, без каскадного уничтожения назначений при удалении ProductType/Attribute; сверить фактические соглашения MariaDB/Laravel.
- Значения `is_required`, `is_filterable` — настоящие boolean; `sort_order` — целое с предсказуемой сортировкой (`sort_order`, затем стабильный tie-breaker по ID/имени).
- Уникальность и FK защищать на уровне БД, а не только формой.

Добавить `belongsToMany` в `ProductType` и обратную связь в `Attribute`, с `withPivot(...)` и `withTimestamps()` только если timestamps есть в pivot. Использовать уже существующие модели; отдельную Pivot-модель создавать только при конкретной технической необходимости, обосновать в отчёте.

**Семантика флагов:**

- `is_required`: в будущей Product-форме значение Attribute будет обязательным для данного типа, но пока никакой Product validation не реализовывать.
- `is_filterable`: кандидат для будущих фильтров; **не означает**, что фильтр автоматически появится в каждой категории. Конфигурация фильтров категорий — отдельный BE-08.4.6.
- `sort_order`: порядок характеристик внутри одного типа, независимый от порядка AttributeOptions и от других типов.
- Назначение не изменяет глобальный `Attribute.is_active`. Архивный Attribute, уже привязанный к типу, должен оставаться видимым администратору для безопасного редактирования/отвязки.

## 4. Этап B — Filament 5

В существующем `ProductTypeResource` добавить **Relation Manager или эквивалентный компактный редактор** для назначенных Attributes. Предпочесть штатные возможности Filament 5, не строить отдельный UI framework.

Требования:

1. На Edit Product Type показывать назначенные Attributes с именем, `code`, `type`, `unit` (где применимо), active, `is_required`, `is_filterable`, `sort_order`.
2. Добавлять Attribute из **активных и ещё не назначенных**. Поиск по имени/code, исключение дубликатов. Не менять существующий Attribute при назначении.
3. Редактировать `is_required`, `is_filterable`, `sort_order` **только для конкретной связи**. Два типа могут иметь разные флаги и порядок для одного Attribute.
4. Позволить явно отвязать Attribute с подтверждением, не удаляя Attribute/Options. Никакого скрытого detach при сохранении формы.
5. Неактивные, ранее назначенные Attributes отображаются и могут быть отредактированы или отвязаны. Прикрепление новых архивных Attributes по умолчанию запрещено; если требуется иное — не расширять без согласования.
6. Предсказуемая сортировка, понятные ошибки при попытке дубля, FK/validation errors и отсутствии прав. При конкурентном назначении DB UNIQUE violation должен обрабатываться корректно.
7. Доступ только администраторам согласно существующей политике `is_admin`; не вводить новый permission framework.
8. Не менять Create/Edit/List интерфейсы Product Types сверх необходимой интеграции relation manager. Если менеджер доступен только после создания типа — это нормально; не усложнять форму создания.
9. Для неактивного Product Type уже назначенные Attributes должны оставаться управляемыми администратором, без автоматического удаления связей.

## 5. Этап C — валидация и безопасность данных

- Серверная проверка существования ProductType и Attribute, допустимости прикрепления только активного Attribute, корректности boolean и целого `sort_order`.
- Защита от повторного attach, от несанкционированных изменений pivot и от удаления справочников через UI.
- Нельзя допустить массовое обновление pivot-полей вне разрешённых колонок или модификацию другого ProductType через подмену ID.
- Проверить, что `is_required=true` совместимо с любым из пяти типов Attribute; не добавлять продуктовые значения или специальные исключения для boolean/multiselect на этом этапе.
- Не вводить новые правила совместимости типа Attribute и ProductType без утверждённых требований.
- Не добавлять стартовые записи, фиктивные Material/Color/Finish/Dimensions или автоматические назначения.

## 6. Этап D — автоматические проверки

Минимальные сценарии (согласовать тестовый стиль с имеющимися `ProductTypeAdminTest` и `AttributeAdminTest`):

1. Pivot создаётся; один ProductType получает несколько Attributes, один Attribute назначается нескольким типам.
2. `UNIQUE(product_type_id, attribute_id)` запрещает дубль на уровне БД.
3. FK/RESTRICT защищают ссылки; detach не удаляет сам Attribute/Options.
4. Значения флагов по умолчанию false, порядок 0; корректно сохраняются true/false и нестандартный порядок.
5. Изменение флагов/порядка в одном ProductType не влияет на назначение того же Attribute в другом.
6. Отображение назначений в Filament, добавление, редактирование и явное удаление связи.
7. Поиск и исключение уже назначенных/неактивных Attributes при новом attach; ранее назначенные архивные доступны для просмотра и управления.
8. Неактивный ProductType не теряет связи.
9. Доступ admin/non-admin, запрет операций без прав; нельзя изменить чужую связь через подмену ID.
10. Стабильный порядок и корректная обработка повторного назначения/конкурентного конфликта.
11. Регрессия BE-08.3.1–BE-08.3.4 и **полный backend suite**.

Команды запускать в Docker Compose с явной тестовой БД `potsandplanters_test` (проверить фактические настройки перед миграцией). Запустить Pint `--test` **только для затронутых файлов**, `git diff --check`. Полный Pint, если запускается, не должен приводить к правкам постороннего кода.
