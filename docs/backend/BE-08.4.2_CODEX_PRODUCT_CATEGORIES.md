# BE-08.4.2 — Product Categories & Primary Category

**Проект:** Pots & Planters 2.0  
**Статус:** техническое задание для Codex; не считать выполненным до отчёта и ручной приёмки.  
**Язык ТЗ:** русский. Публичный интерфейс сайта — английский.

## 1. Цель

Связать существующий `Product` с несколькими существующими `Category` и позволить выбрать **ровно одну Primary Category среди назначенных категорий**. Подготовить данные для будущего canonical `/shop/{primary-category-slug}/{product-slug}` без реализации маршрутов, SEO и API в данном этапе.

## 3. Объём изменений

### 3.1. Схема БД

- Создать pivot `product_category` с FK на существующие `products` и `categories`, `UNIQUE(product_id, category_id)` (или эквивалентным составным PK), индексами и корректным поведением FK. Не удалять категории или товары через Filament.
- Добавить nullable `products.primary_category_id`, поскольку в Product Core пока допустимы черновики без категорий. В будущем **публикация требует** назначенной Primary Category; не вводить скрытую автоматическую публикацию.
- Обеспечить на уровне MariaDB инвариант: ненулевой `primary_category_id` обязательно соответствует существующей строке `(product_id, category_id)` в `product_category`. Предпочтительно составной FK, если он поддерживается реальной схемой и порядком миграций; предусмотреть корректные индексы и порядок создания ограничений. Не допускать решения только на уровне Filament.
- Разобраться с удалением строки pivot, которая сейчас является Primary Category: безопасный явный сценарий смены/очистки Primary Category до detach; без отключения FK и без тихого несогласованного состояния. Не удалять назначение при ошибке валидации.
- При проектировании учитывать циклическую зависимость `products → product_category → products`: миграции и откат должны работать на чистой тестовой БД. Не вводить каскады, которые скрыто очищают важные данные.

### 3.2. Laravel

- Добавить связи `Product::categories()`, `Product::primaryCategory()` и необходимую обратную связь `Category::products()` без изменения существующего поведения Category API.
- Валидация: категории не дублируются, Primary Category принадлежит выбранным категориям; нельзя сохранять несуществующие ID; при смене набора категорий primary явно переназначается или очищается только для допустимого состояния.
- Изменения списка категорий и primary должны сохраняться **атомарно**. Выбрать простой транзакционный сервис/действие или использовать существующий паттерн приложения. Проверять ошибки БД и корректно возвращать их в интерфейс.
- Для `published` Product закрепить правило наличия хотя бы одной категории и выбранной Primary Category при переходе в статус `published` и при дальнейшем редактировании. Сохранить возможность черновиков без категорий. Если в текущем Product Core уже есть опубликованные записи без категорий, не менять их автоматически; зафиксировать конфликт и согласовать безопасное поведение.
- Не менять глобальные scopes Category, маршруты или существующие API. Учитывать действующую модель активности/публикации Category: неактивные/архивные назначения не должны исчезать из формы редактирования и не должны молча переназначаться.

### 3.3. Filament 5

- В существующем Product Resource добавить удобный множественный выбор категорий и **отдельный Primary Category**, доступный только из выбранных категорий.
- При смене списка категорий обновлять варианты Primary Category без потери данных; если прежняя primary исключена, требовать явный новый выбор (или явную очистку для draft), не выбирать первую категорию без ведома администратора.
- При редактировании показывать уже назначенные категории, в том числе ставшие неактивными, с понятной маркировкой; для новых назначений соблюдать текущую политику доступности категорий.
- Обеспечить одинаковое поведение Create и Edit, включая обработку ошибки валидации без частичного сохранения. Не менять внешний вид публичного сайта.
- Переиспользовать существующие подходы Filament; не создавать новый абстрактный UI-фреймворк.

- Не затрагивать чужие незакоммиченные файлы; без нецелевого рефакторинга.

## 5. Тесты и приёмка

Покрыть тестами как минимум:

1. Product в `draft` без категорий сохраняется.
2. Product с несколькими категориями и Primary Category сохраняется и корректно перечитывается.
3. Дубли pivot невозможны на уровне БД.
4. Primary Category вне назначенного набора отклоняется приложением **и БД**.
5. Попытка удалить primary pivot без безопасной смены/очистки отклоняется.
6. Смена primary и удаление вторичной категории сохраняют целостность.
7. `published` без Primary Category не допускается при сохранении через приложение/Filament; проверить фактическую политику Product Core и не менять статус существующих товаров молча.
8. Неактивные категории, ранее назначенные Product, корректно отображаются при редактировании; запрещённые новые назначения не проходят.
9. Неадминистратор не получает доступ к управлению.
10. Миграция и rollback/re-migrate проходят в тестовой БД без нарушения FK.

Запустить профильные тесты Product/Category, полный Laravel backend suite, Pint `--test` для затронутых PHP-файлов, `git diff --check`. Если общий Pint содержит старые нарушения, не исправлять посторонние файлы; указать отдельно.
