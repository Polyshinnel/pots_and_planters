# BE-08.4.3-FIX — Проверка и исправление отката миграций Product Attribute Values

**Тип:** точечная диагностика и исправление. **Статус:** задание для Codex, не выполнено.

## Контекст

BE-08.4.3 реализован: typed scalar values (`text`, `number` DECIMAL(20,6), `boolean`) и отдельные selections для `select`/`multiselect`, Filament-редактор, транзакционное сохранение и Required при публикации. Владелец проверил отображение характеристик в Filament. По отчёту Codex: 127 passed / 933 assertions, Pint и `git diff --check` PASS. Однако один rollback завершился ошибкой после изменения `up()`/`down()` миграции; последующее пересоздание тестовой схемы не подтверждает корректный rollback. Нужно выяснить причину и проверить исправление, не изменяя бизнес-логику.

## Цель

Обеспечить, чтобы **актуальные** миграции BE-08.4.3 корректно выполнялись и откатывались на **изолированной тестовой БД**, включая зависимости между таблицами, индексами и FK. Подтвердить это воспроизводимыми командами и результатами тестов.

3. Найти точный текст исходной ошибки rollback в отчёте/логах, если доступен. Если недоступен — не придумывать причину, воспроизвести в безопасной тестовой среде.
4. Зафиксировать различие между проблемой старой версии миграции, уже применённой ранее, и проблемой текущего файла. Проверить, не изменялась ли применённая миграция задним числом.

## Безопасность данных и окружения

- **Никаких действий в production, staging или обычной dev-БД.** Никаких реальных внешних запросов.
- Использовать Docker Compose `compose.yaml` + `compose.dev.yaml`, backend с **явным** `DB_DATABASE=potsandplanters_test` и проверкой фактического имени БД непосредственно перед каждой миграционной/rollback-командой.
- `migrate:rollback`, `migrate:fresh`, `RefreshDatabase` и любые операции удаления данных допустимы **только** после подтверждения, что подключение указывает на выделенную, одноразовую тестовую БД. Если есть сомнения, тестовая БД содержит ценные данные или нельзя подтвердить изоляцию — **остановиться и запросить разрешение**, не выполнять разрушительные команды.
- Не использовать `--force` как способ обойти проверку окружения; при необходимости объяснить его назначение.
- Не менять уже применённые production-миграции или исторические миграции без документированного обоснования. Если проблема касается несовместимости ранее применённой версии, отдельно предложить безопасную стратегию, но не выполнять production-операций.
- Сохранить все существующие незакоммиченные изменения BE-08, FIX-01 и ручные правки. Не делать commit без запроса.

## Порядок выполнения

### Шаг 1 — Диагностика

- Выписать конкретные миграции BE-08.4.3, их зависимости и фактический порядок rollback.
- Сверить ожидаемую схему после `up()` и после `down()`; проверить, что `down()` удаляет только объекты, созданные соответствующим `up()`, в корректном порядке.
- Воспроизвести проблему на изолированной тестовой БД либо документально подтвердить, что она относилась к промежуточной версии миграции.

### Шаг 2 — Минимальное исправление, только если нужно

- Изменить только миграцию/миграционный тест, если доказан дефект в текущей версии.
- Не менять Product, Filament, API, публичные маршруты, бизнес-валидацию или структуру характеристик ради обхода ошибки.
- Не удалять и не ослаблять существующие тесты. При необходимости добавить небольшой тест миграционного контракта, совместимый с текущей тестовой инфраструктурой.
- Если актуальный rollback уже работает, **не вносить искусственных изменений**; зафиксировать подтверждение в отчёте.

### Шаг 3 — Верификация

- В выделенной тестовой БД проверить цикл **up → rollback → up** именно для миграций BE-08.4.3, учитывая порядок зависимостей и не затрагивая другие БД.
- После повторного применения подтвердить `migrate:status` и фактическое наличие ожидаемых таблиц, FK и индексов.
- Запустить профильные тесты BE-08.4.3 и связанные регрессии BE-08.3/BE-08.4, затем полный backend suite.
- Запустить `pint --test` для затронутых PHP-файлов и `git diff --check`.
- Если ошибка остаётся, указать воспроизводимые шаги и остановиться без перехода к следующему этапу.

## Критерии приёмки

1. Причина первоначального rollback failure установлена или честно обозначена как неподтверждённая при успешно проверенной текущей версии.
2. Цикл up → rollback → up **актуальных** миграций BE-08.4.3 успешно выполнен в изолированной тестовой БД; проверены таблицы и ограничения.
3. Профильные тесты и полный backend suite проходят; Pint и `git diff --check` проходят для изменённых файлов.
4. Нет побочных изменений Product/Filament/API/Next.js и потерь данных вне одноразовой тестовой БД.
5. Предоставлен отчёт: первопричина, точные изменённые файлы (или «изменений нет»), команды, подтверждённая БД, результаты, остаточные риски.
