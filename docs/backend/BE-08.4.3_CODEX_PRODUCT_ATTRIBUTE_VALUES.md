# BE-08.4.3 — Product Attribute Values

**Статус:** техническое задание для Codex; реализация не начата.
**Язык задания:** русский. **Публичный интерфейс сайта:** английский.

## 1. Цель

Реализовать хранение и редактирование значений характеристик конкретного Product на основе уже существующих Product Type ↔ Attributes и Attribute Options. Поддержать `text`, `number`, `boolean`, `select`, `multiselect` без создания отдельных колонок в `products` для каждой характеристики. Обеспечить транзакционность, строгую валидацию, сохранность данных и тесты. **Не переходить к BE-08.4.4.**

## 3. Архитектура данных

Реализовать согласованный D3: типизированные scalar values и отдельные selections для option-значений. Сопоставить названия/ключи с существующим кодом и использовать минимально необходимую схему:

- `product_attribute_values`: FK на Product и Attribute; уникальность пары `(product_id, attribute_id)`; типизированные nullable-поля для текста, точного числового значения и boolean; timestamps по действующим соглашениям. Число хранить в `DECIMAL` с обоснованной точностью, без float и потери единиц; единица измерения берётся из определения Attribute. Для select/multiselect scalar-поля должны оставаться пустыми.
- `product_attribute_selections`: FK на запись значения и AttributeOption; запрет дублей выбранной option. На уровне БД или в атомарном сервисе обеспечить, что option относится к тому же Attribute, а не к другому справочнику. Описать, какие инварианты гарантирует MariaDB, а какие — доменная валидация; не заявлять фиктивную DB-защиту.
- Для scalar типов ровно одно соответствующее значение, для `boolean` отличать `false` от отсутствующего значения. Для `select` допускается ровно одна option, для `multiselect` — набор уникальных options. Пустые необязательные значения не должны создавать ложные заполненные записи.
- Внешние ключи, уникальные индексы и правила удаления должны исключать сиротские selections. Не вводить каскадного уничтожения существующих бизнес-данных без обоснования. Не менять существующие таблицы справочников без необходимости.
- **Обязательность** берётся из назначения Attribute к Product Type, а не из глобального Attribute. Допустимость заполнения — только для характеристик, назначенных текущему типу товара.

Не расширять этот этап на отдельные таблицы размеров, категорийные фильтры или массовый импорт. Не создавать ненужные универсальные фреймворки.

## 4. Доменное поведение и защита данных

1. Реализовать отдельный узкий сервис/manager для сохранения набора значений Product: validate → transaction → persist. Сохранять значения атомарно; ошибка в любом поле не должна оставлять частично обновлённый Product/набор характеристик.
2. Валидировать тип, принадлежность Attribute к Product Type, `required`, допустимость options, дубли, числа и диапазоны согласно реальным ограничениям; не придумывать бизнес-диапазоны для размеров. Неактивные определения/опции: существующие значения сохранять и отображать; новые назначения неактивных значений не разрешать. Уточнить существующую семантику `is_active` до реализации.
3. Смена Product Type с уже заполненными значениями — **не удалять и не обнулять их молча**. Предусмотреть явное предупреждение/подтверждение и безопасную стратегию, совместимую с имеющейся формой; если нельзя надёжно реализовать без расширения scope, блокировать такую смену понятной ошибкой и описать последующий отдельный шаг. Не создавать скрытые несовместимые значения.
4. Смена типа Attribute с заполненными Product values не должна приводить к потере данных; предусмотреть защиту с учётом уже существующих правил BE-08.3.4. Снятие назначения Attribute с Product Type при существующих значениях также не должно незаметно уничтожать данные. При необходимости добавить узкую проверку/запрет и тест.
5. Для `published` товара обеспечить проверку обязательных характеристик при сохранении/публикации, **не ломая** существующие правила Primary Category из BE-08.4.2. Для draft допустимы незаполненные required, чтобы товар можно было подготовить постепенно; на переход в `published` обязательные значения проверяются. Если текущий Product Core имеет другой lifecycle, описать и согласовать минимальное совместимое решение.
6. Не менять автоматически SKU, цену, Brand, Supplier, Series, категории или SEO.

## 5. Filament 5

- В существующей форме Product показать секцию характеристик, динамически зависящую от выбранного Product Type, используя уже настроенные назначения, `sort_order`, `required`, `is_active`.
- Типы полей: `text` → текстовое; `number` → числовое с отображением `unit`; `boolean` → корректное nullable/true/false поведение; `select` → одиночный выбор; `multiselect` → множественный выбор.
- Неактивные или ранее выбранные варианты должны быть видны администратору с понятной пометкой, без автоматической замены; не разрешать незаметное присвоение новых неактивных опций.
- Избежать N+1 при загрузке назначений/options. Не вводить публичные изменения дизайна и не перестраивать ProductResource целиком.
- Корректно сохранять и повторно загружать значения после Create/Edit, в том числе `false`, `0` (для числовых атрибутов, если разрешено), пустые optional и multiselect.

## 6. Обязательные тесты

Добавить профильные Laravel feature/unit tests с реальной MariaDB test-схемой, включая:

- Все пять типов и round-trip сохранение/чтение; `false` vs отсутствует, числовой `0`, decimal precision, select и multiselect.
- Уникальность scalar row и option selections; запрет option чужого Attribute, не назначенного Product Type Attribute, некорректных значений.
- Required на published и допустимость неполного draft; совместимость с Primary Category.
- Транзакционный rollback при ошибке в одном из нескольких полей; отсутствие частичных записей.
- Смена Product Type при заполненных значениях, снятие назначения Attribute, изменение типа заполненного Attribute — данные не теряются.
- Неактивные Attribute/Option: сохранение старых значений, запрет новых невалидных назначений.
- Админский доступ Filament, сохранение/повторное открытие формы и запрет неавторизованного редактирования.
- Регрессия BE-08.3.x и BE-08.4.1/4.2.

Запустить профильные тесты, **полный backend suite**, Pint `--test` для затронутых PHP-файлов, `git diff --check`. Не править чужие style issues ради зелёного общего Pint. Проверить миграции только в test БД (при необходимости rollback/reapply только новой миграции и только там).

## 8. Критерии приёмки

1. Администратор видит только характеристики назначенного Product Type и может сохранить/открыть значения всех пяти типов.
2. Существующие значения не теряются молча при изменении Type, Attribute/Option или назначений.
3. Сохранение атомарно; required проверяется при публикации, но не блокирует черновики.
4. БД и сервер валидируют связи и дубли; тесты покрывают важные инварианты.
5. Профильные и полный backend suite зелёные, Pint затронутых файлов и `git diff --check` зелёные.
6. Ручная проверка Filament владельцем — отдельное условие окончательной приёмки.
