# BE-08.4.4.1 — Async Media Optimization & WebP Variants (пересмотренное ТЗ)

## Цель
После загрузки JPEG/PNG/WebP в Filament (до 10 MiB) быстро сохранять исходный файл и MediaAsset, а конвертацию и генерацию вариантов WebP выполнять асинхронно через существующие Redis + Laravel Horizon. Сохранить существующую галерею при создании и редактировании Product и повторное использование MediaAsset между товарами.

3. Зафиксировать обнаруженные расхождения; не предполагать, что отчёт равен текущему состоянию репозитория. Проверить установленную библиотеку и доступный штатный image driver для Intervention Image v3; если поддержки WebP нет — остановиться и сообщить, не вводить скрытый fallback.

## Обязательная готовая библиотека обработки изображений
- Использовать **Intervention Image v3** (`intervention/image`, стабильная версия 3.x, совместимая с фактической версией PHP); не реализовывать собственные JPEG/PNG/WebP декодеры, ресайзеры или WebP encoder. Laravel integration package не обязателен: использовать библиотеку напрямую в сервисе обработки.
- На read-only аудите проверить `composer.json`, `composer.lock`, уже установленные пакеты и версии PHP; если проект уже содержит подходящую библиотеку, согласовать переиспользование вместо дублирующей зависимости. Установить через Composer только после проверки совместимости, сохранить lockfile. Не делать необоснованный `composer update` всего проекта.
- Проверить GD/Imagick и поддержку WebP в **том же PHP-окружении**, где работает Horizon worker. Выбрать один явно настроенный драйвер; если требуемых возможностей нет, остановиться с диагностикой, без самописной замены и скрытого fallback.
- Использовать API Intervention Image v3 для чтения, ориентации, масштабирования, работы с прозрачностью и WebP encoding. В случае необходимости квадратного холста применять штатные операции библиотеки; не писать собственную обработку пикселей. Учесть различия поведения GD и Imagick и протестировать реальный выбранный драйвер.
- Логику именования, статусов, идемпотентности, файловой публикации и очереди реализовать на уровне приложения: библиотека отвечает только за трансформацию изображений.

## Архитектурное поведение
- HTTP-запрос синхронно валидирует тип/размер, сохраняет оригинал под сгенерированным путём и фиксирует MediaAsset; конвертация не выполняется в HTTP-request. Оригинал хранится в непубличном хранилище, доступном worker, если это совместимо с текущей disk-конфигурацией; пути никогда не выдавать публичному API. Не переносить файлы без плана совместимости.
- Состояния MediaAsset: `pending`, `processing`, `ready`, `failed` с достаточной диагностикой (ошибка без раскрытия приватных путей), временем обработки и возможностью повторной постановки. Проверить, требуется ли отдельная таблица вариантов или стабильные поля/paths; выбрать минимальное решение, обосновать.
- После commit записи MediaAsset ставить job `ProcessMediaAsset` в Redis-очередь, обслуживаемую Horizon; убедиться в реально существующем worker/queue config. Не запускать job до commit. При сбое enqueue MediaAsset остаётся в `pending`, предусмотрен безопасный способ повторной постановки/восстановления, без ложного `ready`.
- Job генерирует ровно три WebP-варианта: `full` 1000×1000, `card` 250×250, `thumb` 100×100. Сохранять пропорции, без crop/искажений, с прозрачными полями для квадратного canvas, без ненужного upscale; документировать точную политику для маленьких исходников и фактические размеры файлов. Корректно учитывать EXIF orientation и alpha; ограничить ресурсы декодирования и проверять фактический тип изображения, а не только MIME клиента.
- Качество WebP конфигурируемое, стартовое значение 82–85. Имена файлов/вариантов стабильны и безопасны; метаданные оригинала не публиковать.
- Обработка идемпотентная и конкурентно-безопасная: повторные jobs и retries не создают дублей, не повреждают ready-набор, не публикуют частично созданные варианты. Использовать временные файлы/атомарную публикацию набора насколько поддерживает выбранный disk; при ошибке очистить только временные артефакты. Защитить от гонки удаления/повторной постановки, корректно настроить retries/backoff/timeout, не допускать бесконечных попыток.
- В Filament показать статус обработки и ошибку, предоставить admin-only Retry для `failed`/застрявших `pending`, с защитой от двойной постановки. После загрузки не блокировать создание/редактирование Product до готовности вариантов. Сохранить ручные доработки галереи на Create и Edit, ALT, порядок, main image и повторное использование Asset.
- Публичные URL не должны указывать на несуществующие варианты. Публичный Product API/Next.js в рамках этого этапа не реализовывать. Не вводить fallback на mock или незаметное использование оригинала вместо отсутствующего варианта.
- Удаление ProductImage только отвязывает Asset. Файлы, используемые несколькими товарами, не удаляются. Никаких автоматических массовых удалений/переконвертаций без отдельного согласования.
- Существующие MediaAsset и старые записи должны остаться валидными. Предложить безопасную явную стратегию backfill/regeneration, но не запускать массовую обработку автоматически; учесть уже загруженные изображения и отсутствие оригиналов.

Не менять существующий image processing stack без обоснования. Не затрагивать production/staging или обычную dev-схему. Беречь все незакоммиченные изменения.

## Этапы реализации
1. Read-only аудит и короткое решение по disk, драйверу, статусам, job/queue, восстановлению после enqueue failure и существующим MediaAsset.
2. Минимальная миграция/модель статусов и вариантов, сервис генерации на Intervention Image v3, job с идемпотентностью и безопасной публикацией.
3. Интеграция загрузчика и Filament UI (включая Create/Edit), статус, Retry.
4. Тесты и отчёт. Все миграции только после явной проверки `DB_DATABASE=potsandplanters_test` в изолированном Compose; проверить up → rollback → up только в тестовой схеме, без уничтожения данных dev.

## Проверки и критерии приёмки
- JPEG/PNG/WebP загружается; ответ не ждёт конвертации, MediaAsset получает pending, job попадает в правильную Redis/Horizon queue после commit.
- Worker создаёт все три WebP-варианта и переводит статус в ready только после проверки целостности набора.
- Прозрачность, EXIF, разные пропорции, маленькие файлы, `false`/ошибки чтения, лимит 10 MiB, повреждённый файл и resource limits протестированы.
- Ошибка обработки даёт failed и видимый Retry; повторный запуск и конкурентные jobs безопасны; сбой enqueue не оставляет неустранимое состояние.
- Filament Create/Edit работает, порядок/main/ALT не теряются, один Asset можно использовать в нескольких Product; отвязка не удаляет общие файлы.
- Старые Asset остаются читаемыми, нет выдачи битых URL или скрытого fallback.
- Тесты: проверка Intervention Image v3 на реальном драйвере, профильные, регрессии BE-08.4.4, полный backend suite, Pint `--test` по затронутым файлам, `git diff --check`; отдельная проверка обработки реальным queue worker (не только Queue::fake), если локальная среда позволяет.
- Итоговый отчёт: файлы, миграции, конфигурация Horizon, сценарии/результаты, ограничения, что проверено автоматически и что остаётся ручной проверкой. Не объявлять ручную приёмку выполненной.
