Исправлен MediaAssetProcessor: перед атомарной публикацией через штатный Storage API устанавливаются **0755** для каталога поколения и **0644** для трёх WebP. До rename набор защищён приватными родительскими каталогами, оригинал не переносится и его права не меняются. Для уже созданного Asset 1 исправлены только права каталога готового поколения; повторная конвертация, изменение записей dev-БД и массовая обработка не выполнялись. Horizon перезапущен для загрузки обновлённого кода. Все три существующих URL после исправления возвращают **HTTP 200, Content-Type: image/webp**; размеры остались 6652 / 1762 / 564 байта.

Добавлены regression-проверки фактических POSIX прав, включая обработку настоящими Redis workers. Проверка каталогов использует `fileperms`, поскольку Flysystem `visibility()` определяет обратное соответствие по файловым permission masks и не различает directory mode 0700 надёжно. Fake private disk явно настроен с `directory_visibility=private`.

Storage расположен в именованном Docker volume `laravel_storage`. Каталог `backend/storage` на хосте не является его bind mount и не отражает загруженные файлы. Внутри backend/Horizon исходники находятся в `/var/www/html/storage/app/private/product-originals`, WebP — в `/var/www/html/storage/app/public/product-media`; nginx читает public из того же volume. README дополнен объяснением и командой просмотра файлов.

Автоматическая проверка исправления: MediaOptimizationTest + MediaQueueWorkerTest — **22 passed / 189 assertions**; полный backend suite — **158 passed / 1166 assertions**; Pint по трём PHP-файлам исправления и `git diff --check` — PASS. ## Хранение и обработка

Новые оригиналы сохраняются на существующем приватном `local` disk (`storage/app/private/product-originals/<UUID>.<extension>`), доступном backend и worker в общем storage volume. Синхронно проверяются действительность upload, размер до **10 MiB включительно**, MIME по серверному fileinfo и тип/размеры по реальному заголовку. Ограничения — 12 миллионов пикселей, не более 12000 пикселей по каждой стороне и оценка доступной памяти перед decode. Преобразование внутри HTTP-request отсутствует. Перед decode worker повторяет проверку; повреждённое содержимое с корректным заголовком отклоняет библиотечный decoder. Имена клиента не используются в путях.

Intervention отвечает за чтение, EXIF autoOrientation, масштабирование, прозрачность и encoding; собственных декодеров/encoder/ресайзеров нет. Использованы API v3 [scaleDown и resizeCanvas](https://image.intervention.io/v3/modifying-images/resizing), [toWebp](https://image.intervention.io/v3/basics/image-output). Animation decoding отключён; данный этап создаёт статические варианты, а неподдерживаемый decoder файл становится failed без fallback.

Всегда создаются ровно три WebP:

| Вариант | Фактический размер файла в пикселях |
| --- | --- |
| full | 1000×1000 |
| card | 250×250 |
| thumb | 100×100 |

Сначала содержимое пропорционально уменьшается до границ варианта без crop и upscale, затем центрируется на прозрачном квадратном холсте. Например, исходник 40×20 остаётся 40×20 на всех трёх холстах; 1400×700 становится 1000×500 / 250×125 / 100×50 внутри соответствующих квадратов. Alpha сохраняется, метаданные не переносятся. WebP quality — **84**, задаётся `MEDIA_WEBP_QUALITY` через общий Compose environment и config/media.php.

Отдельная таблица вариантов не нужна для фиксированного набора: одна nullable JSON-колонка `variants` хранит три path/width/height/size_bytes. Новая миграция добавляет `processing_status` (pending/processing/ready/failed), generation token, queued_at, started_at, finished_at и безопасную ошибку. Время обработки определяется started_at/finished_at.

Варианты сначала создаются в приватном `media-processing/<asset UUID>/<generation UUID>/`. Проверяются WebP type и точные размеры каждого результата. Затем весь каталог одним POSIX rename переносится в `public/product-media/<asset UUID>/<generation UUID>/`, где имена `full.webp`, `card.webp`, `thumb.webp` стабильны. Статус ready и manifest фиксируются после успешной публикации всего набора. Поддерживается только текущий общий local filesystem; для S3 нужен отдельный механизм публикации, скрытого fallback нет.

`variantUrl()` возвращает URL только при ready и наличии запрошенного файла. Pending/failed/legacy не подменяются оригиналом. Оригинальные disk/path/MIME/size и generation token скрыты из стандартной сериализации модели. Публичный Product API не добавлялся.

## Очередь, идемпотентность и восстановление

`MediaAssetDispatcher` резервирует запрос под row lock и регистрирует `DB::afterCommit`: Redis не получает job до commit внешней транзакции. Используется явный `Queue::connection('redis')->push(..., 'default')`, поэтому даже тестовый QUEUE_CONNECTION=sync не превращает HTTP-загрузку в синхронную обработку. Сбой enqueue сохраняет pending и безопасную ошибку, снимает queued_at и допускает повторную постановку.

`ProcessMediaAsset` работает в уже существующей **redis/default**, обслуживаемой Horizon supervisor-1. Новая очередь и сервис не вводились. Job имеет 3 попытки, backoff 15/60 секунд, timeout 45 секунд и failOnTimeout=true; существующий Horizon timeout=60, Redis retry_after=90. Память Horizon worker поднята до 256 MiB в соответствии с PHP memory_limit=256M.

Claim pending → processing и финальная публикация защищены row lock и generation token. Повторный job с тем же token при processing/ready пропускается. Новая явная постановка зависшего запроса меняет token, поэтому старый worker не сможет опубликовать результат или изменить новое состояние. Удаление проверяется повторно перед публикацией; удалённый Asset не восстанавливается. Ошибка очищает собственный временный/ещё не зафиксированный набор, не затрагивая ready-файлы других Assets. Прежний ready набор повторными jobs не перезаписывается.

Retry доступен для failed, pending без queued_at, pending старше пяти минут и processing со started_at старше пяти минут. Повторный одновременный запрос блокируется свежим queued_at под row lock. Помимо Filament есть явная операторская команда **`php artisan media:retry <ID>`** для одного Asset; нет `--all`, автосканирования или массового backfill. Команда отказывает для ready/активного запроса и сообщает о недоступности enqueue.

После обычных исключений запускаются ограниченные queue retries; после их исчерпания статус failed. Ошибки собственного validator/processor показывают безопасную причину (decode, memory/type/size limits, запись/публикация, отсутствующий driver); посторонние исключения заменяются безопасным сообщением. Приватные пути и decoder exceptions не выдаются в UI или queue payload failure.

## Filament и совместимость

На Create сохранены Repeater, порядок, выбор main, ручной и автоматический ALT и redirect на Edit. На Edit сохранён Gallery Relation Manager, добавление/переиспользование Asset, reorder, main и редактирование ALT. Изменена только настройка хранилища новых файлов; временные uploads по-прежнему передаются сервису с `storeFiles(false)`. Наличие готовых вариантов не требуется для сохранения Product.

Галерея показывает статус, безопасную ошибку и обновляется каждые пять секунд; thumbnail появляется после ready. Retry имеет проверку `is_admin` и при отображении, и внутри обработчика. Select использует public_id вместо оригинального пути. Отвязка ProductImage сохраняет Asset и файлы, в том числе используемые другими Products.

Старые MediaAsset получают pending без token/queued_at; миграция не dispatch-ит jobs и не переносит/не удаляет оригиналы. Существующий `public/product-images/*` разрешён при повторном attach. Исходный файл остаётся читаемым на прежнем месте, но не выдаётся как fallback-превью. Legacy thumbnail появится только после явной обработки.

Безопасный backfill: сначала составить проверяемый список ID и подтвердить существование исходников, затем вручную обрабатывать выбранный ID через Retry/`media:retry`, проверяя результат перед следующим. Если оригинала нет или он повреждён, Asset станет failed; нужен корректный исходник/новая загрузка по отдельному решению, а не mock. Команда не регенерирует ready: для изменения политики/качества готовых наборов потребуется отдельно согласованный режим regeneration с новым generation manifest, сохранением прежнего набора до переключения и контролируемой уборкой. Массовый backfill/regeneration не запускался.
