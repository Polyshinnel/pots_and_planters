## 1. Цель

Создать надёжный административный механизм изображений товаров: общий `MediaAsset` для физического файла и `ProductImage` для привязки к конкретному Product, с порядком, main image и ALT. Управление — в Filament, без публичного Product API и без Next.js.

## 2. Утверждённые инварианты

1. Один физический файл может использоваться несколькими Product.
2. `media_assets` идентифицирует файл по `disk + path` (уникальная пара); не привязывает ALT, main и порядок к самому файлу.
3. `product_images` хранит принадлежность товару, сортировку, ручной ALT и признак main; повтор одного MediaAsset в одной галерее запрещён.
4. Главное изображение ровно одно при непустой галерее; у пустой галереи main отсутствует. Перестановка изображений не меняет main автоматически.
5. При добавлении первого изображения оно становится main; при удалении main выбирается другое существующее изображение детерминированно (например, первое по sort order, затем ID).
6. ALT по умолчанию вычисляется из **реальных** данных товара (название, подтверждённые размер/finish при наличии, порядковый номер при необходимости); ручной ALT имеет приоритет и не перезаписывается при изменении товара или порядка.
7. Отвязка изображения от товара не удаляет общий файл, если он используется где-либо ещё. Не удалять физический файл в транзакции БД. Удаление физического файла возможно только после commit и повторной проверки ссылок; в рамках этапа безопаснее оставить неиспользуемый MediaAsset и предусмотреть последующую уборку, чем рисковать потерей данных.
8. Для dev использовать существующий `public` disk и отдельный префикс для product images. В схеме сохранить `disk/path`; решение о production storage не принимать.
9. Не придумывать размеры, finish, ALT-описания или изображения, которых нет в данных.

## 3. Объём реализации

### Шаг A — схема и модели

- Добавить `media_assets`: внутренний ID, `public_id` UUID (если согласуется с текущими сущностями), `disk`, `path`, метаданные только при обоснованной необходимости (например, MIME, bytes, width/height — лишь если фактически доступны), timestamps, `UNIQUE(disk,path)`.
- Добавить `product_images`: ID или составной ключ согласно проектным ограничениям, `product_id`, `media_asset_id`, `sort_order`, nullable `alt_override`, `is_main` либо эквивалентный безопасный механизм, timestamps; FK `RESTRICT`/безопасная политика удаления; `UNIQUE(product_id,media_asset_id)`.
- На уровне БД защитить уникальность main на Product с учётом MariaDB 11.8 (например, nullable generated key с UNIQUE); не полагаться только на UI. Если выбран иной механизм, описать и покрыть конкурентные изменения тестами. Избегать циклических FK с `products`.
- Создать модели `MediaAsset`, `ProductImage`, связи Product → images и media. Не изменять уже утверждённые связи Product Core без необходимости.
- Согласовать существующую практику UUID и файловых путей. Не менять существующие Category/News/Catalogue медиа и не переносить их файлы.

### Шаг B — сервис и безопасность файлов

- Реализовать минимальный транзакционный сервис для прикрепления, перестановки, назначения main, ALT override и отвязки; блокировать конкурентные изменения при необходимости.
- Повторная загрузка/прикрепление одного физического файла не должна порождать дубли `media_assets` по `(disk,path)` или `product_images` в одной галерее.
- Загрузка: валидировать MIME/расширение, размер и реальный тип файла; конкретные ограничения выбирать после проверки текущих upload-конвенций и указать в отчёте. Использовать безопасные генерируемые пути, не доверять имени пользователя как storage path. Не допускать traversal и исполняемых файлов.
- Обрабатывать ошибки storage и БД явно: без частичных связей, фиктивного успеха и удаления чужих файлов. При неуспешной загрузке предусмотреть безопасную очистку только заведомо новых неиспользуемых файлов.
- Не реализовывать глобальную библиотеку UI, массовый импорт OpenCart, image conversions, автоматический CDN/S3, фоновую уборку или удаление общих файлов без отдельного согласования.

### Шаг C — Filament 5

- Добавить в существующий Product Resource удобный раздел/Relation Manager «Gallery» с загрузкой изображений, превью, сортировкой, назначением main, редактированием ручного ALT и отвязкой.
- Показывать, какое изображение главное, и эффективный ALT (manual или auto), не выдавая автоматически рассчитанный ALT за сохранённый override.
- Переиспользовать существующие UI-конвенции Filament; не менять публичный дизайн и другие формы.
- Поддержать повторное использование существующего MediaAsset без повторной физической загрузки, если это можно реализовать в границах минимального UI. Если UI выбора из библиотеки требует отдельного большого компонента, остановиться и сообщить об этом до расширения scope; не нарушать инвариант повторного использования на уровне данных.
- Не разрешать физическое удаление общего MediaAsset через галерею Product.

## 4. Границы и запреты

**Не делать:** Product SEO, OG override, canonical/URL, публичный API, Next.js, OpenCart import, product enquiry/cart, миграции в production/staging, изменение дизайна сайта, переписывание Category/News/Catalogue upload, обновление чужих файлов только ради Pint.

**Миграции:** разрешены только в явно проверенной изолированной `potsandplanters_test` через существующий Compose backend. Перед любой миграцией подтвердить имя БД и окружение. Не запускать destructive rollback/refresh в обычной dev-схеме. Существующие реальные медиа не удалять.

## 5. Проверки и критерии приёмки

Обязательные автоматические сценарии:

1. Первая картинка становится main; добавление следующих не меняет main.
2. Main можно сменить независимо от порядка; reorder сохраняется.
3. Удаление main назначает новый детерминированно; пустая галерея не имеет main.
4. DB не допускает два main одного Product и повтор одного Asset в галерее; FK и `UNIQUE(disk,path)` работают.
5. Один Asset прикреплён к двум товарам; отвязка от первого не удаляет файл и не нарушает второй.
6. ALT override сохраняется при изменении имени/атрибутов/порядка; auto ALT строится только из известных данных.
7. Ошибки валидации, storage и транзакций не оставляют частично записанных связей.
8. Загрузка не принимает неподдерживаемый тип/небезопасный файл; права доступа к Filament сохраняются admin-only.
9. Существующие Product CRUD, категории, значения характеристик и весь backend suite не регрессируют.
10. Миграция проходит на чистой тестовой схеме; при безопасной возможности проверить up → rollback → up для новых миграций без затрагивания чужих данных.

Запустить профильные тесты, полный backend suite, Pint `--test` только по затронутым PHP-файлам, `git diff --check`. Если полный Pint уже имеет исторические замечания, перечислить отдельно, не исправлять без запроса.

Ручная проверка владельцем после отчёта: загрузить 2–3 изображения, переставить, поменять main, задать ALT, удалить main, прикрепить общий Asset к другому Product и убедиться в сохранности исходного файла.
