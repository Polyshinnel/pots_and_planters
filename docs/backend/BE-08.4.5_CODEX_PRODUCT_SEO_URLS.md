# BE-08.4.5 — Product SEO & URLs

## Статус и цель
ТЗ для Codex. Предыдущие BE-08.4.4 и BE-08.4.4.1 приняты владельцем после автоматических и семи ручных проверок. Реализовать управление SEO товаров и надёжную модель канонического адреса с историей HTTP 301, **не начиная публичный Product API и Next.js интеграцию**, если их ещё нет. Не объявлять работающий HTTP redirect без реального теста HTTP-слоя.

## 1. Границы этапа
Входит: SEO-поля Product, генерация дефолтов и ручные override, глобально уникальный slug, история внутренних canonical путей, реакция на изменение primary category и slug, SEO UI в Filament с **переиспользованием существующего Google Search Preview**, ограничения/тесты и контракт для будущего API/Next.js. При наличии уже существующего корректного публичного маршрута — интегрировать и проверить HTTP 301; если маршрута нет — подготовить слой разрешения URL и тестируемый контракт, а публичную реализацию явно отложить до BE-08.5/08.6. Не добавлять заглушку или фиктивную страницу только ради 301.
Не входит: публичный Product API, frontend продуктовая страница/новый дизайн, sitemap, массовый backfill и OpenCart aliases (`?product_id=...`) — это BE-09; не начинать BE-08.4.6.

## 2. Каноническая модель
- Единственный canonical: `/shop/{primary-category-slug}/{product-slug}`. Для draft без primary category публичного canonical нет; не генерировать фальшивый slug категории.
- Product slug глобально уникален среди товаров (не только внутри категории), нормализация по существующим проектным правилам, стабильное поведение при коллизиях и пустом slug. Автогенерация из реального Product name при создании, редактирование вручную, валидация и сохранение ручного значения при последующем изменении name. Не вводить скрытых суффиксов без описанного и тестируемого правила.
- Для published Product primary category обязательна (уже реализовано). Изменение slug или primary category изменяет canonical, прежний canonical сохраняется как исторический alias. Для draft: историю создавать только для реально существовавшего публичного canonical, не для промежуточных draft адресов.
- Разрешение secondary-category product path: 301 на текущий canonical **только если** товар действительно назначен указанной категории и адрес не конфликтует с реестром исторических путей; иначе 404. Уточнить приоритеты с историческими путями и зафиксировать их тестами.
- Исторические пути уникальны, не могут перехватывать актуальные canonical другого товара. Предотвращать циклы и цепочки: любой alias резолвится сразу в **текущий** canonical по immutable Product ID. При повторном использовании slug или категории проверять конфликты до commit. Не ломать existing category/news/other routes.
- При архивировании/снятии публикации не направлять на несуществующий или непубличный товар: определить и зафиксировать ожидаемое 404/410 по текущим проектным правилам, не изобретать redirect на категорию.
- HTTP redirect именно **301**, не Next.js permanentRedirect (308). Канонический запрос должен быть 200, неизвестный 404; не перенаправлять на себя. Реализовать 301 в подходящем реальном HTTP-слое, только если он входит в существующую архитектуру и границы этапа. Иначе оставить явный проверяемый resolver + контракт до этапа публичного роутинга.

## 3. SEO поля и defaults
- SEO Title, Meta Description, OG Image, Slug; проверить реальные названия существующих полей/абстракций и использовать согласованный проектный паттерн. Значения по умолчанию только из существующих Product name/description/main ready MediaAsset (если допустимо по существующей модели). Не выдумывать маркетинговые тексты, характеристики, цены или изображения.
- Manual override отличать от автоматически вычисленного значения: изменение Product name не должно затирать ручное SEO. Очистка override возвращает автоматическое значение по явному правилу. Не сохранять HTML/опасный ввод в meta.
- OG Image: приоритет ручного выбора подходящего существующего MediaAsset/готового WebP, затем главного изображения товара со статусом ready; если нет готового изображения — null, без подмены mock или приватным оригиналом. Проверить текущие решения по выбору варианта и будущему API, не менять сам Media Pipeline.
- В Filament добавить SEO секцию к Product, повторно использовать **тот же** Google Search Preview из BE-02; корректный preview URL зависит от primary category и slug. UI/валидация для draft без canonical, ручных override и смены категории.

## 4. Данные, целостность и сохранение
- Спроектировать минимальную схему: SEO поля и реестр исторических URL с FK на Product, уникальностью path, индексами и подходящими MariaDB ограничениями. UUID/public_id если принято для публичных сущностей. Не создавать универсальный redirect engine без необходимости.
- Сохранение SEO, смены primary category и записи истории — атомарно, совместимо с ProductCategoryManager и уже существующей транзакцией характеристик/галереи. Не создавать историю при неуспешном save. Предусмотреть гонки и конфликты при одновременных обновлениях.
- Не переписывать историю при каждом сохранении без изменения canonical; повторное изменение canonical не создаёт дубли. Не менять опубликованный URL неожиданно из-за переименования товара, если slug уже установлен вручную.
- Существующие продукты и незаполненные legacy SEO не должны ломать миграцию. Никакого массового переименования и выдуманных данных.

## 5. Проверки
- Профильные тесты: генерация/ручное редактирование slug, глобальная уникальность и коллизии; SEO override/defaults; published/draft/archived; смена primary category и slug; история и direct-to-current canonical; secondary categories; конфликт исторического пути с актуальным; защита от циклов; rollback; OG Image ready/pending/failed; сохранение существующих данных/галереи/характеристик.
- При наличии публичного маршрута: интеграционные HTTP тесты 200/301/404, Location и **строго 301**, отсутствие 308, без цепочек. При отсутствии — тесты resolver и явное указание, что HTTP 301 будет завершён в BE-08.5/08.6.
- Миграции только в подтверждённой `potsandplanters_test`, цикл up → rollback → up, никаких операций в обычной dev, staging, production без разрешения. Запустить профильные тесты, полный backend suite, Pint для затронутых файлов, `git diff --check`; если тронут frontend — typecheck/тесты/build (но избегать преждевременной frontend интеграции).
- Ручной Filament чек-лист: создание draft, редактирование SEO, preview, публикация, смена slug/primary, OG override и auto fallback, конфликты.
