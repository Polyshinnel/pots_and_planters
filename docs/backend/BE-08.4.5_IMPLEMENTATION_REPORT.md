# BE-08.4.5 — Product SEO & URLs: implementation report

**Дата:** 2026-11-02  
**Статус:** реализовано и автоматически проверено; ручная приёмка Filament владельцем ожидается. BE-08.4.5 не объявляется принятым.

## Read-only аудит до изменений

Прочитаны `AGENTS.md`, актуальные `docs/common/PROJECT_CONTEXT.md`, `docs/common/ROADMAP.md`, `docs/backend/BE-08_ARCHITECTURE_DECISIONS.md`, отчёты BE-08.4.4 и BE-08.4.4.1, модели Product/Category/MediaAsset/ProductImage, миграции, Filament Resources и менеджеры сохранения, Laravel и Next.js маршруты.

- Laravel `routes/web.php` содержит только комментарий: публичный сайт обслуживается Next.js. В Laravel API уже есть категории, новости, каталоги, контакты и Page SEO, но Product endpoint отсутствует.
- Next.js содержит `/shop/[category]/[slug]` и legacy `/product/[slug]`. Текущая `catalogRepository` читает `frontend/src/data/catalog.mock`; при несовпадении категории Product page вызывает `permanentRedirect` (308). Это не реальный маршрут авторитетного Laravel Product, поэтому его нельзя безопасно использовать для проверки новых URL. Для BE-08.4.5 публичный API/Next.js и HTTP redirect не добавлялись.
- Категории имеют SEO-поля, immutable slug в Filament и используют общий `App\Filament\Components\SeoSearchPreview`. Статические страницы используют тот же preview. Новости имеют SEO overrides и свой отдельный content preview.
- Product до этапа имел `name`, состояние и ссылки на категории/галерею, но не имел slug, product description или SEO-полей. `ProductCategoryManager` выполняет сохранение категорий и характеристик в транзакции; галерея хранит ссылку на `MediaAsset`, чьи публичные `full/card/thumb` варианты доступны только после `ready`.
- Обычный Product slug можно редактировать; slug category при редактировании заблокирован. Устаревшие Product reports находятся в репозитории; их описание медиа процесса соответствует текущим моделям и миграциям.

Несоответствие актуальных handoff документов и кода: контекст до этой задачи указывал, что BE-08.4.5 не начат; фактически во frontend уже были product page routes и mock-данные, но не было Product API или реального Product URL contract. Текущие статусы обновлены ниже без изменения OpenCart/BE-09 планов.

## Реализация

- Миграция `2026_11_02_000012_add_product_seo_and_url_aliases.php` добавляет nullable глобально уникальный бинарный slug, nullable `seo_title`/`seo_description`, nullable FK `seo_og_media_asset_id` с `RESTRICT` и таблицу `product_url_aliases` с глобально уникальным полным path, FK и индексом товара.
- Legacy slug остаётся NULL до сохранения товара; массового backfill и переименования нет. При новом сохранении пустой slug генерируется из Product name (`Str::slug`, fallback `product`); конфликт разрешается стабильными `-2`, `-3` и т. д. Уникальный индекс обеспечивает окончательную гарантию, валидация проверяет lowercase kebab-case. Существующий slug не зависит от последующих изменений name; ручное изменение slug поддерживается.
- SEO title override очищается от HTML; пустой override сбрасывается, effective title берётся из Product name. Meta description override очищается от HTML и `script`/`style` блоков; Product description в модели отсутствует, поэтому автоматическое значение — `NULL`. Это не придумывает SEO-текст.
- Ручной OG override принимает только существующий ready MediaAsset через Filament. URL берётся из доступного публичного `full`, затем `card`/`thumb`; если override не готов/недоступен, используется главное изображение товара только при доступном готовом варианте. Иначе `NULL`; private original и mock не возвращаются. Pipeline не менялся.
- ProductResource повторно использует тот же Google Search Preview. Preview строит URL только при выбранной primary category и slug; иначе показывает, что canonical ещё недоступен. Пустые SEO overrides остаются пустыми в форме и не превращаются незаметно в ручные значения.

## Canonical и история URL

Единственный текущий canonical вычисляется как `/shop/{primary-category-slug}/{product-slug}` только для published Product с существующей published primary category. Slug Product уникален глобально. Исторические URL сохраняются как full-path alias и принадлежат immutable Product ID через FK.

`ProductCategoryManager` сравнивает старый и новый canonical внутри существующей транзакции. При изменении slug/category или снятии публикации он резервирует прежний публичный path; draft-only промежуточные URL в историю не попадают. Повторное сохранение неизменного canonical не создаёт alias. Resolver всегда направляет alias напрямую на актуальный canonical Product, поэтому цепочки и циклы не строятся. Конфликт alias с canonical другого товара блокирует commit; уникальный индекс alias и продукта защищает от дублей. Вторичный category path разрешается только когда Product опубликован и назначен этой published категории.

Приоритет разрешения: (1) текущий canonical, (2) точное совпадение с историческим alias, (3) secondary-category path, (4) not found. Если alias совпадает с secondary path, выигрывает исторический alias; это закреплено кодом и является контрактом resolver. Архивный/draft Product возвращает resolver result `not_found` (будущий HTTP слой должен дать 404; 410 не принят проектом как текущее правило). Resolver возвращает только результат и target path; HTTP redirect не имитируется.

### HTTP и публичный сайт

Реальный backend `ProductUrlResolver` не выдаёт HTTP. Laravel web route отсутствует; Next product routes пока используют mock repository и `permanentRedirect` 308. Реальный 301, canonical 200 и unknown 404 не могут быть доказаны для новых backend Product без Product API. Интеграцию строго 301 и HTTP 200/301/404 следует завершить вместе с authoritative Product API/Next.js в соответствующем публичном этапе. BE-09 aliases `?product_id=...` не реализовывались.

## Ручная приёмка Filament

Ожидает владельца. Проверить:

1. Создать draft с пустым slug, проверить slug по имени и изменение имени при сохранённом slug.
2. Проверить глобальную коллизию и описанный `-2` suffix, затем задать ручной SEO title/description и очистить оба overrides.
3. Убедиться, что Google Search Preview повторно использует общий компонент; при отсутствии primary category canonical не выдумывается.
4. Выбрать ready OG MediaAsset, проверить fallback на готовое главное изображение и отсутствие URL для pending/failed.
5. Опубликовать Product; изменить primary category и slug; проверить историю и отсутствие дубликатов при повторном сохранении.
6. Проверить resolver на canonical, alias после нескольких изменений, назначенную secondary category, конфликт alias/canonical и архивный Product.

До ручной проверки этап считается реализованным и автоматически проверенным, но не принятым владельцем. Не начинать BE-08.4.6; Product API/Next.js и BE-09 остаются отдельными этапами.
