## 1. Цель

Администратор в Filament может настроить **для каждой категории** набор фильтров по существующим атрибутам товаров, порядок и тип UI-представления фильтра. Конфигурация должна быть пригодна для будущего публичного Product API, но **без реализации API или интерфейса каталога сейчас**.

Фильтры — метаданные категории, не копии значений товаров. Источник атрибутов — единый справочник Attributes, их типов и опций. Не создавать отдельные product-specific колонки и не переносить данные товаров.

## 2. Предлагаемая минимальная модель

После аудита реализовать отдельную pivot/config таблицу для Category ↔ Attribute (например, `category_attribute_filters`; точное имя согласовать с существующими конвенциями):

- `category_id`, `attribute_id`: FK и UNIQUE пары; приоритет — RESTRICT/безопасное поведение, без каскадной потери данных.
- `sort_order`: целое неотрицательное значение, детерминированная сортировка с tie-breaker по ID.
- `display_type` / `presentation`: **только допустимые для конкретного типа Attribute** варианты; хранить стабильные машинные значения, а не labels.
- `is_enabled` при необходимости — только если существующий UX действительно требует отключения без удаления; не вводить лишнее состояние без причины.
- timestamps, если соответствуют соглашениям проекта.

**Не дублировать** `required`/`filterable` из Product Type ↔ Attribute, `Attribute.type`, единицы измерения, значения опций, значения товаров. Важный смысл: `filterable` в Product Type определяет пригодность характеристики к фильтрации для данного типа товара; Category config определяет **видимость и порядок** фильтра в конкретной категории. Проверить это правило на существующих данных и закрепить в сервисе/валидации.

## 3. Правила совместимости и выбора

1. Для новой настройки категории предлагать только атрибуты, назначенные хотя бы одному Product Type с `filterable=true`, который реально используется товарами категории, **или** (если такой подход создаёт невозможность конфигурировать пустую категорию) атрибуты с `filterable=true` хотя бы у одного Product Type глобально. Выбрать правило после аудита и **явно описать** его в отчёте; предпочтительно поддерживать настройку пустых категорий до импорта товаров. Не ограничивать настройку только текущим составом товаров без обсуждения.
2. Не выдавать неактивные/архивные атрибуты для новых назначений, если у модели есть соответствующий флаг; существующие назначения отображать и сохранять без тихого удаления.
3. Не разрешать `display_type`, несовместимый с `Attribute.type`. Рекомендуемые сочетания (уточнить после аудита существующего UX): `text` → список значений (если это действительно применимо); `number` → диапазон; `boolean` → да/нет; `select` → список опций; `multiselect` → множественный список опций. Не создавать произвольные UI-компоненты на публичном сайте.
4. Никаких придуманных значений, диапазонов, цен или предрасчитанных счётчиков. Фактические доступные значения фильтров позже должны вычисляться публичным API из опубликованных и видимых товаров.
5. Если атрибут больше не доступен как `filterable` ни для одного релевантного Product Type, существующая конфигурация не должна ломать Filament. Показывать понятное состояние/предупреждение и предлагать явное действие администратора, а не скрыто удалять запись.
6. Изменение типа атрибута и снятие назначения уже защищены BE-08.3/4.3: не обходить эти ограничения. Настройки фильтров не должны позволять удаление/смену типа занятого атрибута.
7. Поддержать категории с несколькими Product Types и товары с несколькими категориями. Не навязывать одинаковую конфигурацию разным категориям; наследование от родительской категории **не вводить** без отдельного решения.
8. Защититься от дублей, некорректных presentation и отрицательного порядка на уровне доменной валидации; где разумно — DB constraints. Изменения нескольких фильтров сохранять атомарно.

## 5. Границы этапа

Входит: schema + Eloquent + сервис/валидация + Filament + автоматические тесты + документация. Если полезно, read-only DTO/метод внутри backend для будущего API, но **не добавлять публичный endpoint**.

Не входит: Product API, Next.js фильтры, SQL-подбор товаров, faceted counts, динамические диапазоны, миграция OpenCart, редиректы/Nginx, SEO генераторы, массовый backfill, refactor не относящихся модулей. Не создавать runtime mock fallback.

- Сохранить все существующие незакоммиченные изменения; не выполнять reset/clean, не форматировать посторонние файлы.

## 7. Критерии приёмки

1. В Filament для каждой категории настраиваются фильтры из общего справочника Attributes, их тип представления и порядок.
2. Нельзя создать дубликат, некорректную комбинацию типа/представления или частично сохранённую конфигурацию.
3. Существующие значения товаров, атрибуты и настройки Product Type не изменяются.
4. Конфигурация пустой категории поддерживается без фиктивных товаров.
5. Нет регрессий SEO, дерева категорий, Product Gallery, Product Attribute Values и существующих маршрутов.
6. Проверки и отчёт завершены. **Ручная приёмка Filament владельцем — отдельный шаг; не объявлять этап принятым автоматически.**
