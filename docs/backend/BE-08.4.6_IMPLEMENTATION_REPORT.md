### Фактические модели и данные

- `categories` не имеет `parent_id` или другого дерева; сейчас есть плоские опубликованные категории. Наследование фильтров не вводилось.
- У Category уже есть many-to-many `product_category`; один Product может иметь несколько категорий. У Product один `product_type_id`.
- `attributes` содержит общий справочник `name`, `code`, `type`, nullable `unit` и `is_active`. Типы: `text`, `number`, `boolean`, `select`, `multiselect`. Опции хранятся отдельно в `attribute_options`.
- `product_type_attribute` — связь с `is_required`, `is_filterable`, `sort_order`; FK используют RESTRICT. `filterable` относится к пригодности атрибута для Product Type.
- Значения товаров уже типизированы в `product_attribute_values` (`text_value`, `number_value`, `boolean_value`); select/multiselect хранятся в `product_attribute_selections`. Категорная настройка не должна копировать эти значения.
- Существующего backend Category ↔ Attribute фильтра не найдено. Во frontend есть отдельная mock-логика каталожных фасетов (`filterKeys`); она не подключена к backend и не менялась в этом этапе.
- Read-only запрос к обычной локальной `potsandplanters` показал: 3 опубликованные категории (`Outdoor Pots`, `Indoor Pots`, `Artificial Plants & Trees`), 2 активных Attributes (`Size`, `number`; `Diameter`, `text`), 3 активных Product Types и 2 назначения Attribute, оба у `Pot`. Оба `is_filterable=false`. Есть 1 опубликованный Product (`Pandora floor vase`) в категории `Indoor Pots`, 2 Product Attribute Values и 0 option selections. Следовательно, сейчас нет доступного атрибута для нового фильтра. Это состояние не менялось.
- `potsandplanters_test` перед миграцией была отдельной MariaDB 11.8.9 схемой на host `db`; после тестов прикладные таблицы каталога пусты. В исходной и итоговой проверках подключения target был явно `potsandplanters_test`.

### Выбор eligibility и расхождения с ТЗ

Выбрано предпочтительное правило ТЗ для пустых категорий: для нового назначения доступен активный Attribute, если он назначен хотя бы одному Product Type с `is_filterable=true` — независимо от текущего набора товаров категории. Это позволяет подготовить пустую категорию до импорта товаров и поддерживает смешанное содержимое категорий. Для уже сохранённых связей не требуется повторная eligibility-проверка при редактировании порядка/presentation: снятие filterable или деактивация Attribute не скрывает их и не удаляет запись.

Расхождений, требующих решения владельца по контракту данных, не обнаружено. Существенное текущее ограничение данных — все два существующих назначения filterable выключены; Filament теперь явно объясняет, где включить флаг. Фронтенд mock-фасеты остаются независимым временным механизмом и не считаются конфигурацией BE-08.4.6.

## Реализация

- Добавлена `category_attribute_filters`: composite primary key и уникальность пары обеспечиваются primary key; FK Category/Attribute используют RESTRICT; `sort_order` unsigned; `display_type` ограничен машинными значениями и CHECK constraint; добавлены timestamps и индекс порядка с tie-break по Attribute ID.
- Добавлены отношения `Category::filterAttributes()` и `Attribute::filterCategories()`.
- `CategoryFilterConfiguration` выполняет attach/update/detach в транзакциях, проверяет активность и глобальную filterable eligibility для новых связей, presentation по Attribute type, отрицательный порядок и дубли. Пакетное изменение порядка валидирует полный набор текущих связей и обновляет его одной транзакцией.
- Presentation mapping: `text → values`, `number → range`, `boolean → boolean`, `select → options`, `multiselect → multi_options`. Это стабильные машинные значения; пользователь видит читаемые labels.
- CategoryResource получил relation manager `Filters`: таблица показывает Attribute name/code/type/unit/active state, presentation и order. Добавление предлагает только активные filterable Attributes; пустой список объясняет prerequisite. Редактирование существующей связи сохраняет её при архивировании/deactivation; отдельное удаление снимает только связь. `Set filter order` атомарно изменяет порядок нескольких строк. Существующая форма, SEO preview, slug, публикация и сортировка категории сохранены.
- Запрет смены `Attribute.type` расширен на Attribute, назначенные категорийным фильтром. FK и Category delete guard предотвращают удаление используемых записей; Product Type flags, options и товарные значения не изменялись.
- Публичный API и UI каталога не добавлялись. Динамические значения, диапазоны и counts не вычисляются.

## Ограничения и ручная проверка

Type/presentation compatibility проверяется доменным сервисом и Filament validation; MariaDB дополнительно ограничивает допустимые machine values, но не может выразить соответствие `display_type` к `attributes.type` без cross-table constraint. Все штатные UI mutation paths проходят через сервис.

Обычная локальная схема `potsandplanters` намеренно осталась без новой таблицы. До отдельного разрешённого применения миграции к этой схеме новая Filament-конфигурация может быть проверена только на окружении, подключённом к `potsandplanters_test`; локальную dev-схему для ручной приёмки не меняли.

Перед ручной проверкой владелец должен включить `Filterable` на активном Attribute, который назначен хотя бы одному Product Type (обычная локальная БД сейчас не содержит таких значений). Затем проверить: разные presentation для типов `number`, `select`, `multiselect`, `boolean`, `text`; добавление фильтра в пустую категорию; редактирование и пакетный order; одинаковый Attribute в двух категориях с независимыми настройками; деактивацию Attribute/снятие filterable при сохранённом назначении; явное удаление только category link; отказ при несовместимом presentation/отрицательном order; запрет смены типа занятого Attribute; сохранность Product Type assignment, options и Product Attribute Values.

Этап ожидает ручной приёмки владельца. BE-08.4.7 и последующие этапы в рамках этой работы не начинались.

## Архитектурное исправление по решению владельца

Владелец уточнил, что `filterable` — свойство самой характеристики. Это решение заменяет трактовку из исходных handoff/BE-08.4.6 материалов, где флаг находился на назначении Product Type ↔ Attribute.

- `attributes.is_filterable` теперь источник истины; `product_type_attribute` хранит только применимость, `is_required` и `sort_order`. Attribute Resource редактирует/показывает фильтруемость; Product Type Attributes manager больше не показывает этот флаг.
- Новая eligibility: Attribute активен, `is_filterable=true` и назначен хотя бы одному Product Type. Категории остаются независимой настройкой видимости, presentation и порядка.
- Migration `2026_11_02_000014_move_filterable_flag_to_attributes.php` переносит глобальное значение как OR по старым Product Type назначениям: Attribute получает `true`, если хотя бы одна связь была filterable. Для rollback глобальное значение копируется на каждое старое назначение, потому что прежние различающиеся per-type флаги после сведения к одному значению восстановить нельзя.
- Перенос проверен временными строками только в `potsandplanters_test`: mixed true/false → Attribute true; all false → Attribute false; затем rollback → up. Временные строки удалены. Обычная `potsandplanters` осталась без новой миграции; по read-only аудиту её два старых назначения были false, поэтому при разрешённой миграции оба Attributes останутся not filterable.
- Профиль после переноса — **37 passed / 257 assertions**; полный backend suite — **172 passed / 1241 assertions**; Pint для 10 PHP-файлов и `git diff --check` прошли. Ручная приёмка BE-08.4.6 по-прежнему ожидается.

Новая миграция применена только к `potsandplanters_test`; миграция в обычную локальную `potsandplanters` остаётся pending по исходному ограничению владельца. Код Filament с новым расположением поля требует применения этой миграции в используемой БД перед запуском обновлённого admin UI на ней.
