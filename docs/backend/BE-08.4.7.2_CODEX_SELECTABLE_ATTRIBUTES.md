# BE-08.4.7.2 — Selectable Product Attributes

## Цель
Позволить администратору выбирать применимые **необязательные** Attributes отдельно для каждого Product в Filament Create/Edit. Product Type остаётся источником допустимых Attributes; заполненные значения сохраняются в существующих typed ProductAttributeValue/selections. Не смешивать выбор применимости, фильтрацию категорий и Card Display Attributes (BE-08.4.7.3).

## Обязательный read-only preflight
1. Прочитать `AGENTS.md`, `docs/common/PROJECT_CONTEXT.md`, `docs/common/ROADMAP.md`, актуальные BE-08.4.3/BE-08.4.6/BE-08.4.7.1 отчёты; проверить `git status --short` и `git diff`, включая ручные изменения владельца.
2. Изучить реальные `ProductResource`, Create/Edit pages, `ProductAttributeValueManager`, `ProductCategoryManager`, `Product`, `ProductType`, `Attribute`, pivot `product_type_attribute`, migrations, existing tests. Не предполагать совпадение кода с аудитом.
3. Зафиксировать ограничения: `Attribute.is_filterable` глобален; Product Type pivot содержит `is_required`, `sort_order`; при смене Product Type с сохранёнными values действует запрет. Если схема отличается — описать расхождение и остановиться до рискованной миграции.

## Архитектурные инварианты
- `ProductType ↔ Attribute` определяет **допустимые** атрибуты; `is_required` обязателен при публикации и не отключается для конкретного товара.
- Необязательные атрибуты выбираются администратором индивидуально. Состояния: (1) не выбран, (2) выбран без значения, (3) выбран со значением. Для (2) требуется отдельное сохранённое назначение, не пустая строка value.
- Существующие значения, включая `false`, `0`, decimals, selections и неактивные ранее сохранённые определения, не теряются. Для legacy product с value без нового назначения трактовать attribute как выбранный; миграция/backfill должна сохранить это состояние и быть идемпотентной.
- Нельзя снять выбор с атрибута, имеющего значение: показать понятную ошибку и предложить сначала явно очистить значение, затем снять выбор. Никаких скрытых удалений при toggle.
- Нельзя назначать новые неактивные Attributes, не принадлежащие текущему Product Type. Существующие legacy значения неактивных определений должны оставаться читаемыми/редактируемыми согласно текущим правилам.
- `Attribute.is_filterable` и category filters не менять. `Product Description`, SEO, SKU, price, gallery Create/Edit, statuses, category/primary, URL registry не менять.
- Не создавать ProductVariant, не дублировать значения или определения Attributes.

## Этап 1 — схема и доменная модель
- Ввести минимальную таблицу выбора `product_attribute_assignments` (название уточнить по конвенциям репозитория): `product_id`, `attribute_id`, уникальный составной ключ, FK/индексы/каскады согласно существующей модели. Без поля значения и без преждевременного `sort_order` (порядок type-level, display-order в следующем этапе).
- Проанализировать DB-ограничение соответствия Product Type↔Attribute. Не добавлять хрупкий составной FK без проверки существующих ключей и сценариев смены типа; обязательно серверная проверка в одной транзакции.
- Добавить отношения модели и механизм совместимости со старыми ProductAttributeValues. Для уже существующих данных выбрать безопасный backfill из values (без уничтожения values), проверить повторный запуск/rollback. Уточнить, что делать с required-назначениями: при чтении всегда считать выбранными; при записи допустимо создавать явные assignments, но не допускать разного поведения Create/Edit.
- При удалении/изменении Product Type↔Attribute, деактивации и смене типа сохранять существующие защитные инварианты. Не ослаблять проверки ради новой таблицы.

## Этап 2 — транзакционное сохранение
- Расширить существующий manager/service без параллельного механизма записи значений: передавать список выбранных optional Attribute IDs отдельно от typed values.
- В одной транзакции валидировать допустимость назначений, обязательность при публикации, совместимость inactive/legacy и отсутствие скрытого удаления. При ошибке откатывать Product, categories, selections, assignments и values согласованно.
- Не интерпретировать пустой value как снятие применимости; очищение value и снятие assignment — два явных действия.
- Если выбор отключается после явной очистки, обеспечить корректное сохранение и отсутствие orphan selections. Сохранить запрет смены Product Type при заполненных values; оценить, должны ли **пустые assignments** также блокировать смену типа либо явно очищаться после подтверждения — выбрать безопасный вариант и покрыть тестом, не удаляя молча.

## Этап 3 — Filament Create/Edit
- Секция Attributes: показывать required Attributes Product Type как всегда включённые; optional — управляемый выбор из назначенных этому типу (checkbox/select/add action — выбрать по текущим UI-паттернам Filament).
- Поля значений отображать только для выбранных/required, плюс исторические неактивные с данными. Сохранённые assignments с пустым значением должны восстанавливаться при повторном открытии Edit.
- При попытке снять заполненный optional Attribute блокировать действие/сохранение с понятным сообщением, без потери данных. При изменении Product Type обновлять доступный список без нарушения существующего запрета и без очистки данных.
- Сохранить существующий стиль ProductResource, галерею на Create и Edit, SEO Google Search Preview. Не изменять публичный Next.js/API.

## Этап 4 — тестирование и отчёт
- Тесты схемы, уникальности и связности; Create/Edit; required на draft/published; все 5 типов; selected-empty persistence; legacy value без assignment; inactive options; запрет снятия с заполненным значением; очистка затем снятие; недопустимый/чужой Attribute; смена Product Type; транзакционный rollback; backfill/rollback/re-run.
- Использовать только Docker Compose и изолированную MariaDB `potsandplanters_test` для миграций и тестов. **Никаких миграций dev/staging/production** без явного разрешения.
- Запустить профильный набор, полный backend suite, Pint затронутых PHP-файлов и `git diff --check`. Не изменять frontend и не выполнять нерелевантные проверки без причины.
- Отчёт: фактические файлы и миграции, принятые решения по required/empty assignments/type changes, точные команды и результаты тестов, ограничения, чек-лист ручной приёмки Filament, статус dev schema, `git status` и сохранённые незакоммиченные изменения. Обновить PROJECT_CONTEXT.md/ROADMAP.md по факту, не объявлять ручную приёмку завершённой.

## Критерии приёмки
1. Для круглого изделия можно выбрать Diameter+Height, для прямоугольного Length+Width+Height в рамках одного Product Type, если эти Attributes назначены ему и не являются обязательными для всех.
2. Выбранный, но пустой Attribute остаётся выбранным после сохранения и повторного открытия.
3. Никакие ранее сохранённые typed values/selections не пропадают автоматически; заполненный Attribute нельзя отключить до очистки.
4. Required Attributes нельзя отключить; публикация с незаполненным required по-прежнему отклоняется.
5. Изменения атомарны, ошибки явно видны, ручные исправления `Attribute.is_filterable` сохранены.
6. API/Next.js, SEO, галерея и публичный дизайн не изменены.
