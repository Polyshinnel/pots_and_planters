## Реализация и решения

- Добавлена `product_attribute_assignments` с составным PK `(product_id, attribute_id)`, FK на Product (cascade при удалении) и Attribute (restrict), timestamps и индексом по Attribute. Таблица не дублирует значения и не содержит `sort_order`.
- Миграция backfill-ит optional assignments для существующих `product_attribute_values`; required attributes остаются выбранными по `is_required`. Backfill использует `INSERT … ON DUPLICATE KEY UPDATE`, поэтому повторный запуск его DML безопасен. При миграции тестовая схема не содержала существующих Products/values; legacy-сценарий отдельно проверен feature test-ом: value без assignment восстанавливается как выбранный и сохраняется.
- В Product добавлена связь `selectedAttributes()`, в Attribute — обратная связь `selectedProducts()`.
- `ProductAttributeValueManager` принимает список optional IDs отдельно от typed values. Проверяет связь с текущим Product Type, обязательность, активность, значения и selections; синхронизирует assignments и typed values в общей транзакции с Product/categories. Ошибка значения откатывает и Product, и assignments.
- Required attributes не входят в переключатель и всегда отображают поле; незаполненный required блокирует публикацию прежней серверной проверкой. Optional selection без value сохраняется отдельной строкой assignment.
- Existing values автоматически интерпретируются как выбранные для legacy совместимости. Нельзя снять выбор, пока scalar value или selections не очищены и сохранение не завершилось; очистка и снятие выбора — два отдельных сохранения. При снятии пустого assignment orphan value удаляется, если существовал пустой legacy row.
- Неактивные Attributes не предлагаются для новых выборов; ранее назначенные или имеющие legacy value остаются доступны. Изменение Product Type требует предварительно сохранить снятые пустые selections; saved values по-прежнему нужно явно очистить/перенести. Product type assignments не удаляются молча.
- Category filters, `Attribute.is_filterable`, описание, SEO, галерея, URL registry, frontend, публичный API и Product statuses вне существующей required-проверки не менялись.

## Миграции и проверки

Все миграции и тесты выполнялись в Compose `backend`, с явным `DB_DATABASE=potsandplanters_test`. `db:show` подтвердил database `potsandplanters_test`, host `db`. Помимо обычного `rollback → migrate`, backfill проверен на временной legacy-записи: в тестовой схеме создан Product с optional numeric value без assignment, миграция откатилась и повторно применилась, после чего assignment присутствовал, а `number_value` сохранился как `0.123456`. Временные Product, value, Product Type, Attribute, Brand и Supplier удалены. Итоговый `migrate:status` показывает migration 000016 как `Ran`; контрольные counts для Products/values/assignments и временных справочников — 0. Обычная `potsandplanters` и dev schema не мигрировались. Их схема остаётся без таблицы assignments; Product Create/Edit на такой схеме требует отдельного применения миграции до запуска обновлённого admin UI.

- Профильная команда: `docker compose -f compose.yaml -f compose.dev.yaml exec -T backend sh -lc 'DB_DATABASE=potsandplanters_test php artisan test --compact tests/Feature/ProductAttributeValuesTest.php tests/Feature/ProductDescriptionTest.php tests/Feature/ProductAdminTest.php tests/Feature/ProductCategoriesTest.php tests/Feature/ProductSeoUrlsTest.php tests/Feature/ProductTypeAttributeTest.php'` — **41 passed, 245 assertions**.
- Полная команда: `docker compose -f compose.yaml -f compose.dev.yaml exec -T backend sh -lc 'DB_DATABASE=potsandplanters_test php artisan test --compact'` — **180 passed, 1281 assertions**. Логи содержали ожидаемые диагностические warning/error из тестов Telegram, Infrastructure и media; suite завершилась успешно.
- Pint на 8 затронутых PHP-файлах через Compose: `vendor/bin/pint --test ...` — **PASS**. Обычный форматирующий режим Pint не смог записать файлы через read-only bind mount backend; выявленные Pint отличия поправлены в workspace, повторный `--test` прошёл.
- `git diff --check` — **PASS**.

Проверены round-trip пяти типов, `false`, decimal, select/multiselect, required на draft/published, Filament create/edit, пустой выбранный Attribute, legacy value без assignment, inactive options, чужой Attribute, дубликат assignment, запрет снять заполненный Attribute, очистка отдельным сохранением, запрет смены Product Type при выборе и транзакционный rollback, включая сбой финальной серверной валидации после синхронизации assignment. Backfill фактически проверен с предварительно сохранённой legacy value; DML использует upsert для устойчивого повторного применения.

## Ручная приёмка Filament

Проверить в интерфейсе создание и редактирование Products:

1. В одном Product Type выбрать разные optional характеристики для круглого и прямоугольного товара.
2. Сохранить выбранный пустой Attribute и убедиться, что он отмечен после повторного открытия.
3. Убедиться, что попытка снять заполненный Attribute показывает ошибку и сохраняет значение; затем очистить, сохранить, снять выбор и сохранить.
4. Убедиться, что required нельзя отключить, required value требуется только при публикации, inactive/legacy поля доступны для существующих данных.
5. Убедиться, что предупреждение о Product Type понятно и сначала требует отдельного удаления optional selections.

Ручная приёмка владельцем не выполнена, поэтому этап пока не считается принятым. Product API, Next.js и BE-08.4.7.3 не начинались.
