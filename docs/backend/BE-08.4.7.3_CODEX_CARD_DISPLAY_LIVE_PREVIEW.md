# BE-08.4.7.3 — Card Display Attributes + Live Product Card Preview

## Цель
В Filament ProductResource дать администратору выбрать и упорядочить характеристики, отображаемые под названием товара, и сразу увидеть **живой предпросмотр полной карточки** в визуальном стиле существующего каталога Next.js. Не менять публичный Next.js, API, SEO и маршруты на этом этапе.

## Перед изменениями: обязательный read-only аудит
1. Прочитать `AGENTS.md`, `docs/common/PROJECT_CONTEXT.md`, `docs/common/ROADMAP.md`, актуальные отчёты BE-08.4.7.1/.2 и проверить `git status --short`; не затирать ручные/незакоммиченные изменения.
2. Проверить реальные модели/миграции `Product`, `Attribute`, Product Type, selected assignments, typed values, `ProductResource` Create/Edit, MediaAsset/gallery и цену.
3. Изучить **точную** структуру и стиль публичной карточки: `frontend/src/components/catalog/ProductCardDetails.tsx`, `frontend/src/components/home/ProductCard.tsx`, используемые ими компоненты/стили и `frontend/src/lib/catalog/format-specifications.ts`. Выяснить точный порядок изображения, имени, SKU, цены, спецификаций и поведения `Price on enquiry`. Не переносить наугад и не менять публичный дизайн.
4. Проверить ограничения реактивности Filament 5/Livewire: обновление при изменении несохранённых значений, выбранных атрибутов и их порядка, name, price, SKU, основного изображения. Зафиксировать, какие поля доступны в Create до сохранения.
5. Если выявлено несовместимое с согласованной моделью поведение — описать и предложить минимальное решение в отчёте; не расширять scope молча.

## Принятые решения и инварианты
- Product Type задаёт допустимые Attributes; Product выбирает применимые optional Attributes; required Attributes не отключаются. Выбранные и пустые значения сохраняются отдельно от typed values (BE-08.4.7.2).
- `Attribute.is_filterable` глобален и не связан с Card Display.
- Product name — чистое название; display-настройка не переписывает имя, SEO, значения или snapshots заявок.
- Храним **только уникальные ID выбранных Attribute в явном порядке**; никаких копий label/value/unit и никакого произвольного HTML в конфигурации.
- Отображать можно только атрибуты, разрешённые Product Type и выбранные для конкретного товара; required считаются выбранными. Legacy typed values должны продолжать считаться выбранными согласно действующему контракту.
- Если атрибут снят/стал недопустим, не оставлять битые display-ссылки: валидировать и поддерживать консистентность в той же транзакции. Не удалять typed values незаметно.
- Пустые значения не отображать и не создавать пустых разделителей; `false`, `0`, десятичные числа и выбранные options обрабатывать корректно, без потери точности.
- Никаких mock-значений или выдуманных изображений/цен в preview. Nullable price — существующее поведение `Price on enquiry`.
- Ошибка галереи Create оставляет созданный товар с существующим уведомлением и восстановлением через Edit — не менять.
- Production/dev миграции без разрешения запрещены; только изолированная `potsandplanters_test` для тестов.

## Этап A — хранение и валидация
1. После аудита выбрать минимальный способ хранения упорядоченного списка ID: например, nullable JSON в `products` с корректным cast/validation; не создавать отдельную сущность без необходимости. Forward migration, rollback, совместимость старых товаров (пустой список по умолчанию), отсутствие потери данных.
2. Серверная валидация: ID целые/существующие, уникальные, принадлежат Product Type, применимы к Product, без произвольных значений. Сохранение вместе с Product/selected attributes/typed values атомарно, в соответствии с текущими менеджерами.
3. Предусмотреть изменение списка применимых атрибутов: не допускать тихого сохранения невалидной конфигурации; при попытке снять display-атрибут обеспечить понятную валидацию либо явную корректировку списка без удаления значений. Выбрать наиболее безопасный вариант после изучения текущего UX.
4. Не добавлять новых SEO/публичных API полей в этом этапе.

## Этап B — краткие обозначения и форматирование
1. Добавить необязательный `short_label` у Attribute **только если после аудита нет эквивалентного поля**. Настройка в существующем AttributeResource; безопасная ограниченная длина, trim, отсутствие HTML; старые записи совместимы.
2. Unit брать из существующего `Attribute.unit`. Не выводить `Ø`, `H`, `L`, `W` на основании имени/slug: только из явно настроенного short label. При его отсутствии выводить значение/label по согласованному fallback, не угадывать.
3. Реализовать небольшой тестируемый Laravel formatter/view-model для preview и будущего DTO, который получает реальные выбранные значения, типы, option labels, unit и порядок. Decimal не приводить к float. Для boolean/multiselect явно определить стабильное отображение. Не создавать универсальный форматтер для всех случаев.
4. Формат объединения: размеры можно соединять ` × `, остальные параметры — ` · `, **только если правило группировки явно задано** (существующая metadata или минимальная новая конфигурация). Не определять «размер» по имени атрибута. Если не хватает основания, применить безопасный единый разделитель и вынести решение на согласование, а не угадывать.
5. Примеры `Ø 50 × H 125 cm · Silver leaf` использовать лишь как тестовые fixture, не как реальные product данные. Проверить круглую и прямоугольную геометрию.

## Этап C — Filament UX и Live Preview
1. В ProductResource дать выбрать из применимых атрибутов подмножество для карточки, включить/исключить и переставить порядок. Не показывать чужие Product Type атрибуты. Предусмотреть пустой список, Create/Edit, переключение Product Type по текущим ограничениям, неактивные сохранённые значения.
2. Добавить **живой предпросмотр полной карточки** в Filament (Blade/Livewire/Filament, без встраивания React или тяжёлых новых зависимостей). Внешний вид воспроизводит текущую карточку каталога: изображение, название, SKU, спецификации, цену и состояния отсутствующих данных — только те элементы, которые действительно есть в актуальном публичном компоненте.
3. Preview реагирует на несохранённые изменения формы, в том числе имя, цену, SKU, selected/display attributes, значения и порядок; для изображения использовать доступное главное изображение, если ready, иначе корректный placeholder. Не делать запросы ко всем MediaAsset и не подставлять mock. Если мгновенное отображение загруженного в Create файла невозможно без сохранения, явно показать состояние и документировать ограничение, не имитировать готовое изображение.
4. У preview не должно быть публичных ссылок, добавления в корзину или отправки заявки. Не изменять публичную карточку Next.js. Стили preview сверить по фактическому frontend, не создавать новую публичную дизайн-систему.
5. При необходимости ограничить число запросов и избежать N+1 при получении gallery/attributes; не вводить polling без необходимости.

## Этап D — проверки и отчёт
- Профильные тесты: migration up→rollback→up; модель и серверная валидация списка; дубликаты/чужой Attribute/невыбранный Attribute; Create/Edit, порядок и перезагрузка; legacy values; изменение optional assignment; required; inactive; значения `0`, `false`, decimals, options/multiselect; пустые значения; цена NULL; отсутствие изображения; отсутствие SEO-побочных эффектов.
- Проверить formatter отдельно: short labels, unit, разделители, escaping, отсутствие float conversion, порядок. Проверить Livewire/Filament preview насколько позволяют тестовые средства; подготовить ручной чек-лист на динамическое обновление и визуальное сравнение с Next.js.
- Запустить профильные и полные backend-тесты в Docker Compose на `potsandplanters_test`, Pint для затронутых PHP-файлов и `git diff --check`. Frontend только read-only, если изменений там нет. Не применять миграции к обычной dev/production БД.
- Отчёт `docs/backend/BE-08.4.7.3_IMPLEMENTATION_REPORT.md`: изменённые файлы, решения и ограничения, команды/результаты проверок, состояние dev schema, что проверено автоматически и что ожидает ручной приёмки. Обновить `docs/common/PROJECT_CONTEXT.md` и `ROADMAP.md` с точными статусами.
- Не начинать BE-08.4.7.4 или BE-08.5. Не трогать nginx 301, SEO auto generation, импорт OpenCart, публичные маршруты или дизайн.

## Критерии приёмки владельцем
- Можно настроить для Round Planter Diameter+Height, а для Square Planter Length+Width+Height в одном Product Type; порядок display настраивается независимо.
- Изменение значений сразу отражается в preview; отображение не содержит невыбранных/пустых атрибутов и не дублирует данные.
- Полная карточка визуально соответствует текущему каталогу; отсутствие изображения/цены показано честно.
- Повторное открытие Edit сохраняет порядок; заполненные значения, SEO, SKU, галерея и публикация не повреждены.
- Все тесты и ручные проверки документированы отдельно, без заявления о полной приёмке до подтверждения владельца.
