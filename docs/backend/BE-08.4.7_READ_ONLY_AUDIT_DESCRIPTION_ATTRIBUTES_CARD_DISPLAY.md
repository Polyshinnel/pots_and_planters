# BE-08.4.7 — read-only аудит перед расширением модели товара

## Цель
Проверить фактическую реализацию модели Product, ProductResource, динамических атрибутов и формирования строки характеристик на публичном сайте, чтобы подготовить небольшие безопасные ТЗ для BE-08.4.7.1–4. **Только аудит: ничего не менять.**

## Контекст и утверждённые решения
- Стек: Laravel 13, Filament 5, MariaDB; Next.js 16, React 19, TypeScript, Mantine 9.
- Product Description — отдельное форматируемое поле (RichEditor), не SEO Meta Description. Без выдуманной автогенерации SEO.
- Product Type задаёт допустимые атрибуты; конкретный Product выбирает только применимые (например, Diameter+Height либо Length+Width+Height). Не создавать дубли значений.
- Отдельная конфигурация Product определяет, какие из выбранных заполненных атрибутов и в каком порядке показываются под кратким названием товара. Пример формата: `Ø 50 × H 125 cm · Silver leaf`; значения берутся из атрибутов, не из ручной копии текста.
- Сохранять глобальный `Attribute.is_filterable`, Category Filter Configuration, неизменность SKU/Product ID, правила публикации и текущую галерею Create/Edit. При сбое прикрепления файлов в Create товар остаётся созданным, показывается уведомление и доступно восстановление через Edit.
- Публичный дизайн, SEO-маршруты, Product API, миграции и production не трогать. Не допускать runtime fallback на mock.

## До начала
1. Прочитать `AGENTS.md`, актуальные `docs/common/PROJECT_CONTEXT.md`, `docs/common/ROADMAP.md`, ADR и предыдущий аудит BE-08.4.7. Документы в репозитории могут отличаться от ранее присланных версий.
2. Снять `git status --short` и сохранить список незакоммиченных изменений; не делать reset/checkout/format.
3. Найти реальные файлы и ссылки на строки; не предполагать пути или устройство модели заранее.

## Проверки
### A. Description
- Есть ли уже описание в БД, модели, API/DTO, mock/Next.js и миграционных источниках? Какова семантика существующих `description`, `short_description`, SEO description?
- Найти существующий безопасный RichEditor pipeline у News: формат хранения, sanitizer, разрешённые элементы, ссылки, отображение и тесты. Оценить возможность повторного использования без создания общего абстрактного фреймворка.
- Предложить nullable-поле и безопасную обратную совместимость; отдельно оценить миграцию старого OpenCart HTML (без фактического импорта).

### B. Индивидуальный выбор атрибутов
- Проследить ProductType↔Attribute, `is_required`, ProductAttributeValueManager, модель значений, Filament Create/Edit, транзакции, inactive options и смену Product Type.
- Как сейчас строятся поля? Сохраняются ли пустые значения? Можно ли отличить «не выбран» от «выбран, но пока пуст»? Какие ограничения БД/сервиса мешают явному выбору?
- Сформулировать минимальную модель выбора применимых атрибутов с сохранением существующих значений. Рассмотреть, нужна ли отдельная связь/selection state, или достаточно текущей таблицы значений; обосновать выбор и сценарии незаполненного значения.
- Уточнить семантику required: действительно обязательные для всего Product Type атрибуты должны проверяться при публикации; не превращать Diameter в обязательный для квадратных кашпо. Описать правила для ранее сохранённых значений и inactive атрибутов.

### C. Характеристики под названием
- Найти источник текущего полного названия и строки характеристик в mock, Next.js Product Card, Product Detail, Cart/Enquiry; показать точные файлы и форматирование, проверить разделение title/variant/size/finish.
- Определить минимальную структуру per-product выбора и порядка отображаемых атрибутов без дублирования их значений. Учесть units, numeric/decimal, select/multiselect, boolean, отсутствующие значения, локализацию публичного английского UI, типографику `Ø`, `×`, `·`.
- Разделить конфигурацию данных и форматтер; не менять публичный дизайн в этом аудите. Проверить, где понадобится одна и та же строка (карточка, PDP, корзина, snapshot заявки) и какие обратные совместимости необходимы.

### D. Риски и проверки
- Проверить миграции, FK, уникальность, порядок, транзакционность, ограничения удаления/смены Product Type, SEO preview, публикацию и существующие тесты.
- Отдельно отметить расхождения документации с реальным кодом, включая перенос `is_filterable` на Attribute.
- Определить, можно ли внедрить изменения без модификации публичного Next.js до BE-08.5; выделить любые блокирующие решения владельца.

## Результат
Вернуть в ответе Codex (без изменений файлов):
1. Таблицу «факт / риск / файл:строка» по трём направлениям.

3. План четырёх независимых подэтапов: **BE-08.4.7.1 Description**, **.2 Selectable Attributes**, **.3 Card Display Attributes**, **.4 Regression/Acceptance**. Для каждого: цель, ограничения, изменения, критерии приёмки, тесты.
4. Отдельный перечень вопросов, требующих решения владельца; не считать предположения утверждёнными.
5. Подтверждение, что `git status --short` после аудита не изменился.
