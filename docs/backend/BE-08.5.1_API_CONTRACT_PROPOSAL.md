# BE-08.5.1 — предложение Product API Contract

Статус: proposal; **Requires owner approval** для помеченных решений. Это спецификация, не реализованный контракт. Примеры данных синтетические.

## 1. Рекомендуемые read-only endpoints

| Method/path | Назначение | Успех |
|---|---|---|
| `GET /api/v1/products` | Публичный список; глобальный список либо категория | `200 {data, meta, facets}`; пустой список — 200 |
| `GET /api/v1/products/{slug}` | Деталь по globally unique product slug; не принимает category path и не перенаправляет | `200 {data}`; неизвестен/не опубликован — одинаковый 404 |

Текущие `GET /api/v1/categories` и `/categories/{slug}` оставить без breaking changes. Они не содержат product filters; list response при `category` включает фильтры и facets, поэтому отдельный filter endpoint не нужен на первом этапе. Зафиксировать, что фильтры доступны только с category scope.

### List query

- `category=<category-slug>` опционально. Category должна быть published; неизвестная category — `404 category_not_found` (не пустая выдача).
- `page=1..N`, default 1; `perPage=12`, разрешённый диапазон 1–48. Invalid/out-of-range syntax → 422. Валидная страница за концом диапазона даёт `data:[]`, `meta` с requested page и total; не clamp молча.
- `sort=featured|name-asc|name-desc|price-asc|price-desc`; default `featured`. Для price sort null prices идут после точных значений; ties стабильно по public ID. Смысл featured и tie order требует owner approval, так как нет Product featured field.
- `filter[<attribute-code>]=<value>[,<value>...]`; значения — option stable key (`attribute_options.value`) для select/multiselect, `true|false` для boolean, exact canonical value для text/number только если выбрана `values` presentation. `range` принимает `filter[code][min]` и `[max]`. Невалидный/non-configured filter → 422 с ошибкой; выключенный filterable/config или empty facet не принимается.
- OR между несколькими selected values одного multiselect filter, AND между разными attributes. Для списка категорий фильтры применяются к опубликованным товарам, где категория любая назначенная published category, не только Primary Category. Семантика ranges/counts и unsupported mixed type needs approval.
- Фильтрация/сортировка должна быть серверной до пагинации. Пустой category result: `200`, `data:[]`, `meta.total:0`, `facets:[]`.

## 4. Error/status policy

Рекомендуемый stable envelope:

```json
{"error":{"code":"product_not_found","message":"The requested product was not found.","requestId":"synthetic-request-id"}}
```

- `200`: found list/detail; empty list valid.
- `404`: product absent, draft, archived, unpublished category/primary category, or unknown slug. Same external response prevents public status enumeration. Category endpoint can use `category_not_found`.
- `422`: malformed query, unknown filter key/value, invalid pagination/sort. Include `errors` keyed by query field; never include SQL/stack details.
- `503`: backend/database unavailable, generic `service_unavailable` and `requestId`; frontend error boundary shows unavailable state and does not render mock products.
- Current Laravel APIs often use `firstOrFail` or validator JSON defaults; this normalized envelope is proposed, not established behavior. Status-specific mapping and request IDs need implementation approval.
- `Cache-Control: no-store` recommended for first release, matching existing Laravel APIs and Next `serverApiFetch`. Do not add ISR or cached stale product snapshots without separate agreement.

## 5. Publication, IDs, categories, URL

- Only `products.status=published` and a published primary category can be returned. A public list also requires at least one published associated category. A category-specific list includes association to requested published category.
- Brand/Supplier inactive handling is **Requires owner approval**. Recommendation: keep Product visible by Product status initially; inactivity should not silently hide/alter history unless explicit policy requires cascading public hide. Supplier ID/name need not be in public DTO absent a consumer.
- Inactive Product Type/Attribute/Option behavior is **Requires owner approval**. Recommendation: preserve values attached to published Product for display even if definition inactive; omit inactive option from selectable filter choices but preserve its display label for the saved product. This conflicts with potentially stale option semantics and should be explicit.
- `id` is Product `public_id`, stable UUID. No DB key. SKU is a displayed model code and validation cross-check, not sole ID.
- canonical path computed only by `ProductUrlResolver::canonicalPath`: `/shop/{published-primary-category-slug}/{product-slug}`. List links for any secondary category use this same path. Detail endpoint returns product by slug and its canonical path; it does not issue redirects or mutate aliases.
- Path mismatch / historical alias / secondary category direct request: Product API still returns product detail when slug resolves, with canonicalPath; Next response behavior remains a future routing decision. Exact 301 and old OpenCart URLs stay BE-09 after legacy mapping. Do not build redirects in BE-08.5.
- Unknown slug and unpublished product are identical 404. A stale alias points to current canonical only in future redirect layer, not this API.

## 6. Attribute/filter semantics

### Proposed DTO value semantics

`attributes[]` carries `code`, type, public stable attribute id, label, value and unit. Scalar `text` value is string; `number` is decimal string with scale six; `boolean` is JSON boolean (including false); select/multiselect should use option stable key and label. Empty scalar, no selected option, and unselected optional Attribute are omitted. Required fields remain represented only if populated. Consider switching number `value` to string uniformly for simpler TS and no precision loss.

Card display uses ordered `card_display_attribute_ids`; backend `ProductCardSpecificationsFormatter` is the proposed authority for both `cardSpecifications[]` and `cardSpecificationsText`. Short label fallback is Attribute name. Numeric unit is emitted for number values. Select/multiselect use option labels as current formatter does. Empty/missing value omitted. Structured rows support PDP; card text preserves `ProductCardDetails` visual contract. This duplicates a presentation product intentionally in a single backend authority, not two independently calculated values. Requires approval because the current frontend formats legacy dimensions independently.

### Filter discovery and matching

- A Category filter is eligible only when pivot-configured, Attribute active, globally `is_filterable`, assigned to at least one Product Type, and its `display_type` is compatible.
- Runtime eligible facet values/counts come only from public Products returned for that category. This handles mixed Product Types by only counting Products having the Attribute and compatible values; it does not synthesize values from inactive attributes.
- Current storage supports `text`, `number`, `boolean`, `select`, `multiselect`; category display types are `values`, `range`, `boolean`, `options`, `multi_options`.
- No range-boundary semantics, exact text normalization, multiselect matching rules, facet counts after other selected filters (disjunctive/conjunctive facets), OR semantics for selected options, and unknown/inactive existing option behavior have been approved. Proposal uses conjunction across attributes, OR within one attribute; counts are computed after all filters (conjunctive). **Requires owner approval**.
- Legacy query parameters `material`, `color`, `size`, `usage` are hardcoded in mock domain. Mapping these keys to dynamic `Attribute.code`, whether query params should instead become `filter[code]`, and preservation of shareable legacy URLs need approval. Recommend `filter[code]` going forward, with any compatibility mapping explicit.
- Filter `count` reflects distinct published products in requested category, including secondary category assignment. Price ranges and count meaning when no matching products need confirmation.

## 7. Media and SEO

- Only ready media whose variant object still exists is serialized. `ProductImage` effective ALT is override or generated “Product image of {name} [position]”; preserve gallery order and single main.
- Card `card` variant preference, gallery full/card/thumb variant requirements, and what to do when `full` absent need agreement. Recommendation: card uses card then thumb; gallery uses full then card then thumb; omit if none; UI existing honest image placeholder handles no image. Never use pending/failed source original.
- Manual OG ready image then main ready image matches model accessor; no storage disk/path internals. URLs may be public `/storage/...` variants. Do not return original filename/path, storage key or private original path.
- SEO title: explicit override or product name. Meta description: only explicit override unless owner approves a specific fallback; no auto-generated SEO copy asserted. OG URL uses canonical; OG image follows ready override/main logic. `robots` current frontend marks Product noindex; whether to retain or change on integration is **Requires owner approval**. Canonical and OG host derive from configured public site URL, while DTO `canonicalPath` is host-independent.
- Sanitize description in Laravel (already done on model save) and serialize nullable HTML; don't duplicate unsafe source trust. Confirm browser-safe output and link policy in integration tests.

## 8. Frontend, cart and enquiry compatibility

- Keep `/shop`, `/shop/[category]`, `/shop/[category]/[slug]`, `/product/[slug]`, category query state, existing card/gallery/actions and design. Product DTO mapping changes repository source, not components/design. API failure is an error state, not mock fallback; 404 maps to Next `notFound`, 503 to existing/new error UI, empty list to explicit empty UI.
- Detail metadata and page rendering use one fetched DTO; canonical path comes from API. No premature redirect behavior change. Current page `permanentRedirect` for non-primary category is an existing Next 308, distinct from D4 desired 301; resolve in BE-09 routing integration.
- Cart browser storage currently stores `{productId,sku,quantity}`; line display resolves name/attributes/price from fixture. Proposed later behavior resolves live DTO by stable public ID+SKU at server boundary; client display can refresh snapshots from detail/list API. On submit Laravel must recheck same published Product public_id and exact SKU, ignore client-supplied name/attributes/price for authoritative record, persist submission-time snapshot. Deletion/archive/unpublish outcome: reject unavailable items rather than silently dropping or rewriting; **Requires owner approval**.
- API decimal strings must stay strings in DTO and snapshots. Existing enquiry JSON uses numeric `informationalUnitPriceAed`; migration to exact decimal string and server-authoritative price needs a separately versioned/enabled enquiry contract. Do not break current Contact/Catalogue enquiry submissions.
- Cart currently deduplicates by SKU, though SKU uniqueness is only per Brand. Recommend line key = public Product ID and same-product merge by ID, then verify SKU; this requires UI/storage migration decision. `lineKey` may remain a display snapshot, not identity.
- Product Enquiry / Cart Enquiry remain disabled until API is integrated and owner separately enables them. This read-only product contract does not activate them.

## 9. TypeScript DTO outline and versioning

```ts
type ProductListDto = {
  id: string; slug: string; sku: string; name: string;
  brand: { id: string; name: string };
  priceAed: string | null; currency: 'AED';
  categoryIds: string[];
  primaryCategory: { id: string; slug: string; name: string; path: string };
  canonicalPath: string;
  cardImage: { url: string; alt: string } | null;
  cardSpecifications: ProductSpecificationDto[];
  cardSpecificationsText: string;
};
type ProductDetailDto = ProductListDto & {
  series: { id: string; name: string } | null;
  descriptionHtml: string | null;
  seo: { title: string; description: string | null; ogImage: string | null; robots: string };
  images: ProductImageDto[];
  attributes: ProductAttributeDto[];
};
type ProductSpecificationDto = { code: string; label: string; value: string; displayText: string };
```

`/api/v1` is the route version boundary. This initial DTO should be additive within v1; breaking field/semantic changes need a reviewed contract change and consumer update. Don't add a separate version property unless API governance chooses one. `priceAed` and numeric attribute values stay decimal strings. Nullable fields remain explicit `null` for stable API types; category list may return empty. Prefer OpenAPI or Laravel contract tests once implementation stage is approved.

## 10. DB/query considerations

- List query should filter published products and category associations in SQL before pagination, eager-load primaryCategory/categories/brand/main image/media/card attributes and values/options.
- Details should eager-load complete gallery and displayed attributes, avoid N+1 per card. Do not eager-load unused Supplier, all options, history aliases or raw media original metadata.
- Existing `products(status,updated_at,id)` index does not directly serve `status + category + sort`; pivots have useful category index. Attribute facet aggregation can be expensive across typed value/selection tables. Capture representative EXPLAIN/query counts on test fixtures before proposing migration/index additions; no index is approved here.
- Confirm collation/slug comparisons remain consistent with binary unique columns. Avoid casting decimal values to PHP float during SQL ordering or JSON serialization.
