# BE-08.5.1 — Read-only аудит и проектирование Product API Contract

**Проект:** Pots & Planters 2.0  
**Статус:** ТЗ для Codex; только аудит и проектирование, без реализации.  
**Следующий этап после принятого владельцем BE-08.4:** BE-08.5.1.

## 1. Цель

На основании **актуального репозитория**, а не исторических описаний, зафиксировать контракт между Laravel Product Domain и существующим Next.js 16 каталогом. Подготовить проверяемую спецификацию API/DTO, карту интеграции, решения и открытые вопросы, а также план BE-08.5.2–BE-08.5.5. Никакой реализации на этом этапе.

## 2. Обязательные исходные документы и порядок

1. Сначала read-only: `git status --short`, `AGENTS.md` (включая вложенные), `docs/common/PROJECT_CONTEXT.md`, `docs/common/ROADMAP.md`, `docs/backend/BE-08_ARCHITECTURE_DECISIONS.md`, отчёты BE-08.4.1–BE-08.4.7.4, если существуют.
2. Проверить фактический код моделей, миграций, scopes, API routes/controllers/resources, Filament ProductResource, media processing, SEO URL registry, categories, filters, enquiry и cart.
3. Проверить существующие Next.js компоненты ProductCard/ProductCardDetails, каталог и категории, фильтры, product detail, cart, enquiry, SEO metadata, SSR data-fetch utilities, fixtures и тесты. Установить фактические пути поиском, не предполагать расположение.
4. Сверить документацию с кодом; каждое противоречие отметить с точными путями/символами. Учесть незакоммиченные ручные изменения; **не трогать их**.
5. Отметить в документации (только в итоговом предложении изменений, не редактировать файлы), что владелец 2026-11-09 подтвердил ручную приёмку BE-08.4.7.4, следовательно BE-08.4 принят локально; production deployment/activation не подтверждены.

## 3. Жёсткие ограничения

- **Только read-only аудит и проектирование.** Не менять код, тесты, конфигурацию, схемы БД, `PROJECT_CONTEXT.md` и `ROADMAP.md`; не устанавливать пакеты; не запускать миграции, сидеры, import, jobs, HTTP writes или production operations. Допустимо создать только отчёт/контракт/план в `docs/backend/` по согласованной структуре; если в репозитории запрещено создавать файлы без отдельного разрешения — вывести документы в ответе и запросить разрешение.
- Стек: Next.js 16, React 19, TypeScript, Mantine 9, Laravel 13, Filament 5, MariaDB, Redis/Horizon.
- Не менять публичный дизайн, маршруты, SEO и поведение. Не предлагать ProductVariant. Не создавать mock fallback при ошибках API.
- Публичные контракты `/api/v1`; не раскрывать приватные пути оригиналов, внутренние идентификаторы хранения или неопубликованные товары.
- Никаких 301 в BE-08.5: исторический mapping и реальные Nginx 301 — BE-09 после наполнения каталога. Автогенерацию SEO не проектировать как утверждённую.
- Учитывать, что Product Enquiry и Cart Enquiry ещё не активированы для реальных Product ID/SKU.

## 4. Что исследовать и описать

### A. Инвентаризация данных

Составить матрицу: поле Laravel/тип/nullable/правила публикации → поле публичного DTO → потребители Next.js → преобразование/ограничения. Включить: immutable Product ID, SKU, Brand/Supplier/Product Type/Series, status, AED `DECIMAL(15,4)` nullable (JSON string, без потери точности), category associations/Primary Category, global slug, canonical URL, description HTML (санитизированное), SEO overrides, OG image, media ready/full/card/thumb, gallery ALT/order/main, typed attribute values, applicable optional/required assignments, Card Display order/Short Label/unit, category filter configuration. Отдельно выяснить политику inactive Brand/Supplier, архивных товаров и устаревших options по фактическому коду; спорные вопросы не решать молча.

### B. Текущий frontend и зависимости

Для каждого экрана/компонента: маршрут, источник данных сегодня (API/mock/fixture), требования к DTO, loading/empty/404/503, SEO SSR, кеширование, сортировка/пагинация, изображения, actions. Отдельно разобрать ProductCard и ProductCardDetails, форматирование specs, category listing/filter state, PDP, cart snapshot и enquiry payload; выявить места, где Product ID vs SKU vs slug используются как ключи.

### C. Предлагаемый API контракт

Предложить минимальный согласованный набор read-only endpoints для списка товаров и деталей, а также данных фильтров/категорий **только если существующий API их не покрывает**. Для каждого: метод/путь, query params, допустимые значения, сортировка по умолчанию, pagination (включая лимиты), status codes, error shape, sample JSON **с явно синтетическими значениями, не выдаваемыми за реальные товары**, способ построения canonical и правила 404/empty/503. Проверить, что slug lookup учитывает Primary Category и не реализует преждевременные HTTP redirects. Описать contract versioning и DTO TypeScript, включая decimal strings и nullable values. Указать query/DB индексы и N+1 риски без преждевременной оптимизации.

### D. Фильтрация и отображение

Описать семантику фильтров: глобальный `Attribute.is_filterable`, конфигурация Category ↔ Attribute, доступность атрибута у Product Type, typed values, boolean/number/select/multiselect, inactive options, empty values, count/facets и URL query params. Разделить реально существующее поведение и предлагаемые правила; все неопределённости вынести на утверждение.

Форматирование Card Display должно соответствовать сохранённым ID/order, Short Label и numeric unit. Выяснить, отдавать ли API структурированные specs и/или готовую строку: предложить один авторитетный источник форматирования и доказать совместимость с frontend; не копировать независимую бизнес-логику без причины.

### E. SEO, медиа и отказоустойчивость

Схематично описать SSR/metadata/canonical/OG, неизвестные и unpublished товары, категории, no-store/кеширование по существующим правилам, pending/failed media, fallback **только на честный placeholder для отсутствующего изображения**, а не mock product. Отдельно указать возможные утечки private media paths. Определить поведение API errors и отличие empty collection от недоступного backend.

### F. Cart/Enquiry и совместимость

Показать контракт для Product ID + SKU + snapshot цены/наименования/характеристик и серверной перепроверки, не меняя уже существующие пользовательские сценарии. Не активировать Product Enquiry/Cart Enquiry сейчас. Описать совместимость существующих URL, query-параметров, SEO и поведения корзины.

## 5. Итоговые артефакты

Создать **только документацию** (имена можно согласовать с принятой структурой):

1. `docs/backend/BE-08.5.1_AUDIT_REPORT.md`: фактическая карта backend/frontend, таблица зависимостей, расхождения с docs, риски и ссылки на код (пути + символы/строки).
2. `docs/backend/BE-08.5.1_API_CONTRACT_PROPOSAL.md`: endpoints, DTO, params, JSON examples с пометкой synthetic, статусы, правила публикации, SEO, media, filters, errors, cart/enquiry, open decisions.
3. `docs/backend/BE-08.5.1_IMPLEMENTATION_PLAN.md`: небольшие этапы BE-08.5.2–.5, для каждого цель, границы, конкретные изменения, тесты и критерии приёмки, зависимости и точки остановки. Включить предлагаемые изменения в PROJECT_CONTEXT/ROADMAP **как текст для будущего обновления**, но не менять эти файлы на этапе аудита.

Если важное архитектурное решение неоднозначно — предложить варианты, плюсы/минусы и рекомендуемый вариант, но пометить **Requires owner approval**, не выдавать его за утверждённый.

## 6. Критерии приёмки

- Ни одного изменения production code, миграций, тестов, env, compose, frontend или существующих ручных правок.
- Документированы все потребители товаров, все существующие API и точная граница mock/real data.
- Контракт достаточен для независимого начала BE-08.5.2 после утверждения; API не требует переделки публичного дизайна и не предполагает ProductVariant.
- Правила фильтрации, Price on enquiry, decimal precision, media readiness, canonical, URL history и errors рассмотрены явно.
- Отдельно перечислены нерешённые вопросы владельцу и необходимые интеграционные проверки.
- Отчёт включает `git status --short` до/после и список read-only команд; если выполнялись тесты, указать точные результаты, но запускать тесты необязательно для проектирования.
- **Остановиться после отчёта.** Не начинать BE-08.5.2, не вносить код без согласования API-контракта.
