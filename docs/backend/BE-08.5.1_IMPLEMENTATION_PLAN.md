## BE-08.5.2 — Laravel Product API

### Цель

Реализовать утверждённые read-only `GET /api/v1/products` и `GET /api/v1/products/{slug}` без миграций, импорта, ProductVariant и HTTP redirects.

### Границы и изменения

- В `backend/routes/api.php` добавить только согласованные GET routes.
- Ввести typed Laravel DTO/Data classes/resources для list, detail, category, card specs, gallery/attributes/facets согласно утверждённому контракту. Не отдавать Eloquent-модели напрямую.
- Выделить public Product query/scope/use case: опубликованность, published primary category и категория-ассоциация, стабильная сортировка и pagination. Применить решение по Brand/Supplier/definitions status.
- Slug endpoint использует global slug, отдаёт canonical path через `ProductUrlResolver`; не перенаправляет alias/secondary path и не меняет alias registry. Скрытые/неопубликованные записи одинаково отвечают 404.
- Список eager-loads ровно нужные relations: primary/category/brand, ready main image, card-ordered attributes/typed values/selections/options. Detail дополнительно gallery, description, SEO/OG и применимые attributes. Проверить отсутствие N+1 запросов с query-count/fixture evidence.
- Серверная валидация query parameters и normalized JSON errors (если утверждено); существующие APIs и ошибки не менять побочно.
- `Cache-Control: no-store` для согласованного поведения первой версии.
- Числа выдавать string без float; UUID использовать для public IDs. Только ready media URL; не сериализовать private disk/path/internal numeric keys.
- Не добавлять DB indexes до EXPLAIN и evidence; миграция, если доказана необходимость, отдельное owner review.

### Проверки

- Feature tests: опубликованный draft/archive/unknown slug; inactive Brand/Supplier/definitions согласно принятой политике; published category/primary; secondary association; SKU/public_id; nullable и точный `DECIMAL(15,4)`; sanitized HTML; SEO override/fallback; OG override/main fallback; gallery ready/pending/failed/missing variant и ALT/order/main; attributes всех пяти типов, false/zero/decimals, optional selection, inactive option policy; URL canonical/alias/secondary без redirect; list category and pagination/sort/errors.
- DTO contract tests подтверждают JSON shape, explicit null, отсутствия private storage data и DB PK, decimal JSON strings.
- Проверить Laravel suite по `AGENTS.md` только через Compose backend и `potsandplanters_test`. Не запускать migrate/seed, если тестовому окружению это не нужно; никаких тестов против обычной/dev/production БД.
- `php artisan route:list --path=api/v1`, Pint затронутых PHP-файлов, `git diff --check`; зафиксировать exact command/results.

### Приёмка и зависимость

API доступен только через read-only endpoints и выдаёт исключительно разрешённые публичные товары; empty list отличается от 404/503; ни одна ошибка не раскрывает SQL или внутренний path. Backend contract report принят до BE-08.5.3.

## BE-08.5.3 — Next.js listing/detail integration

### Цель

Подключить существующий UI к авторитетному API при сохранении страниц и дизайна. Удаление fixture imports ограничить затронутыми public Product modules; данные остальных модулей (например Solutions) не мигрировать без scope.

### Границы и изменения

- Заменить Product часть `frontend/src/lib/catalog/repository.ts` на server adapter над `serverApiFetch`; сделать typed Product API DTO→UI mapper для decimal strings, nullable values, category IDs, images/specifications.
- `CatalogPage` получает API category products и использует имеющиеся `CatalogListing`, `CatalogCard`, `ProductCardDetails`; карточку, галерею, actions, PDP sections и стили визуально не перерабатывать.
- Product detail data fetch должен использовать одну DTO на `generateMetadata` и страницу или явно контролируемое dedupe; обработать 404 через `notFound()`, 503 через error boundary/ошибку, отсутствие товаров — текущим явным empty UI.
- Предусмотреть Server API errors без скрытого mock fallback. Исправить нынешние места, где UI зависит от fixture Product: detail/recommendations и `resolveEnquiryLine` только в границах, утверждённых для данного этапа. Не активировать формы.
- SEO metadata брать из DTO: canonicalPath, title, explicit description, OG. Текущий `robots:index:false` сохранить до утверждения изменения; redirects/mismatched category оставить вне scope BE-08.5.3, если отдельно не утверждено безопасное behavior. Legacy `/product/[slug]` и `/shop/[category]/[slug]` остаются.
- Подключить `FeaturedProductsSlider` из home.mock только если утверждён источник `featured`/правило выбора; Product model сейчас не имеет featured. В ином случае явно оставить home consumer как открытый вопрос, не выдумывать флаг.
- Search mock Product source включать только после аудита его кода на этой фазе.

### Проверки

- Frontend `npm run typecheck`, `test:catalog`, `test:product`, `test:enquiry`, `test:forms` через Compose frontend по AGENTS (из корня).
- SSR smoke для shop, категории, товара, unknown slug, empty list, API 503; проверить `no-store`, canonical/metadata, ссылки из secondary category, ready image/placeholder, AED exact string/Price on enquiry.
- Проверить mock Product imports отсутствуют из включённых экранов/runtime path. Runtime API outage не должен отображать fixtures.
- Production-mode build через Compose; `git diff --check`. Не проверять/менять production окружение.

### Приёмка и зависимость

Публичные экраны показывают API данные и не меняют дизайн/маршруты; data failure явно сообщает ошибку, empty result явно показывает отсутствие; page metadata и image contract совпадают с API. После отчёта остановиться для проверки страницы владельцем.

## BE-08.5.4 — Category filters and facets

### Цель

Заменить четыре fixture-only facets (`material/color/size/usage`) на категорийную конфигурацию Category ↔ Attribute и реальную фильтрацию только по утверждённой семантике.

### Границы и изменения

- Backend: реализовать compatible filter eligibility из CategoryFilterConfiguration плюс global `is_filterable`, Attribute/ProductType availability, filter value resolution и facets/counts только для published products category scope (включая secondary category).
- Filter/query parsing, invalid keys/options, inactive attributes/options, `false`, zero, null/empty values, single/multi/range и AND/OR должны соответствовать решению владельца; не решать на усмотрение реализации.
- Фильтрацию выполнять в SQL до pagination. Оценить cardinality, generated SQL, EXPLAIN и relation query counts на тестовых данных; не запускать длительный load test и не добавлять index без подтверждения.
- Frontend: перенести facet metadata, URL parser/serializer и filter state на динамические codes; сохранить существующие category paths и shareable searchParams. Сохранить понятное empty result, loading/error and active-filter removal. UI layout не менять без отдельного запроса.
- Legacy query mapping (`material`, `color`, `size`, `usage`) — только если утверждённый контракт требует его; иначе выбрать совместимую стратегию URL миграции с владельцем до изменения ссылок.

### Проверки

- Backend feature/contract tests: конфигурации category independent/order; eligibility; products mixed Product Types; secondary category; typed comparisons; option labels/keys; no-value exclusion; zero/false; OR within multi options, AND across attributes; counts per accepted model; empty facet exclusion; invalid filter 422; pagination after filtering.
- Frontend tests: parse/serialize round-trip, repeated values, unknown stale params, pagination reset if filter changes, browser back/forward, no-filter, zero results, API failure; preserve canonical path/query behavior.
- Run all required frontend catalog tests and backend targeted/full suites through specified Compose services/DB; API/SSR smoke for category-specific filters; typecheck and production build; `git diff --check`.

### Приёмка и зависимость

Фильтры определяются API и сохраняются в URL, counts/empty behavior документированы и воспроизводимы; stale query does not crash/return unrelated data. Отчёт и owner check precede cart changes.

## BE-08.5.5 — Cart snapshot reconciliation and enquiry readiness

### Цель

Подготовить текущий enquiry cart к реальным Product identity, не менять контактные/catalogue enquiry сценарии и не активировать Product/Cart Enquiry без отдельного разрешения.

### Границы и изменения

- Сперва проверить текущий BE-07 `StoreEnquiryRequest`, `EnquirySubmission`, `EnquiryItem` persistence and client `EnquirySubmissionPayload` ещё раз read-only на старте этапа; проверить API compatibility и idempotency.
- Согласовать versioned payload: Product `public_id` + submitted SKU + quantity + client snapshot display values + informational price string/null. Laravel сверяет public ID+SKU и publication at submission; authoritative server snapshot хранит current name, brand/SKU, selected attributes and exact AED price. Client price/name/attributes не являются authority.
- Выбрать unavailable-item outcome (предложение: reject whole request с 404/422 и понятным item-specific error; не удалять молча) и snapshot immutability/retention. Не переписывать уже сохранённые enquiry snapshots.
- Пересмотреть localStorage schema/dedupe: текущий key хранит `productId, sku, quantity`, merge по SKU конфликтует с SKU uniqueness only per Brand. Предложение — line identity по public Product ID, отдельный storage version migration/invalid-item recovery; не менять пока не согласовано.
- Включить API-backed cart line hydration для имени, ссылки, images/specification/price; outage должен сохранять cart keys и показывать unavailable state, не подменять mock.
- Existing `/api/v1/enquiries` POST остается enabled только для своих текущих accepted enquiry categories. Product Enquiry and Cart Enquiry feature flags остаются false. Их запуск — отдельный manual acceptance + explicit activation task after privacy/legal prerequisites.

### Проверки

- Backend tests: valid live ID+SKU, mismatch, duplicate/archived/unpublished product, concurrent status change policy, exact decimal snapshots, sanitized attribute snapshot, line quantity, request idempotency/replay/conflict, DB outage, no client-side tampering, no notification payload leaks.
- Frontend tests: storage migration, different Brand same SKU, same Product merges, stale ID/SKU, deleted/archived Product, API 503, no product mock import, exact price rendering, quantity validation, existing Contact/Catalogue enquiry regression.
- Compose backend tests only against `potsandplanters_test`; frontend suites/typecheck/build by AGENTS. Existing Contact/Catalogue API smoke and Product/Cart enquiry disabled flag verification. Manual review of cart reconciliation and explicit final owner activation gate.

### Приёмка и зависимость

Authoritative snapshot created server-side without changing existing enquiry flows; idempotency and no duplicate delivery hold. Product/Cart form activation remains disabled and is not considered complete by passing tests; task ends at review-ready readiness unless owner separately authorizes activation.
