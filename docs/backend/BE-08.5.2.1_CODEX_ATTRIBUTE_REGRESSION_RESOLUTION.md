# BE-08.5.2.1 — Разбор конфликта ProductAttributeValueManager и регрессионного теста

**Проект:** Pots & Planters 2.0  
**Статус:** ТЗ для Codex; выполнение не начато  
**Цель:** выяснить причину единственного failing test после BE-08.5.2, согласовать фактическое бизнес-поведение с действующими правилами и добиться зелёного полного backend suite без потери ручных изменений.

## 1. Исходные факты

Отчёт `docs/backend/BE-08.5.2_IMPLEMENTATION_REPORT.md` фиксирует:
- Product Read API реализован; профильные тесты `ProductReadApiTest`: 4 passed / 44 assertions.
- Полный backend suite: **187 passed, 1 failed / 1334 assertions**.
- Падает `ProductAttributeValuesTest::test_unselecting_a_filled_attribute_is_blocked`.
- В `backend/app/Services/ProductAttributeValueManager.php` есть незакоммиченная ручная правка, удаляющая прежнюю блокировку снятия заполненного Attribute; BE-08.5.2 её не изменял.
- Предыдущая договорённость проекта: заполненный optional Attribute нельзя снять без явного очищения значения и отдельного сохранения. Но актуальная ручная правка может отражать осознанное изменение UX — нельзя автоматически считать её ошибкой.

**Важное:** отчёт не содержит самого diff и воспроизводимого стека failing assertion. Выводы о намерении ручной правки делать только после чтения реального репозитория. Не использовать историю переписки вместо фактического кода.

## 2. Этап A — read-only аудит

**Цель:** установить точную семантику и минимальный радиус влияния.

1. Прочитать `AGENTS.md`, `docs/common/PROJECT_CONTEXT.md`, `docs/common/ROADMAP.md`, `docs/backend/BE-08_ARCHITECTURE_DECISIONS.md`, отчёт BE-08.5.2 и связанные инструкции/тесты. Если пути изменились — найти актуальные, не угадывать.
2. Зафиксировать `git status --short`, `git diff` для `ProductAttributeValueManager.php`, `ProductAttributeValuesTest.php`, `ProductResource.php`, `EditProduct.php` и иных релевантных файлов. **Не сбрасывать, не stash, не checkout и не перезаписывать ручные изменения.**
3. Проследить вызовы менеджера из Filament Create/Edit, валидацию selected optional attributes, сохранение typed values и влияние на card display attributes, preview и Product API.
4. Разобрать failing test по шагам: setup, action, expected vs actual, точное assertion message, какие значения и assignments реально остаются/удаляются.
5. Проверить сценарии: (a) пустой optional attribute снимается; (b) заполненный снимается; (c) значение очищается и затем атрибут снимается; (d) required attribute; (e) смена Product Type; (f) последующее повторное добавление; (g) сохранение и повторное открытие Edit; (h) нет ли orphan values/неожиданной потери данных; (i) влияние на card display/публичный DTO.
6. Указать расхождение между документированным правилом и текущим UX. Не интерпретировать зелёный тест как доказательство корректного бизнес-правила.

**Результат A:** краткая таблица «сценарий → текущее поведение → ожидаемое по документации → риск» и вывод, что именно нужно исправить.

## 3. Этап B — выбор минимального решения

Приоритет — сохранить осознанные ручные изменения и целостность данных.

- **Если** ручная правка только меняет защиту UI, а снятие заполненного атрибута безопасно и явно согласовано в актуальной документации/коде: предложить обновление теста под новый контракт, с тестом на фактическое сохранение/удаление значения и повторное открытие Edit.
- **Если** снятие заполненного атрибута приводит к неявной потере значения или нарушает ранее принятое правило: предложить минимальную защиту/валидацию, совместимую с ручными правками. Не откатывать файл целиком.
- **Если** намерение владельца из актуального кода и документов нельзя установить однозначно: **остановиться и запросить решение владельца**, показав конкретный diff, два варианта поведения и последствия. Не менять тест или сервис до решения.
- Не менять тест лишь ради PASS, не добавлять `skip`, `todo`, `markTestIncomplete`, `withoutExceptionHandling` для маскировки проблемы и не ослаблять assertions без обоснования.

**Граница:** менять только необходимые backend service/test/Filament файлы в пределах найденного дефекта. Любые изменения Product API contract, frontend, DB schema, public routes, SEO, миграций или production запрещены.
