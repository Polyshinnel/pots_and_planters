# BE-08.5.3 — Codex: Next.js Product Catalogue Integration

**Статус:** техническое задание, реализация не начата. **Язык задания:** русский; публичный UI/content — английский.

## 0. Основание и границы

BE-08.4 принят владельцем локально. BE-08.5.1 — read-only аудит. BE-08.5.2 Laravel Product Read API реализован и после BE-08.5.2.1 регрессии принят для перехода к frontend: полный backend suite 188 passed / 1336 assertions; Product Attribute + Product API 16 passed / 113 assertions. Известный Pint issue `ProductResource.php` (array_indentation/method_chain в ручной Tabs-разметке) не исправлять в этой задаче. Production deployment не подтверждён.

**Авторитетные входы в текущем репозитории:** `AGENTS.md`, `docs/common/PROJECT_CONTEXT.md`, `docs/common/ROADMAP.md`, `docs/backend/BE-08.5_FINAL_PRODUCT_API_CONTRACT.md`, `docs/backend/BE-08.5.2_IMPLEMENTATION_REPORT.md`, `docs/backend/BE-08.5.2.1_ATTRIBUTE_REGRESSION_REPORT.md`, фактический код Laravel/Next.js. Если эти документы и код расходятся — зафиксировать и остановиться на существенных противоречиях. Исторические handoff-копии не считать текущим состоянием репозитория.

**Цель:** подключить существующие публичные страницы каталога и товара к авторитетному `GET /api/v1/products` и `GET /api/v1/products/{slug}` без изменения публичного дизайна, маршрутов и включения Product/Cart Enquiry. Не показывать mock Product при ошибках API.

**Не входит:** реализация/изменение Laravel Product API, миграции, Filament, импорты, SEO-index activation, HTTP 301, изменение Nginx, редизайн, полноценная динамическая фильтрация/facets (BE-08.5.4), cart storage migration/server-authoritative snapshots (BE-08.5.5), Solutions integration, production deploy.

## 2. Этап B — typed server API adapter и mapper

1. Реализовать минимальный typed server-only adapter через существующий `serverApiFetch`/`API_INTERNAL_URL`, не дублируя общие API abstractions и не добавляя зависимостей.
2. Типизировать фактические DTO: `id` = Product public UUID; `sku` отдельно; `priceAed: string|null` (никаких JS float для исходного точного значения); `currency: AED`; `primaryCategory`, `categoryIds`, `canonicalPath`, nullable `cardImage`, ordered card specs, sanitized `descriptionHtml`, SEO, gallery, typed attributes.
3. Дать отдельный DTO→existing UI mapper только где нужно. Не менять глобальную модель Product/все компоненты ради удобства; при конфликте форматов показать узкий adapter. Отсутствующая цена — `Price on enquiry`, а не 0. Никаких вымышленных характеристик, товаров, цен, related/featured данных.
4. Обработать 200 empty отдельно от 404 и 503. Неподдерживаемые/некорректные query параметры не игнорировать молча; 422 должен давать предсказуемое поведение. На API outage показывать честный error state/error boundary, **никогда mock fallback**.
5. Не передавать в клиент private storage keys, backend numeric PK или internal paths; использовать только готовые URL изображений из DTO, честный существующий placeholder при `null`.

**Checkpoint B:** typed tests mapper/adapter, включая decimal string/null, 404/422/503, empty и отсутствующие изображения. Не начинать UI без проверки контракта.

## 3. Этап C — существующие публичные страницы и SEO

1. `/shop` и `/shop/[category]`: читать Product list из API, категории по уже существующему Categories API. Сохранить текущие компоненты, grid, карточки, ссылки, pagination и дизайн. Для secondary category ссылка на товар всегда `canonicalPath` из API.
2. `/shop/[category]/[slug]`: Product detail по глобальному slug, рендер из единой DTO. `generateMetadata` и страница должны использовать согласованный fetch/deduplication подход, без противоречивых источников. Сохранить `robots: noindex,follow`, ручные title/meta/OG и canonical из DTO. Не генерировать SEO copy и не включать index.
3. Сохранить существующие `/product/[slug]` и `/shop/[category]/[slug]`, включая текущее поведение Next redirect при mismatch, **без введения новых redirects или изменения кодов**. Учитывать, что текущий `permanentRedirect` — Next 308, а BE-09 будет решать целевые HTTP 301. Если фактическое поведение невозможно сохранить с новым DTO, остановиться на owner decision.
4. Не нарушить карточку, галерею, sanitized description, actions, контакты, SEO, OG, ALT и пустые состояния. Не менять CSS/layout/визуальную структуру.
5. Product recommendations/related, home featured и search: по inventory этапа A не оставлять mock Product на **включённых** публичных страницах под видом реальных данных. Если авторитетного backend источника для `featured`/related/search нет, не изобретать сортировку, флаг или подборку. Предложить минимальное безопасное поведение (например, явное отсутствие необязательного блока) только после фиксации в отчёте и при необходимости отдельного согласования владельца; не удалять важный публичный блок без разрешения.
6. Cart `/cart` и `resolveEnquiryLine`: Product/Cart Enquiry остаются выключены. Не внедрять новый localStorage schema, не менять submission payload или серверные snapshots в BE-08.5.3. При невозможности заменить fixture-based hydration без полноценной BE-08.5.5 — обозначить dependency и не маскировать её mock. Если включённая публичная корзина зависит от fixture Product, остановиться с предложением безопасной промежуточной интеграции для owner approval.

**Checkpoint C:** страничные/SSR тесты для shop, категории, detail, unknown slug, category mismatch, secondary category, empty, API outage; metadata canonical/OG/robots; никаких fixture Product на включённых runtime paths.

## 4. Этап D — URL state и граница BE-08.5.4

1. **Не реализовывать полноценные category dynamic facets** в этом этапе: это BE-08.5.4. Но нельзя оставлять работающий визуальный фильтр, который фильтрует локальные mock Product или выдаёт неподтверждённые результаты.
2. Для текущих URL `?sort=...&page=...` использовать реальные backend sorting/pagination (`newest` по умолчанию) с учётом текущего UX. При несовместимости UI сортировок — явный mapper и тесты; не подменять `featured` фиктивным.
3. `filter[code]` и legacy keys: сначала проверить backend contract. Если backend возвращает 422 для legacy из-за пустой конфигурации, не утверждать, что совместимость реализована. Не добавлять произвольных `material/color/size/usage` mappings. Зафиксировать blocker и отнести полноценную конфигурацию/URL compatibility к BE-08.5.4. Не игнорировать параметры молча и не показывать ошибочно нефильтрованную выдачу как успешную фильтрацию.
4. Любое временное UI-поведение, скрытие/отключение фильтров или изменение URL behavior, влияющее на пользователей, согласовать до изменения. Если без такого решения нельзя безопасно завершить этап, остановиться.
