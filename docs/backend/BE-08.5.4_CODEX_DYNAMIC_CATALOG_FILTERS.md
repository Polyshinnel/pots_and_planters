## Этап A — read-only контрактный аудит (обязательный checkpoint)

**Цель:** сопоставить фактический Product Read API, facets и существующий интерфейс фильтров.

1. Проверить реальные endpoint, query encoding `filter[code]`, DTO `facets`, допустимые типы атрибутов, option codes/values, counts, category scoping, пагинацию и сортировку. Изучить backend tests, не предполагать форму DTO.
2. Проверить доступность фильтров для типов select/multiselect/boolean/number/text и возможности UI; определить, какие типы действительно поддерживает контракт. Не придумывать ranges, options или counts.
3. Проверить правило: OR внутри одного атрибута, AND между атрибутами; включительные числовые границы, точный текст, значения `false` и `0`; facet counts после всех активных фильтров, показывать только options с count > 0. Уточнить поведение уже выбранной опции с count=0, чтобы пользователь мог её снять.
4. Проверить текущие URL `?material`, `?color`, `?size`, `?usage`, `?sort`, `?page`, `filter[code]`, `sort=featured` и реальные атрибуты/категории. Legacy mapping разрешён только при доказанном однозначном соответствии в конкретной категории; неизвестные/неоднозначные/конфликтующие параметры нельзя игнорировать.
5. Проверить, какие текущие frontend-компоненты можно переиспользовать без изменения дизайна, включая mobile и доступность.

**Checkpoint:** если фактический API не поддерживает необходимые запросы/DTO, или нельзя безопасно определить encoding/legacy mapping, остановиться и предоставить минимальные варианты исправления. Не менять Laravel API/схему/Filament без согласования. При достаточном контракте продолжить B–D.

## Этап B — Next.js integration

**Цель:** реальные фильтры через Laravel Product API.

- Подключить отображение facets из реального API для `/shop` и `/shop/[category]`; сохранять категорийный контекст. Никаких статических/mock списков или выдуманных чисел.
- Реализовать URL-driven состояние: поддерживаемые `filter[code]`, корректное кодирование повторяющихся значений, сортировка и пагинация. Перезагрузка/прямая ссылка/back-forward должны воспроизводить состояние.
- При выборе/снятии фильтра сбрасывать `page` в 1, сохранять остальные валидные параметры. Clear filters очищает только фильтры, не теряет сортировку; определить поведение page явно.
- Сохранить утверждённые API sort `newest`, `name-asc`, `name-desc`, `price-asc`, `price-desc`; сохранить ранний HTTP 307 `featured → newest`.
- Не показывать неподдерживаемые типы как работающие. Для неизвестных, конфликтующих и неоднозначных legacy query — явное сообщение об ошибке/недоступности с возможностью исправить URL; не показывать нефильтрованный результат как будто фильтр применён. Существующие ссылки не ломать молча.
- Учитывать 0 и false как реальные значения, NULL цены — в конце сортировки согласно backend.
- API 422 показывать как ошибку валидации фильтра, 503 как недоступность API, пустой 200 как пустой результат. Без mock fallback и без подмены ошибок нулевым количеством товаров.

## Этап C — UI и UX без редизайна

- Показывать выбранные фильтры и понятный Clear filters. Обеспечить keyboard accessibility, label и корректное состояние элементов.
- Если нет применимых facets, не рисовать фиктивные опции; не скрывать ошибку API.
- Публичные тексты на английском. Не активировать Add to Enquiry/корзину.

## Критерии приёмки

1. Фильтры `/shop` и категорий используют только авторитетные Product API facets; counts не выдумываются.
2. Сочетания фильтров и URL корректны, page/sort не ломаются, существующие ссылки обрабатываются явно.
3. Ошибки 422/503 и пустые ответы различаются; нет mock fallback.
4. Внешний дизайн, SEO, 404/307, мобильное поведение и отключение Enquiry сохранены.
5. Тесты/build/diff check пройдены, отчёт готов; ограничения документированы.
