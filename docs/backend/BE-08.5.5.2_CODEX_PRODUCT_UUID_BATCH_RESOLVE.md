# BE-08.5.5.2 — Laravel Product UUID Batch Resolve

**Статус:** утверждённое ТЗ; реализация не начата. **Язык:** русский. Публичные API-тексты — английский.

## Контекст и цель

Владелец утвердил контракт BE-08.5.5.1: идентичность позиции Product Enquiry / Cart Enquiry — `products.public_id` (UUID), не SKU. SKU — только отображаемый атрибут, уникальный в рамках Brand. Существующие Product Read API разрешают detail по slug и пагинируемый список, но не UUID batch lookup.

Добавить **только** `POST /api/v1/products/resolve`, возвращающий актуальное публичное представление товаров по UUID в одном пакетном запросе. Endpoint будет использован будущей корзиной, но сейчас Product/Cart Enquiry остаются выключенными.

## Этап B — API contract и реализация

**Request:** `POST /api/v1/products/resolve`, JSON `{ "ids": ["<UUID>", "..."] }`.

- `ids` — обязательный массив из **1..100** уникальных валидных UUID. Дубликаты, пустой массив, не-массив, невалидный UUID, более 100 ID, неизвестные поля — **422** в существующем API error envelope `{error:{code,message,requestId,errors?}}`.
- Результат — `{ "data": [ ... ] }`, **ровно один элемент на каждый входной UUID**, в исходном порядке.
- Для публичного товара: `{ "id": "<UUID>", "status": "available", "product": { ... } }`. `product` переиспользует существующий безопасный Product Read DTO (или минимальный явно документированный его subset), с `id` UUID, `sku`, `name`, Brand, nullable decimal-string AED price, canonical path, подготовленным публичным изображением при наличии. Не вводить новые выдуманные поля/цены; не раскрывать внутренние поля.
- Для любого отсутствующего или непубличного UUID: `{ "id": "<UUID>", "status": "unavailable" }`. Не возвращать SKU, Brand, название, причину, существование записи или иной приватный контент. Одинаковый результат для unknown/draft/archived/inactive Supplier/unpublished primary Category.
- `available` = **публичная видимость**, а не физический stock. Использовать существующий approved Product visibility scope; не дублировать правила вручную с риском расхождения.
- Только batch DB lookup; отсутствие N+1 для 100 позиций (включая связи DTO). Сохранить порядок input в PHP без отдельных SQL-запросов на каждый UUID.
- `Cache-Control: no-store` и текущая конвенция ошибок/Request ID; инфраструктурная ошибка — **503**, не 200/пустой список и не mock fallback. Проверить существующий обработчик, не создавать альтернативный envelope.
- POST endpoint read-only: не пишет данные, не отправляет события и не меняет Product/Enquiry state.
- Не использовать SKU/slug как fallback, не сопоставлять по ним UUID. Два товара разных Brand с одинаковым SKU должны возвращаться как разные UUID.
- Соблюсти текущие ограничения безопасности публичного API; оценить/использовать существующий rate limiting для POST resolve, не ослабляя его.

**Важное правило реализации:** сначала установить точный состав уже существующего публичного DTO. Если невозможно переиспользовать его без выдачи лишних данных, зафиксировать безопасный subset и покрыть его тестами; не изобретать другой несовместимый формат.

## Этап C — тесты и проверки

Добавить focused Laravel feature/contract tests (в существующий `ProductReadApiTest.php` или отдельный профильный файл):

1. Один UUID, несколько UUID, 100 UUID, сохранение порядка и соответствие количества элементов.
2. 0/101, дубликаты, malformed UUID, wrong JSON shape, extra fields → 422.
3. Unknown UUID и все непубличные состояния → одинаковый `unavailable` без утечки полей.
4. Публичный DTO, nullable price и точная десятичная строка; не конвертировать в float.
5. Два Product с одинаковым SKU у разных Brand остаются разными позициями.
6. Visibility parity с `GET /api/v1/products`, no-store, error envelope, DB unavailable → 503.
7. Отсутствие N+1 при 100 UUID; не привязывать тест к хрупкому абсолютному числу SQL-запросов, если оно зависит от framework bootstrap.
8. Регрессии существующих `/api/v1/products` и `/api/v1/products/{slug}`, включая route precedence.
