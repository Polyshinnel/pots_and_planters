## Реализованный контракт

`POST /api/v1/products/resolve` принимает JSON `{ "ids": ["<UUID>", ...] }`. Принимается список от 1 до 100 уникальных UUID без неизвестных полей. Ошибка входа возвращается как HTTP 422 в используемом Product API envelope `error{code,message,requestId,errors}`.

Ответ содержит один элемент на каждый входной UUID, в исходном порядке. Доступный товар получает `{ "id": "<UUID>", "status": "available", "product": <ProductListData> }`. Отсутствующий или непубличный товар получает только `{ "id": "<UUID>", "status": "unavailable" }`. `available` означает публичную видимость, не складской остаток.

Resolve вызывает тот же visibility query, что list/detail: Product `published`, primary Category `published`, Supplier active. Batch `whereIn(public_id)` и eager loading существующих DTO relations выполняют один batch lookup; нет запросов по одному UUID. Цена остается десятичной строкой либо `null`. Поиск по SKU/slug не выполняется.

Ответы resolve имеют `Cache-Control: no-store`. Инфраструктурный `QueryException` логируется с request ID и возвращает HTTP 503 `service_unavailable` в стандартном error envelope. Route ограничен именованным rate limiter `products-resolve` — 60 запросов в минуту на IP. Существующие GET `/api/v1/products` и `/api/v1/products/{slug}` сохранены; статический POST маршрут объявлен до slug-маршрута.

## Примеры

```json
{
  "data": [
    { "id": "<uuid-a>", "status": "available", "product": { "id": "<uuid-a>", "sku": "PP-01", "name": "Planter", "brand": { "id": "<brand-uuid>", "name": "Brand" }, "priceAed": "125.0000", "currency": "AED", "canonicalPath": "/shop/indoor/planter" } },
    { "id": "<uuid-b>", "status": "unavailable" }
  ]
}
```

Объекты `product` в фактическом ответе содержат полный существующий `ProductListData`, как описано выше. Вторая позиция показывает сохранение порядка и одинаковую безопасную форму для unknown и private ID.
