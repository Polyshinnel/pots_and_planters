# BE-08.5.5.3 — Laravel Product/Cart Enquiry Submit & Server Snapshots

**Статус:** техническое задание для Codex; реализация не начата. Язык публичных сообщений — английский.

## Цель

Добавить безопасную серверную обработку `product_enquiry` и `cart_enquiry` через существующий `POST /api/v1/enquiries`, с UUID Product, атомарной проверкой публичной видимости и неизменяемыми серверными снимками товара. Не активировать публичную отправку до отдельного решения владельца.

## Утверждённый контракт

- `productId` — только UUID `products.public_id`; SKU, slug, name, price, brand и любые клиентские snapshots не являются идентификаторами/источником истины.
- Явный `apiVersion: 2` для Product/Cart, не менять семантику Contact/Catalogue v1. `product_enquiry`: `product: {productId, quantity}`; `cart_enquiry`: `items: [{productId, quantity}]`, от 1 до 100 позиций. Quantity — integer 1..999999. Дубли UUID — 422, неизвестные поля товарных позиций — 422. Существующие поля контакта/source и header `Idempotency-Key` сохранить согласно BE-07.
- Публичность: published Product, published primary Category, active Supplier — переиспользовать существующий Product API visibility scope. Это не проверка складских остатков.
- При неизвестном или непубличном UUID отклонять **всю** заявку (предпочтительно 422 `products_unavailable` с безопасным списком входных UUID), без частичных `enquiry_items`/outbox и без раскрытия причин непубличности.
- Внутри одной DB transaction выполнить batch загрузку и блокировку подходящих строк с детерминированным порядком UUID; повторно проверить публичность на submit, сформировать snapshots **из БД**, сохранить заявку, строки и outbox в рамках существующей идемпотентной схемы. Аудит должен проверить блокировки и конкурентные изменения Product/Category/Supplier: не заявлять абсолютную гарантию, если lock coverage её не обеспечивает; при необходимости остановиться с предложением безопасной корректировки.
- Snapshot каждой позиции: `product_public_id`, `sku`, `name`, `brand_public_id`, `brand_name`, `quantity`, `unit_price_aed` nullable DECIMAL, `currency` AED, `availability` (публичен на момент проверки), `snapshot_at`, при необходимости `canonicalPath` и краткие публичные спецификации. Рекомендуется структурированные колонки для идентичности/цены и `product_snapshot` JSON для неизменяемого полного публичного отображения. **До миграции** провести read-only аудит схемы и выбрать минимальные additive изменения; не переписывать старые строки. Цена `null` не превращается в 0; не использовать float для денежных вычислений.
- Существующий idempotency replay возвращает прежний результат без новых строк/outbox; тот же ключ с иным payload — 409. Соблюдать действующие ограничения длины ключа, retries и BE-07 error envelope; не менять общие сценарии Contact/Catalogue.
- Ошибки: валидация 422; недоступные Product — согласованный 422; idempotency conflict 409; rate limit 429; DB/service outage 503. Не выдавать успех до фактического persist. API response для успешного submit должен соответствовать существующему BE-07 контракту (`persisted`, enquiryId, notificationStatus) без ложных обещаний доставки Telegram.
- Product/Cart feature gates — отдельные от Contact/Catalogue, **выключены по умолчанию**. Разделить возможность backend тестирования контракта и публичную активацию; не допустить случайного открытия через существующий общий флаг. Если текущая архитектура требует изменения флагов/конфига, согласовать точные имена и границы, не включать их.

## Этап A — модель данных и миграция (без production исполнения)

Цель: минимально расширить `enquiry_items` для исторически достоверных snapshots. Ограничения: только additive migration, совместимость старых заявок и Filament, никаких backfill вымышленными данными. Изменения: migration/model/casts, решение nullable полей и JSON, проверка сохранения десятичных строк. Приёмка: старые строки читаются, новые snapshot корректны, rollback определён, migration исполняется только на `potsandplanters_test` после проверки DB isolation.

## Этап B — request validation и transactional submit

Цель: реализовать два новых типа без регрессии BE-07. Ограничения: один batch lookup, UUID identity, отсутствие клиентских snapshots, all-or-nothing, existing idempotency/outbox. Изменения: request/service/controller и необходимые внутренние DTO; переиспользовать Product visibility scope. Приёмка: оба типа сохраняются с правильными snapshots; 422/409/503 не создают частичных данных; replay не дублирует строки/outbox; разные Brand с одинаковым SKU не сливаются; обновлённые имя/цена на момент submit становятся snapshot.

## Этап C — Filament и Telegram/outbox

Цель: отображать сохранённые snapshots, не обращаться к текущему Product для исторических данных. Ограничения: не менять работающие Contact/Catalogue и их шаблоны без необходимости, не отправлять реальный Telegram в тестах. Изменения: минимальные корректировки отображения Enquiry items и formatter уведомлений. Приёмка: null price отображается как `Price on enquiry` либо текущий согласованный английский текст; Brand/SKU/quantity сохраняются; отсутствующий впоследствии Product не ломает просмотр старой заявки; outbox содержит только разрешённые snapshots, без внутренних данных.
