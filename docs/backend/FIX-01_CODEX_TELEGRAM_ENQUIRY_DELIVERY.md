# FIX-01 — Диагностика и исправление сбоя Telegram Enquiry Delivery

## Контекст

Pots & Planters 2.0: Laravel 13 / PHP 8.4, MariaDB, Redis/Horizon. После BE-08.3.1 профильные тесты Brand/Supplier проходят (4 tests / 42 assertions), но полный backend suite: 83 passed, 1 failed (613 assertions). Сбой воспроизводится отдельно:

`EnquiryDeliveryAndDownloadsTest::test_successful_delivery_uses_signed_string_chat_id_and_sent_rows_are_idempotent`

По отчёту Codex тест на строке 98 не находит ожидаемый HTTP payload `chat_id` / `text`. Ручная проверка Brand/Supplier владельцем пройдена. BE-08.3.1 не должен менять поведение Telegram.

## Цель

Установить фактическую причину сбоя и минимально исправить её, восстановив зелёный полный backend suite без изменения согласованной бизнес-логики заявок, безопасности и контракта Telegram.

## Этап 1 — диагностика (сначала read-only)

1. Прочитать `AGENTS.md`, `PROJECT_CONTEXT.md`, актуальный код, тест и git diff/status. Не считать, что причина известна по отчёту.
2. Воспроизвести точный тест в существующей изолированной test-среде; зафиксировать полную ошибку и фактические HTTP-запросы/состояния outbox, delivery, jobs. Не выводить токены, реальные chat IDs, телефоны и содержимое реальных заявок в отчёт.
3. Проследить цепочку: создание заявки → outbox → reservation/dispatch → job → Telegram transport → HTTP fake/прокси → обновление статуса. Проверить `chat_id` как signed string (включая отрицательные значения), `text`, idempotency, HTTP fake matching, config/cache, jobs/queues и настройки proxy.
4. Сопоставить тест с фактическим контрактом BE-07 и кодом; определить, является ли дефект production-кода, теста или test-конфигурации. Перед изменениями кратко зафиксировать root cause и минимальный план.

## Этап 2 — точечное исправление

1. Менять только файлы, непосредственно необходимые для исправления подтверждённой причины.
2. Сохранить: MariaDB outbox как источник истины, recipient snapshots, idempotency, retries, отсутствие direct fallback при настроенном Squid proxy, существующие правила ошибок и безопасность Telegram credentials.
3. Не подгонять тест под неправильное поведение. Если ошибочен тест — объяснить, какой контракт он нарушает, и поправить тест с проверкой реального ожидаемого поведения. Если ошибочен код — исправить код и добавить регрессионную проверку.
4. Не менять Product/Brand/Supplier, frontend, публичный дизайн, API-контракты и production-конфигурацию. Не добавлять зависимости, не делать рефакторинг соседних модулей.
5. Не отправлять реальные сообщения в Telegram. Использовать HTTP fake, изолированную тестовую БД и безопасные фиктивные данные. Никаких production/staging миграций или действий.

## Этап 3 — проверки

1. Повторить падавший тест отдельно, затем весь `EnquiryDeliveryAndDownloadsTest`, профильные enquiry/Telegram тесты и полный backend suite.
2. Запустить Pint `--test` для затронутых PHP-файлов и `git diff --check`.
3. При необходимости проверить несколько последовательных запусков проблемного теста для выявления зависимости от порядка/состояния.
4. Если полный suite остаётся красным, не объявлять задачу закрытой: указать точную причину и границы оставшейся проблемы.

## Отчёт и критерии приёмки

- Root cause подтверждён конкретными строками кода/теста и фактическим наблюдением.
- Исправление минимально и не ослабляет assertions, не скрывает ошибки и не изменяет Telegram transport без необходимости.
- Исходный тест и полный backend suite проходят; число тестов/assertions приведено по факту.
- Перечень изменённых файлов и выполненных команд, подтверждение отсутствия реальных Telegram отправок и production операций.
- Не переходить к BE-08.3.2. Если требуется изменить бизнес-контракт или есть риск безопасности, остановиться и запросить решение владельца.
