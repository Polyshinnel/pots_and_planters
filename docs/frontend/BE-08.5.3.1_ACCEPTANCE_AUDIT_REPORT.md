## Root cause and minimal options

### Missing nested Product: 200 instead of 404

The API contract is correct: it returns a real 404. The adapter preserves that distinction and the page calls `notFound()`. The status changes because Next has a loading/Suspense boundary at the parent category segment and can flush the response shell before the nested Product request resolves. Once the shell is sent, App Router can render its not-found UI and markers but cannot replace the already-sent HTTP 200 with 404. `notFound()` alone is therefore insufficient proof of a 404 response.

Potential minimal approaches, pending owner choice:

1. **Preserve current loading UI and add a pre-stream status gate for the nested Product route.** A request-time gate would resolve Product existence before Next begins streaming the page and allow 404 to be returned early. It risks an extra Laravel request, duplicates authorization/visibility semantics, and must define behavior for API 503 without introducing a fallback. A Next Proxy/Middleware or Nginx interception would cross the explicit boundary in this audit and should not be selected implicitly.
2. **Change the loading-boundary placement so the detail route cannot flush before its decisive Product lookup.** This is the smallest conceptual change to the cause, but moving/removing the inherited loading UI may affect category listing behavior and perceived loading design. A route-group restructuring could preserve public paths, but adds routing architecture and needs regression review.
3. **Keep streamed behavior and accept the current browser status.** Lowest implementation risk, but does not meet the expected HTTP 404 acceptance and can weaken crawler/client error semantics.

Adding a route-specific `not-found.tsx` can improve not-found presentation but cannot restore the HTTP status after the stream starts. Changing `dynamic`/cache settings alone is not evidence that streaming is disabled.

### `sort=featured`: streamed redirect

`redirect()` is called from `CatalogPage`, after the matching route and its loading boundary have started rendering. In this execution mode Next emits a streamed redirect instruction (meta refresh / RSC `NEXT_REDIRECT` with status code 307) in an HTTP 200 response.

Minimal candidate: move only this normalization into an early routing redirect rule that runs before React rendering (for `/shop` and `/shop/:category`, matching query `sort=featured`, replacing it with `sort=newest`). A Next config redirect rule is a candidate to evaluate; it must be verified to produce HTTP 307 + `Location`, preserve unrelated and repeated query keys/values, and avoid matching nested Product routes or loops. A static rule may not preserve duplicate `sort` semantics exactly. Middleware/Proxy or Nginx interception is explicitly not recommended under the current scope. Keeping the current in-component redirect retains the streamed 200 behavior.

## API error and SEO findings

- **404 vs 503:** detail API 404 becomes `notFound`; 422/503 remain thrown errors. Product list API failures also throw. The adapter does not fall back to mock data or empty lists on errors. Related-products failure is caught separately and displayed as an alert; it is not silently presented as zero related items.
- **HTTP on outage:** error boundaries provide visible fallback UI, but because the page can already be streaming, a 503 may likewise be delivered with HTTP 200. This was not exercised with an outage server and remains unverified.
- **Robots/canonical:** populated Product `generateMetadata` uses API `seo.robots` (contract value `noindex,follow`) and `canonicalPath`, with API OG fields. Category metadata was observed and canonicalized correctly. Missing Product smoke output had `robots=noindex` from Next's not-found handling, with no Product canonical; that is not evidence against the populated Product metadata path.
- **API error exposure:** `ServerApiError` includes only HTTP status in its message; API body/private details are not rendered. Error UI is generic English. Root layout Contacts failure is separately caught as `status: error`, so it does not turn a Product 404 into a Product API success.

## Populated SSR smoke feasibility

**Isolated contract-faithful stub: feasible.** A separate temporary API fixture server and an isolated Next process can exercise the actual App Router and server adapter without touching MariaDB. Use explicitly synthetic, test-only records for: one published Product with primary and secondary categories, ready/absent media cases, null price, one related Product, and API 404/503 variants. Make no fixture available as an application runtime fallback. This establishes frontend adapter, metadata, SSR HTML and route behavior against the declared DTO contract; it does **not** establish Laravel serialization, database relations, or media-file existence. It was not run in this audit because the existing frontend container is serving the shared dev app and changing its process/config/build artifacts would interfere with the user's live workspace.

**Laravel + MariaDB SSR: feasible after isolated test-data approval.** First confirm that all commands use Compose and `DB_DATABASE=potsandplanters_test`; verify the DB name before any write. The current route smoke did not establish that isolation. A minimal useful populated dataset would include:

- one published primary category and one published secondary category;
- one active supplier and one published Product attached to both categories, with a stable public UUID and a null price (to verify `Price on enquiry`);
- a second published Product in the primary category to verify related exclusion/current UUID behavior;
- optional ready MediaAsset plus its physical public variants for image URL/ALT/OG coverage; omit media for the first pass if creating valid ready assets requires a pipeline or file writes.

Use existing factories/API integration helpers where possible, record the pre-run test DB state, tag every created row with unique audit slugs/UUIDs, and clean only those identified rows in a `finally`/transaction cleanup after SSR. Preserve any pre-existing test data and confirm the cleanup counts. No such rows were created. A separate failure-injection mechanism is still needed for live 503; use an isolated API stub rather than changing Laravel state.
