- Сначала **read-only аудит** текущего репозитория, `git status`/diff и существующих ручных изменений; не предполагать, что рабочее дерево чистое. Не перезаписывать незакоммиченные изменения.

- Не внедрять mock fallback; synthetic fixtures допускаются **только для изолированных тестов** с явно обозначенными искусственными данными.
- Не запускать production migrations, seeds, deploy, indexation или активацию заявок.
- Проверки только в Compose, с явным `DB_DATABASE=potsandplanters_test`; до любых операций записи проверить окружение, имя БД и изоляцию. Предпочтение — read-only SSR с детерминированным тестовым API/stub на отдельном порту, если он способен воспроизвести контракт и Next production server без подмены production runtime. Если нужны записи в тестовую БД, сначала предоставить план изоляции, отката и запросить разрешение владельца; не делать запись автоматически.

## Этап A — read-only анализ причин HTTP status и redirect

**Цель:** установить точный путь исполнения, при котором Next.js 16 App Router фиксирует HTTP 200 до `notFound()` или `redirect()`.

**Действия:**
1. Прочитать фактические `page.tsx`, `generateMetadata`, layout/loading/Suspense, `products.server.ts`, `serverApiFetch`, error/not-found handlers, middleware и конфигурацию Next/Nginx, относящиеся к `/shop`, `/shop/[category]`, `/shop/[category]/[slug]`, `/product/[slug]`.
2. Проследить порядок `await` и начала streaming: где возникает 404 от Laravel, когда вызывается `notFound()`, что уже успело отправиться в HTTP response. Не считать наличие `notFound()` доказательством HTTP 404.
3. Отдельно проверить `sort=featured`: почему `redirect()` даёт streamed 200/meta refresh, сохраняет ли все прочие query keys, есть ли возможность получить настоящий HTTP 307/308 без изменения поведения и без redirect loop.
4. Сравнить фактическое поведение canonical, `robots noindex,follow`, metadata, API 404 и API 503. Проверить, что API 503 не маскируется как 404/empty state.
5. Подготовить варианты **минимальных** исправлений, их затронутые файлы и риски. Не внедрять middleware/Nginx rewrite, proxy interception или глобальную смену rendering strategy по умолчанию.

**Контрольная точка A:** если решение меняет HTTP/SEO semantics, архитектуру загрузки или user-visible behavior, остановиться и согласовать с владельцем. В этом задании не разрешено автоматически внедрять такие исправления.

## Этап B — воспроизводимые SSR acceptance cases

**Цель:** проверить реальные серверные HTML/headers и поведение на непустых данных без доступа к production.

**Действия:**
1. Составить матрицу тестов: опубликованный товар в primary category; товар в secondary category и canonical mismatch; отсутствующий slug; unpublished/inactive supplier; ready card/gallery media, ALT и OG; null price; API 503; newly published product без rebuild; Featured newest и Related исключает текущий UUID.
2. Сначала определить, можно ли покрыть сценарии через изолированный contract-faithful HTTP fixture server для API в Compose без записи в БД. Не использовать его как runtime fallback. Отметить отдельно, что такой тест проверяет SSR-адаптер/маршрутизацию, но **не** реальную интеграцию с MariaDB/Laravel.
3. Для end-to-end Laravel + MariaDB, если требуется непустая `potsandplanters_test`, описать конкретный минимальный набор тестовых записей и план безопасной очистки; **не создавать их без отдельного разрешения**. Учитывать связи categories, supplier, media и сохранение существующих тестовых данных.
4. Для каждого выполненного кейса фиксировать HTTP status, `Location` при redirect, `Content-Type`, robots/canonical в HTML, visible content, отсутствие fixture Product, ошибки в логах и факт GET-only/отсутствия записей.
5. Разделять `PASS`, `FAIL`, `NOT RUN`, `BLOCKED` и указать точный вид проверки: unit/contract, stub SSR или Laravel+MariaDB SSR.
