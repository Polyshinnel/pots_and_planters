# BE-08.5.3.3 — Product API Error Boundary Fix

**Status: READY FOR ACCEPTANCE.** Product API errors now produce explicit SSR error UI in the detail and listing consumers. API Product 404 still follows `notFound()`. No Laravel/API changes, database writes, mocks in runtime, public route changes, or design changes were made.

## Read-only baseline and cause

The worktree was already dirty with the BE-08.5.3 frontend integration and BE-08.5.3.2 route changes. Those edits and unrelated backend/admin/docs changes were preserved. This task changes only frontend Product error handling plus this report.

The production SSR reproduction identified two paths:

- Product detail calls `resolveProduct()` from `generateMetadata()` and again from the page. Next runs metadata generation outside the segment `error.tsx` boundary. A `ServerApiError(503)` there aborted the render before the route's normal HTML/error UI, producing HTTP 500 with Next's root error document (`<html id="__next_error__">`). The existing `error.tsx` could not render that failure.
- Catalog listing awaited Product `getProducts()` without a local API-error state. A Product list 404/503 escaped the async page and the loading/error boundary did not yield the intended visible HTML fallback in the production smoke.
- `FeaturedProducts` already catches list API failures and renders an explicit alert. Its 404 and 503 behavior was confirmed.

Product detail API 404 already maps to `undefined`, then `notFound()`. That path was preserved. Runtime errors that are not `ServerApiError` continue to propagate as rendering failures.

## Minimal fix

- `frontend/src/app/shop/[category]/[slug]/page.tsx` now catches non-404 `ServerApiError` during metadata generation and returns only `robots: noindex,follow` for the unavailable response. The page then catches the Product API error and renders a shared Product unavailable state. The API error is never mapped to Product data, an empty Product, a Product 404, or mock data.
- `frontend/src/components/product/ProductErrorState.tsx` holds the existing Product error copy and retry control. The route error boundary and API failure path share it. Retry uses the boundary reset callback or `router.refresh()`.
- `frontend/src/components/catalog/CatalogPage.tsx` catches `ServerApiError` from Product list requests and renders the existing Catalogue unavailable copy through `CatalogErrorState`. It does not turn the failure into an empty catalogue. Unrelated rendering/type errors are rethrown.
- `frontend/src/components/catalog/CatalogErrorState.tsx` shares the current catalog fallback markup and retry behavior. `frontend/src/app/shop/(catalog)/error.tsx` supplies the route group's error boundary for other uncaught failures.
- `frontend/src/app/shop/error.tsx` and `frontend/src/app/shop/[category]/[slug]/error.tsx` now reuse those same UI components. The loading boundary, route-group structure, SEO success path, redirect config, and public routes were not changed in this task.

## Isolated production SSR matrix

The verification used a separate production standalone build and a temporary contract-shaped HTTP stub. All records were synthetic and confined to the smoke process. The stub did not connect to Laravel or MariaDB; no runtime fallback was added.

| Scenario | Observed response | Result |
|---|---|---|
| Detail Product endpoint returns API 404 | HTTP **404**; Next not-found document | **PASS**. No Product error UI, Product data, or empty state. |
| Detail Product endpoint returns API 503 | HTTP **200** with `Product unavailable` and `We could not load this product. Please try again.` | **PASS** for explicit failure UI. It is not a 404, empty Product, or mock. Next status is 200 because the page renders the explicit fallback; upstream 503 is not propagated as the outer HTTP status. |
| Product listing endpoint returns API 503 | HTTP **200** with `Catalogue unavailable` and the existing alert text | **PASS**. No empty catalogue was presented. |
| Product listing endpoint returns API 404 | HTTP **200** with `Catalogue unavailable` | **PASS**. A list endpoint error does not become a Product/page 404 or empty result. |
| Featured Products endpoint returns API 503 | HTTP **200** with `Featured products are temporarily unavailable. Please try again.` | **PASS**. Existing catch behavior was confirmed. |
| Featured Products endpoint returns API 404 | HTTP **200** with the same explicit unavailable alert | **PASS**. It is not shown as the successful empty state. |
| Malformed synthetic DTO causes a React render failure | HTTP **500**, Next root error document | **PASS** for classification. It does not enter the API error fallback, become 404, or become empty data. The custom route error UI was not emitted for this server-render failure; it remains a separate rendering-error limitation. |
| `/shop?sort=featured&page=4&material=ceramic` | HTTP **307**, `Location: /shop?sort=newest&page=4&material=ceramic` | **PASS**. Prior redirect behavior remains intact. |
| Successful synthetic Product detail DTO | HTTP **200**; title, canonical, `robots=noindex,follow` present | **PASS**. Normal Product metadata branch is preserved. |

For the API 503 detail reproduction, the stub observed one Product detail request across metadata generation and page rendering after metadata completed successfully with its safe robots fallback. The separate malformed-DTO case made two successful detail requests, as metadata and page resolution remain separate on that success path; this task did not add a lookup for status handling.

## Remaining limitation

Explicit Product API failure UI is served with outer HTTP 200. The response body clearly identifies the unavailable Product/catalogue, and no data is represented as successfully loaded. A separate requirement to retain an outer non-2xx status while rendering this fallback would need another Next response-status mechanism; that behavior was not introduced here.

No populated Laravel + MariaDB smoke, seed, migration, production action, or database write was performed. **Waiting for owner acceptance.**
