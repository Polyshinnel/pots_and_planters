# BE-08.5.4.2 — Next.js Dynamic Product Filters

**Статус:** ТЗ к исполнению; реализация не подтверждена.  
**Предпосылка:** BE-08.5.4.1 принят на уровне focused backend tests; полный backend suite и production проверка отдельно.

## Цель
Подключить `/shop` и `/shop/[category]` к фактическим facets и типизированным `filter[code]` Laravel Product Read API, сохранив дизайн, маршруты, SEO и действующую пагинацию/сортировку.

1. Прочитать `AGENTS.md`, `docs/common/PROJECT_CONTEXT.md`, `docs/common/ROADMAP.md`, отчёты BE-08.5.4.1 и BE-08.5.3.3; проверить `git status` и ручные изменения. Не предполагать, что код соответствует переписке.
2. Изучить реальные DTO/валидацию `ProductReadController`, `ProductReadApiTest`, API adapter, CatalogPage/CatalogListing, mobile drawer, URL-парсер, loading/error states.
3. Зафиксировать точный формат сериализации `filter[code]` для каждого типа, включая повторяющиеся значения, boolean false, number/range, пустые/некорректные значения и URL encoding. Не выдумывать синтаксис.
4. Проверить поля facet (`code`, `label`, `type`, `displayType`, `options`, `min`, `max`), eligibility, поведение нулевых/пустых facets и серверных ошибок. Для `number` — фактические десятичные строки `min/max` или null; нет `options`/`count`.
5. Проверить текущую семантику SEO/canonical, 404, redirect `sort=featured → newest`, error UI и отключённых Enquiry actions.

## Этап B — API adapter и URL-driven state
- Расширить типы DTO и server-only adapter для глобальных и категорийных facets. API — единственный источник фильтров, доступности значений и counts; не вычислять counts на клиенте из текущей страницы.
- Сериализовать активные фильтры в URL по фактической grammar API. OR внутри одного атрибута, AND между атрибутами обеспечивает backend. Сохранять выбранные значения при навигации/refresh/back-forward.
- Изменение фильтра сбрасывает `page` на 1, сохраняет сортировку и остальные валидные фильтры; изменение сортировки не должно терять фильтры. Сохранять query параметры, не относящиеся к фильтрам, если это не противоречит существующей валидации.
- Не подменять 422/503 пустой выдачей; показывать явное английское сообщение. Неподтверждённые legacy `material/color/size/usage` не конвертировать и не игнорировать; сохранить согласованный explicit unsupported state/clear action.
- Включить `filter[code]` в запросы API на `/shop` и в категориях. Не делать запросы на весь каталог ради подсчёта facets.

## Этап C — UI без редизайна
- Повторно использовать существующую панель и mobile drawer, spacing, typography, layout, accessibility patterns.
- `select/multiselect` и другие дискретные facets: использовать `options` и серверные `count`; отображать только реальные данные, не придумывать варианты. Учитывать выбранные значения при изменении набора facets; не терять их молча.
- `boolean`: поддерживать оба реальных значения, включая `false`; не путать false с отсутствием фильтра.
- `number/range`: поля Min/Max, реальные `min/max` как информационные границы; пользовательские значения не округлять через float и не перезаписывать автоматически при изменении facets. Валидация ввода и отправка inclusive bounds строго по API grammar. При `min=max=null` не рисовать ложный диапазон.
- `text`: если API поддерживает exact text, использовать явный exact-match UX, без обещания полнотекстового поиска.
- Не вводить диапазонные buckets или counts для чисел. При отсутствии доступных facets каталог продолжает работать без пустой фиктивной панели.
- Доступность с клавиатуры, подписи полей, mobile apply/reset и URL должны быть проверены. Если UI-паттерн требует изменения дизайна, остановиться и согласовать минимальный вариант.
