# BE-08.5.5.1 — Read-only аудит Product Enquiry Cart и согласование контракта

**Проект:** Pots & Planters 2.0  
**Статус:** ТЗ на аудит; реализация не разрешена.  
**Цель:** установить фактическое состояние клиентской корзины, Product Enquiry, Laravel endpoint и подготовить согласованный контракт перехода на Product `public_id` (UUID) без потери существующих записей.

## 0. Обязательный контекст

Перед началом прочитать `AGENTS.md`, актуальные `docs/common/PROJECT_CONTEXT.md`, `docs/common/ROADMAP.md`, отчёты BE-07, BE-08.5.2–BE-08.5.4.2 и текущий `git status --short`. Исторические документы не считать доказательством текущего состояния репозитория. Все существующие ручные и незакоммиченные изменения сохранить.

Стек: Next.js 16 / React 19 / TypeScript / Mantine 9; Laravel 13 / Filament 5 / MariaDB / Redis / Horizon. Публичный UI на английском. Дизайн, маршруты, SEO не менять.

## Этап A — read-only карта потока

**Цель:** описать каждый реальный путь создания, хранения, разрешения, отображения и отправки позиции Product Enquiry.

Проверить:
1. Все `Add to Enquiry` и `Submit` точки: Product detail, каталожные карточки, Featured, Related, `/solutions`, `/cart`, header/badge, формы, мобильные элементы. Отдельно подтвердить, какие действия сейчас отключены, а какие реально вызывают store/endpoint.
2. Точную схему localStorage, ключи, типы, миграции/версии, ID и SKU, brand context, quantity, snapshot и поведение при повреждённых/устаревших данных. Не очищать storage.
3. `resolveEnquiryLine`, `catalogRepository`, mock-зависимости, клиентские и серверные ограничения; определить, где SKU может быть неоднозначен между брендами.
4. Product Read API: список/detail, поддерживаемые идентификаторы, visibility, `public_id`, `slug`, SKU/Brand, price nullable, готовые изображения. Проверить, существует ли безопасный batch lookup по UUID, не предполагать его наличие.
5. Laravel `POST /api/v1/enquiries`: реальные типы `product_enquiry` и `cart_enquiry`, DTO, валидация, snapshots, доступность Product, лимиты, идемпотентность, ошибки, Telegram/outbox и feature flags. Проверить, не основан ли endpoint на прежних fixture/SKU-предположениях.
6. Поведение при 404/422/503, unpublished/archived/inactive supplier, изменении цены, исчезнувшем товаре, дубликатах, пустой корзине, refresh и повторной отправке.

**Ограничение:** только чтение, никаких правок, seed, миграций, переключения БД, включения Product/Cart Enquiry или вызовов реальной отправки заявок.

## Этап B — проект контракта (без реализации)

Предложить один основной и при необходимости альтернативный контракт с точными DTO/URL/ошибками:
- Идентичность позиции: `public_id` как стабильный ключ; SKU только отображаемое поле. Не сопоставлять существующие позиции по одному SKU, имени или slug без доказанной однозначности.
- Совместимость существующих `potsandplanters.enquiry.v1` записей: классификация legacy, безопасное разрешение, явные состояния unresolved; без молчаливого удаления или подмены. Определить, нужна ли версия v2 и как миграция будет атомарной/идемпотентной.
- Авторитетные серверные snapshots на момент submission: цена (включая `null`), наименование, SKU, бренд, количество, availability. Клиентский snapshot не считать источником истины.
- Разрешение нескольких UUID без N+1 и без выгрузки всего каталога; если необходим новый API endpoint, предложить минимальный Laravel контракт и тесты, **не реализовывать**.
- Перед отправкой проверять все позиции, включая недоступные: отклонять submit с понятной ошибкой и возможностью исправления; не удалять их автоматически.
- Идемпотентность, ошибки API и сохранение localStorage при сбое; UI не показывает ложный успех.
- Чёткое разделение `product_enquiry` (один Product) и `cart_enquiry` (несколько), включая существующие backend правила.
- Feature flag: не активировать Product/Cart Enquiry до отдельного разрешения и успешной проверки. `/solutions` остаётся отдельным будущим модулем, mock Product из него не добавлять.

## Этап C — план вертикальной реализации

Разделить BE-08.5.5 на малые этапы: при необходимости Laravel read/resolve endpoint → Laravel validation/snapshots → Next.js resolver/store compatibility → UI/actions → интеграционные тесты/ручная приёмка. Для каждого: цель, точные файлы/слои, ограничения, тесты, критерии приёмки и явные owner checkpoints. Предпочесть переиспользование текущих сервисов BE-07.

## Обязательные сценарии проверки в плане

- Один и несколько разных UUID; одинаковый SKU у двух брендов.
- Null price и точная decimal цена; изменённая цена/название после добавления.
- Существующий legacy storage, повреждённый JSON, старый fixture ID, отсутствующий Product.
- Archived/unpublished Product, inactive Supplier, API 503, 422, duplicate submission/idempotency 409.
- Refresh, удаление вручную, quantity, повторная отправка, сохранение позиций при ошибке.
- Отсутствие fixture write paths и mock fallback, неактивность `/solutions` Add actions.
- Контроль feature flags в dev и production; никакого production activation.
- Тесты Laravel только с подтверждённым `DB_DATABASE=potsandplanters_test`, frontend через Compose; тестовые записи только после отдельного разрешения.

## Выходные артефакты

Создать `docs/frontend/BE-08.5.5.1_ENQUIRY_CART_AUDIT_REPORT.md` с: (1) фактической картой потоков и ссылками на файлы/строки; (2) таблицей рисков; (3) предложенным контрактом API/storage; (4) точками несовместимости; (5) разбивкой этапов и acceptance criteria; (6) перечнем решений, требующих владельца; (7) точным статусом проверок (NOT RUN для невыполненных).
