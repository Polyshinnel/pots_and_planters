### localStorage и разрешение строк

- Ключ: `potsandplanters.enquiry.v1`; envelope `{version: 1, items: [...]}`; запись позиции `{productId: string, sku: string, quantity: safe integer 1..999999}`. Данные записи хранят только идентификаторы и количество; product name/price/specifications не сохраняются.
- JSON с повреждением, неизвестной версией/формой даёт пустое состояние **в памяти**, исходное значение localStorage не удаляется. Некорректные элементы пропускаются; обработка ограничена первыми 1000 элементами. Дубликаты группируются по SKU; повторный SKU с другим productId игнорируется. Добавление с совпавшим SKU и другим productId бросает ошибку. Это наследует предположение «SKU идентифицирует модель», которое уже не валидно: SKU unique per Brand, не глобально.
- Store подписывается на storage event, гидратирует на клиенте, записывает только при явных операциях; при отказе localStorage помечает `persistent=false`, сохраняя текущую вкладочную копию. Ручное удаление позиции/очистка реализованы.
- `resolveEnquiryLine` находит только в `@/data/catalog.mock` по совпадению `id + sku + published`. Поэтому текущие API UUID из Laravel без совпадающей fixture не разрешаются, выводится `Model <SKU>` и статус «needs reconfirmation». При наличии fixture берутся mock-цена, характеристики, имя и картинка; доступность определяется существованием fixture, а не Laravel. `buildEnquiryPayload` включает эти клиентские snapshot поля, но текущая checkout отправка его не использует.
- Product API отдаёт UUID в DTO-поле `id` (это `products.public_id`), SKU, name, brand, decimal price строкой либо `null`; публичен только published Product с published primary category и active Supplier. Detail доступен по slug, list — пагинирован, максимум 48; endpoint поиска по `public_id` отсутствует. Доступность в API — критерий публичной видимости, не складской остаток.

## 4. Предлагаемый контракт (для согласования)

### 4.1 Идентичность и DTO

Канонический ID строки — Product `public_id` UUID. Во frontend API adapter сейчас называет этот DTO `id`; на enquiry boundary использовать однозначное `productId` либо `productPublicId` (предпочтение автора: `productId`, если документируется UUID), но не slug/SKU. SKU, name, Brand и цена в запросе не являются authority. SKU всегда scoped к Brand и не использовать для matching/deduplication.

Предлагаю единый формат позиции:

```json
{"productId":"<public_id UUID>","quantity":2}
```

`product_enquiry`: одна такая позиция в top-level `product`; `cart_enquiry`: `items` из 1..100 позиций. Backend rejects duplicate UUIDs (не складывает незаметно), неверные UUID и неизвестные поля. Количество ограничить согласованным единым диапазоном — сейчас UI 1..999999, Laravel 1..1000000; рекомендую 1..999999 с текущим UI. Общие contact/source поля оставить по BE-07. `product_enquiry` и `cart_enquiry` остаются разными типами, валидацией и item cardinality.

UUID resolution следует добавить как `POST /api/v1/products/resolve` с `{ "ids": ["uuid", ...] }`, лимит 100 уникальных UUID, no-store, без пагинации каталога. Ответ содержит `data[]` по каждому входному ID со статусом `available|unavailable`; доступные значения возвращают тот же безопасный публичный Product DTO (id, SKU, name, Brand, nullable decimal price string, canonical path, подготовленная картинка/спецификации при нужде). Недоступный UUID возвращает только `id` и `status: unavailable`, без различения draft/archived/inactive supplier/unknown, чтобы не раскрывать приватные записи. Сохранить порядок входа; повторные ID — 422. Ошибки — общий API envelope: 422 malformed/duplicates/too many, 503 database/API unavailable. Метод POST выбран, чтобы не помещать до 100 UUID в URL/logs и не зависеть от query length.

**Почему endpoint необходим:** существующий `GET /v1/products/{slug}` не разрешает UUID; list endpoint имеет perPage ≤48, нужен пагинируемый публичный каталог, а `filter` не предоставляет UUID selector. Последовательный вызов detail для каждой позиции был бы N+1. Поэтому переиспользование текущих endpoint не даёт безопасного batch resolution.

### 4.2 Availability semantics

`available` означает соответствие текущему публичному Product API: status `published`, опубликованная primary category и активный Supplier. У товара нет подтверждённого stock/inventory поля; не называть это наличием на складе. Перед отправкой клиент повторно batch-resolve все UUID. Если любой недоступен/исчез/переход вернул 503 — блокировать submit, сохранить все строки, дать удалить/повторить и сообщить по конкретным позициям. Backend повторяет все проверки атомарно непосредственно перед snapshot/commit; скрытая/удалённая позиция возвращает 422 `products_unavailable` (или согласованный 404, одинаковый для всех недоступных ID), без частичной заявки.

### 4.3 Laravel Enquiry submit и snapshots

POST `/api/v1/enquiries` остаётся endpoint. Для обоих типов Laravel внутри одной DB transaction загружает UUIDs батчем с `sharedLock`, применяет visibility scope, сверяет полноту набора и создаёт серверный snapshot. В запросе допускаются только identity UUID, quantity, contact/source и стандартный idempotency header; клиентские name/SKU/brand/price/availability/attributes запрещены. Если требуется optimistic UX, клиент может передать отображённую версию/время проверки только как диагностическую подсказку, не как цену/истину.

На момент submit сохранять неизменяемые значения: `product_public_id`, `sku`, `name`, `brand_public_id` и `brand_name`, `quantity`, `unit_price_aed` (`DECIMAL`/строка, nullable), `currency=AED`, `availability=available`, `snapshot_at`; допустимо также `slug/canonicalPath` и короткие безопасные спецификации для аудита/уведомлений. Обновлённая после добавления цена/название заменяет клиентское отображение при re-resolve и становится snapshot только если Product всё ещё публичен. `null` price сохраняется как null; не считать 0 и не выполнять арифметику, обещающую итоговую цену. Полный snapshot дублируется в JSON `enquiry_items.product_snapshot`, либо в нормализованных колонках плюс JSON; решение схемы — owner checkpoint. Не изменять старые rows и не назначать им выдуманные UUID/snapshots.

Рекомендация: явно версионировать payload как `apiVersion: 2`/`version: 2`, а не молча менять v1 семантику. Принимаемость Contact/Catalogue v1 сохранить. Идемпотентность остаётся одной заявкой + outbox в транзакции, текущий `Idempotency-Key` (16..128 символов) и 409 при повторе того же ключа с иным payload; один ключ должен жить на одну неизменную попытку и повторяться после network/503.

Рекомендуемые ответы: 201/200 replay `{data:{status:"persisted",enquiryId,notificationStatus}}`; 422 `validation_failed` с field errors или `products_unavailable` с UUIDs позиций; 404 не должен быть основным источником диагностики отдельных UUID (batch resolve маскирует их); 409 `idempotency_conflict`; 429 throttle; 503 `persistence_unavailable`/`service_unavailable`. Клиент никогда не очищает корзину автоматически. Успех показывается только после `data.status=persisted`; при любой ошибке остаются строки и контактные поля.

### 4.4 Безопасная миграция storage

Не переиспользовать v1 форму как будто `productId` уже UUID. Предложение: добавить v2 envelope под отдельным ключом `potsandplanters.enquiry.v2` с `version:2` и `items:[{productId:<UUID>,quantity}]`. На первой миграции считать старый `potsandplanters.enquiry.v1` read-only legacy source; показать отдельную строку на каждую legacy позицию и её разрешение.

Безопасная миграция выполняется по каждой записи только при доказанной связи исходного ID с ровно одним API Product UUID (например, исходный `productId` уже валидный UUID и batch resolve подтвердил этот же ID; не по одному SKU/name/slug). Неоднозначные/fixture IDs/удалённые Product получают состояние unresolved и остаются видимы с исходным SKU/quantity; разрешить владельцу вручную удалить строку. Никакой автоматической подстановки нового Product по совпавшему SKU. Записать v2 целиком атомарным `setItem`, убедиться чтением/валидацией, и лишь затем можно пометить legacy мигрированным; не удалять v1 в этом этапе. Повреждённый JSON/неизвестная версия не должна превращаться в пустую корзину для записи: блокировать add/submit/commit до восстановления или явного пользовательского reset, а оригинал не перезаписывать. Ошибка quota/storage должна оставить текущую сессию и явно показать, что долговременное хранение недоступно.

Удаление строки/изменение quantity в unresolved состоянии сохраняет остальные строки, включая валидные. Объединение строк разрешено только по `productId` UUID. Refresh повторно разрешает актуальные Product и показывает новый snapshot; без API отображает последнее безопасное сохранённое display snapshot, но блокирует submit до успешной проверки. Решение, нужен ли минимальный v2 display cache (SKU/name/brand/price) для корректного отображения при refresh/offline, вынесено владельцу; такой cache никогда не является submit authority.

## 6. Решения, требующие владельца

1. Подтвердить `POST /api/v1/products/resolve` с лимитом 100, DTO и маскированием недоступных Product (рекомендуется: **да, endpoint нужен**).
2. Подтвердить имена `productId` UUID и `apiVersion/version:2`; подтвердить product single-item shape и cart `items[]` shape.
3. Подтвердить semantics availability: public visibility, а не stock.
4. Выбрать snapshot representation/schema и точный состав полей, включая nullable price и сохранение спецификаций.
5. Утвердить storage v2 key + оставить v1 read-only без удаления; определить UX для unresolved legacy, corrupt JSON и display cache.
6. Утвердить единый максимум quantity (предлагается 999999), max cart lines (100), и поведение duplicate UUID (422).
7. Подтвердить поведение submit race, если товар скрылся между batch resolve и transaction: all-or-nothing 422 с безопасным списком UUID.
8. Утвердить два независимых feature flags (Product и Cart), оставив оба выключенными до отдельной приёмки; Contact/Catalogue флаг остаётся независимо управляемым.
