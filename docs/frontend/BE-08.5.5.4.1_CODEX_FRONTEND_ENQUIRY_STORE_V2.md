# BE-08.5.5.4.1 — Frontend Enquiry Store v2 & Legacy Storage Compatibility

**Тип этапа:** frontend domain/store implementation  
**Статус:** задание подготовлено; реализация не начиналась  
**Язык:** техническое задание для Codex — русский  
**Проект:** Pots & Planters 2.0

## 1. Цель

Подготовить frontend-хранилище Product/Cart Enquiry v2 на основе Product `public_id` UUID и обеспечить безопасное сосуществование с ранее сохранённым localStorage v1.

На этом этапе реализуется только доменный слой и storage/store compatibility. Пользовательские действия добавления товара и отправки заявки остаются отключёнными. Не подключать UI и формы к новому store, пока следующий этап отдельно не разрешит это.

Главный инвариант: **ни одна существующая позиция v1 не должна исчезнуть, быть автоматически заменена другим товаром или стать основанием для отправки заявки без доказанного соответствия Product UUID.**

## 3. Утверждённый контракт хранения

### 3.1. Ключи и версии

Существующий v1:

- key: `potsandplanters.enquiry.v1`;
- envelope: `{ "version": 1, "items": [...] }`;
- legacy item: `{ "productId": string, "sku": string, "quantity": integer }`.

Новый v2:

- key: `potsandplanters.enquiry.v2`;
- envelope: `{ "version": 2, "items": [...] }`;
- item: `{ "productId": "<Product public_id UUID>", "quantity": integer }`.

Требования:

- Не менять формат и семантику v1.
- Не переиспользовать v1 key для v2.
- Не удалять v1 key в этом этапе и не перезаписывать его.
- v2 идентифицирует позиции только UUID. SKU не является ключом, не участвует в дедупликации и не используется для поиска.
- Quantity — безопасное целое число от 1 до 999999.
- Максимум 100 уникальных строк в v2 store.
- Дубли UUID при входной валидации не должны незаметно создавать несколько строк: добавление существующего UUID увеличивает quantity существующей строки с проверкой верхнего лимита. При импорте/чтении некорректного v2 с повторяющимися UUID считать envelope invalid, не нормализовывать его молча.
- Никаких клиентских price/name/brand/specification полей в submit-authoritative storage.

### 3.2. Legacy v1 — только read-only source на этом этапе

На этом этапе:

- Читать и валидировать v1 отдельно от v2.
- Показывать legacy позиции доменному слою как отдельные unresolved records с исходными `productId`, `sku`, `quantity`.
- Не трактовать v1 `productId` как UUID только потому, что строка синтаксически похожа на UUID.
- Не сопоставлять legacy позиции по SKU, названию, slug или сходству данных.
- Не объединять v1 позиции между собой и с v2.
- Не удалять v1 после чтения, hydration, создания v2 или операций с v2.
- Не выполнять автоматическую миграцию v1 → v2 в этом этапе. Даже если старый `productId` выглядит как UUID, перевод возможен только в отдельном этапе после batch resolve и подтверждения точного совпадения UUID.
- Пользовательские add/remove/submit actions остаются выключенными; этот этап не должен активировать их.

Legacy records должны оставаться доступными для последующего UI: исходные SKU и quantity нужны для отображения и ручного удаления. Не превращать unresolved в обычный доступный Product.

### 3.3. Разделённое состояние

Store/domain должен различать как минимум:

- `ready` — v2 корректен, legacy отсутствует или корректно прочитан;
- `legacy_present` — v1 содержит позиции, не перенесённые в v2;
- `corrupt` — v1 или v2 содержит повреждённый JSON, неизвестную версию или некорректную структуру;
- `storage_unavailable` — localStorage недоступен, чтение/запись завершились исключением;
- `not_hydrated` — клиентская гидратация ещё не выполнена.

Допускается иная внутренняя типизация, если она сохраняет эти различия и не приводит к потере информации.

Не объединять `corrupt` с пустой корзиной. Не представлять `storage_unavailable` как успешно сохранённое состояние.

## 4. Требования к v2 store

1. Сохранить существующий публичный API store, если он используется другими частями приложения; новые функции добавлять без ненужного рефакторинга.
2. Выделить чистые функции:
   - parse/validate v2 envelope;
   - parse/validate legacy v1 envelope;
   - UUID validation;
   - quantity validation;
   - сериализация v2;
   - безопасное применение add/remove/update quantity к v2 state.
3. Не обращаться к `window`/`localStorage` при SSR или на уровне module initialization. Storage доступен только в клиентском runtime после hydration либо через существующую безопасную абстракцию.
4. Сохранить корректную работу `storage` event между вкладками.
5. Любая запись v2:
   - сначала полностью валидирует новый envelope;
   - сериализует его в памяти;
   - выполняет один `setItem` по v2 key;
   - после записи перечитывает и валидирует значение;
   - только после успешной проверки считает состояние сохранённым.
6. Не выполнять `removeItem` для v1 или v2 в рамках автоматической миграции.
7. Если `setItem` бросает (quota/security/private mode), сохранить актуальное состояние текущей вкладки в памяти, выставить `storage_unavailable`/`persistent=false` и не заявлять о долговременном сохранении.
8. Если v2 повреждён или версия неизвестна, блокировать любые destructive writes в v2 до отдельного явного recovery/reset flow. В этом задании recovery/reset UI не реализовывать.
9. Если v1 повреждён или версия неизвестна, не перезаписывать его и не очищать. Состояние должно сигнализировать о необходимости recovery; обычные операции, которые могут создать впечатление, что legacy корзина пуста и безопасно перезаписана, блокируются.
10. Не допускать, чтобы ошибочный v1 блокировал чтение корректного v2: оба источника должны диагностироваться раздельно. Но общий state обязан сообщить о legacy/corrupt status, чтобы следующий UI не скрыл проблему.

## 5. Поведение операций доменного слоя

Реализовать и протестировать операции над v2 state, не подключая их к публичным кнопкам:

- `add(productId, quantity)`:
  - принимает только валидный UUID;
  - при существующем UUID увеличивает quantity;
  - проверяет итоговое quantity ≤ 999999;
  - не принимает SKU или product details как идентификатор;
  - не допускает более 100 уникальных строк.
- `remove(productId)` удаляет только соответствующую UUID-строку.
- `setQuantity(productId, quantity)` принимает целое 1..999999; ноль не является quantity (для удаления есть отдельная операция).
- Все операции сохраняют порядок строк, кроме случая добавления новой строки в конец.
- Операции не затрагивают legacy v1 records.
- Если состояние `corrupt` либо storage не позволяет подтвердить безопасную запись, операция должна вернуть явный typed failure, а не молча продолжить как успешная.
- Повторное добавление UUID объединяет только по UUID. Одинаковые SKU у разных UUID должны оставаться двумя разными строками.

Если текущий store использует другой стиль API, адаптировать операции к существующим conventions, не создавать параллельную store architecture.

## 6. Display cache — границы

В этом этапе **не добавлять Product display cache в v2 storage**, если он не требуется для технической совместимости текущего store.

Причины:

- `POST /api/v1/products/resolve` является источником актуального публичного Product DTO;
- клиентский cache не является источником истины и не может использоваться для submit;
- минимальный display cache и его правила обновления должны быть спроектированы вместе с batch resolve/UI в следующем frontend-этапе.

Legacy v1 SKU сохраняется как исходное legacy-поле для отображения, но не используется для разрешения товара.

## 8. Тестирование

Добавить focused frontend tests для:

### Parsing и validation

- корректный пустой v2 envelope;
- корректный v2 с несколькими UUID;
- malformed JSON;
- неизвестная версия;
- неверный UUID;
- quantity: 0, отрицательное, дробное, строка, >999999;
- больше 100 строк;
- повтор UUID внутри сохранённого envelope;
- неизвестные/лишние поля, если schema использует strict validation.

### Legacy compatibility

- корректный v1 читается как legacy unresolved;
- fixture ID не превращается в UUID;
- UUID-похожий legacy ID не переносится автоматически;
- одинаковый SKU не объединяет строки;
- неизвестная версия и malformed v1 не удаляются и не перезаписываются;
- корректный v2 доступен независимо от наличия legacy v1;
- v1 сохраняется байт-в-байт после hydration и операций v2.

### Store operations

- add новой UUID строки;
- add того же UUID увеличивает quantity;
- одинаковый SKU (если он существует только в тестовых legacy fixtures) не влияет на UUID дедупликацию;
- remove одной строки не затрагивает остальные;
- setQuantity;
- лимит 100 строк;
- quantity overflow;
- corrupt state блокирует запись;
- storage `setItem` exception сохраняет вкладочное состояние и честно выставляет persistent=false;
- read-back mismatch не считается успешной записью;
- storage event обновляет state без потери/перезаписи других версий.

### Regression

- существующие Contact/Catalogue Enquiry tests остаются зелёными;
- текущие Product action guards остаются выключенными;
- Solutions add actions остаются выключенными;
- нет новых вызовов enquiry store из UI;
- нет SSR обращений к `window`/localStorage.

Команды и тестовые сценарии брать из актуального `AGENTS.md` и package scripts. Запускать frontend checks через установленный Docker Compose workflow проекта. Не предполагать, что локальные npm-команды являются утверждённым способом.
