## 1. Цель

Подключить новый UUID-only store v2 (`potsandplanters.enquiry.v2`) к интерфейсу просмотра Enquiry Cart и разрешать его Product UUID через существующий Laravel endpoint:

`POST /api/v1/products/resolve`

Показать пользователю:

- товары со статусом `unavailable`;

- честное состояние повреждённого или недоступного localStorage.

На этом этапе **не восстанавливать добавление товаров и отправку заявок**. Цель — безопасное отображение и восстановление ранее сохранённого состояния, а не активация Enquiry.

## 3. Утверждённые API-контракт и DTO

### 3.1. Resolve request

```json
{
  "ids": [
    "00000000-0000-4000-8000-000000000001",
    "00000000-0000-4000-8000-000000000002"
  ]
}
```

- От 1 до 100 уникальных UUID.
- Порядок ответа совпадает с порядком входных UUID.
- Повтор UUID в запросе — HTTP 422.
- SKU, slug и внутренний DB ID не используются для разрешения.
- Ответ имеет `Cache-Control: no-store`.
- Backend rate limit — 60 запросов в минуту на IP.

### 3.2. Resolve response

Доступная позиция:

```json
{
  "id": "00000000-0000-4000-8000-000000000001",
  "status": "available",
  "product": {
    "id": "00000000-0000-4000-8000-000000000001",
    "slug": "example-product",
    "sku": "PP-001",
    "name": "Example Product",
    "brand": { "id": "brand-public-uuid", "name": "Example Brand" },
    "priceAed": "125.0000",
    "currency": "AED",
    "categoryIds": [],
    "primaryCategory": {
      "id": "category-public-uuid",
      "slug": "indoor-pots",
      "name": "Indoor Pots",
      "path": "/shop/indoor-pots"
    },
    "canonicalPath": "/shop/indoor-pots/example-product",
    "cardImage": null,
    "cardSpecifications": [],
    "cardSpecificationsText": ""
  }
}
```

Недоступная позиция:

```json
{
  "id": "00000000-0000-4000-8000-000000000002",
  "status": "unavailable"
}
```

Фактический `ProductListData` в backend является источником истины. Не урезать и не переименовывать поля на основании только этого примера. Сверить точную схему с backend DTO и реальным contract test.

`available` означает публичную видимость Product, опубликованной primary Category и активного Supplier. Это **не** подтверждение складского остатка.

### 3.3. Поля отображения

Использовать только DTO из resolve:
- `name`;
- `sku`;
- `brand.name`;
- `priceAed` как decimal string либо `null`;
- `currency`;
- `cardImage` и его `url`/`alt`;
- `cardSpecifications` / `cardSpecificationsText`;
- `canonicalPath` только если существующий UI уже предусматривает ссылку на Product.

Цена:
- `null` отображать как `Price on enquiry`;
- не преобразовывать decimal string во float для расчётов;
- не выводить сумму корзины как обещанную стоимость;
- не выводить subtotal/total на основании цены, если такой расчёт не был утверждён.

Изображение:
- использовать только готовый публичный URL `cardImage` из API;
- `null`/ошибка изображения — существующий placeholder;
- никаких mock images, original/private paths или построения URL вручную.

Не добавлять Product description/gallery или новые публичные поля ради Cart UI.

## 4. Интеграция store v2

### 4.1. UUID позиции

- Источник UUID — только `item.productId` из v2 store.
- Resolve запрашивается пакетно, не по одному товару.
- Сохранять порядок строк store.
- Один resolve request для списка до 100 UUID; если текущая архитектура допускает более 100 строк только по ошибочным данным, показать corrupt/invalid state, не разбивать и не обходить лимит.
- Не добавлять UUID, SKU или Product DTO в v1 store.
- Не менять схему v2 envelope без отдельного решения.

### 4.2. Hydration и runtime

- Не обращаться к localStorage при SSR/module initialization.
- До завершения hydration не показывать пустую корзину как окончательный результат.
- После hydration читать v2 store, затем выполнять resolve для UUID.
- Не запускать resolve для пустого списка.
- Не создавать циклические запросы при `storage` event или повторном render.
- Использовать существующие hooks/subscription conventions проекта; не создавать вторую независимую store architecture.

### 4.3. Ошибки resolve — три разных состояния

Строго различать:

1. **`available`** — backend вернул доступный Product DTO.
2. **`unavailable`** — backend успешно ответил для конкретного UUID, но товар неизвестен или не публичен. Показывать нейтральное сообщение `This product is no longer available`.
3. **`resolve_error`** — запрос не выполнен, timeout/network, 429, 422 из-за нарушения клиентского контракта, 500/503 или некорректный response. Это не означает, что товар недоступен.

При `resolve_error`:
- не удалять и не менять позиции;
- не помечать их `unavailable`;
- не очищать store;
- показать `We couldn't load your enquiry items. Please try again.`;
- предоставить явное действие Retry;
- не использовать mock fallback или последний фиктивный snapshot.

Возможен read-only display cache только если он уже существует и его происхождение/схема подтверждены аудитом. В рамках этого задания новый cache не добавлять. Без cache при API error показывать SKU/quantity из v2 state неотображаемы (их там нет) — поэтому показать UUID в пользовательском UI не нужно; отобразить нейтральную строку `Product details temporarily unavailable` и сохранить возможность повторить запрос/удалить позицию.

## 5. Отображение v2 позиций в Cart

Переиспользовать существующие компоненты карточек/строк Cart и Mantine стили. Не менять публичный дизайн без необходимости.

Для каждой v2 позиции:
- доступная: image/placeholder, Product name, Brand, SKU, card specifications (если пригодны существующему Cart layout), quantity;
- `priceAed === null`: `Price on enquiry`;
- цена есть: отформатированная AED цена с сохранением исходной decimal precision на уровне данных;
- недоступная: нейтральное состояние, без подстановки другого товара;
- временная ошибка resolve: отдельное сообщение, не `unavailable`.

В этом этапе:
- quantity отображается read-only;
- add/remove/quantity controls для v2 не активировать;
- не добавлять subtotal/total;
- не активировать Product Enquiry/Cart Enquiry CTA.

Если v2 пустой, но v1 содержит legacy lines, показывать legacy section. Если оба пусты, показывать существующий empty-cart state.

Если v2 и v1 одновременно содержат строки, показывать их раздельно с ясными названиями секций. Не объединять и не дедуплицировать между версиями.

## 6. Legacy v1 UX и явное удаление

Legacy позиции остаются unresolved. Нельзя:
- трактовать legacy `productId` как UUID даже если строка UUID-подобна;
- искать по SKU, name, slug или mock catalogue;
- подменять позицию похожим или одноимённым товаром;
- включать legacy позицию в Product/Cart submit;
- автоматически мигрировать v1 → v2.

Для каждой legacy позиции показывать исходные `sku` и `quantity` (и исходный ID — только если он нужен для диагностики, не обязательно в публичном UI), плюс понятное сообщение:

`This saved item is from an older enquiry list and needs to be added again from the current catalogue.`

### Явное ручное удаление

Владелец ранее утвердил возможность вручную удалить unresolved legacy position. Это единственная допустимая операция над v1 в этом этапе и только по прямому нажатию пользователя.

Требования:
- никаких автоматических записей/очистки v1 при hydration, resolve, retry или действиях с v2;
- удалить ровно выбранную legacy запись, сохранив все остальные записи и порядок;
- если v1 envelope malformed, unknown version или не может быть безопасно разобран — disable remove и показать, что данные требуют восстановления; не переписывать исходное значение;
- если несколько legacy lines имеют одинаковый SKU/productId, удаление одной строки не должно удалить все совпадающие строки: идентифицировать строку стабильным исходным индексом/opaque key в parsed snapshot;
- при storage write failure сохранить исходный v1 bytes, сообщить о невозможности сохранения и не показывать удаление как успешное;
- не удалять v1 key целиком, если удалена последняя позиция: сохранить валидный envelope version 1 с `items: []`, чтобы не менять смысл версии/наличия ключа;
- не использовать SKU для выбора записи при удалении;
- не менять v1 store API широко: добавить узкую explicit remove helper только если это необходимо и покрыть тестами.

Если реализация безопасного точечного удаления невозможна без изменения общей семантики v1 store или потери неизвестных полей/записей, остановиться и запросить решение владельца. Не делать best-effort rewrite.

## 7. Повреждённое и недоступное хранилище

Использовать статусы, добавленные в BE-08.5.5.4.1:
- `not_hydrated`;
- `ready`;
- `legacy_present`;
- `corrupt`;
- `storage_unavailable`;
- persistent/diagnostic flags v1/v2.

Правила:
- `corrupt` никогда не отображать как пустую корзину;
- не предлагать автоматический reset;
- не перезаписывать оригинальные bytes;
- `storage_unavailable` должен честно сообщать, что изменения/состояние нельзя гарантированно сохранить между посещениями;
- если один источник (v1 или v2) корректен, его read-only данные можно показать, но общий error state другого источника не скрывать;
- никакие операции над v2 в этом этапе не активировать, кроме уже необходимых read-only hydration/subscription.

Recovery/export/reset flow не реализовывать.

## 9. Тестирование

Запускать через frontend Docker Compose workflow, определённый `AGENTS.md`. Не предполагать, что локальный npm workflow допустим.

### API adapter / resolve

- Пустой список не вызывает API.
- 1 UUID и несколько UUID — один batch request.
- Порядок response корректно сопоставляется с исходными UUID.
- `available` требует корректный Product DTO и совпадение `response.id === product.id === requested UUID`.
- `unavailable` отображается отдельно.
- Повреждённый response / дубли / missing IDs / unexpected IDs не приводят к частичному ложному успеху.
- 422/429/500/503/network/timeout — `resolve_error`, все store items сохранены.
- Retry повторяет batch resolve без записи/изменения store.
- Нет N+1 запросов с frontend.
- Нет обращений к mock catalogue.

### Cart display

- Только v2 available.
- Несколько available в исходном порядке.
- Смешанные available/unavailable.
- `priceAed: null` → `Price on enquiry`.
- Decimal string не преобразуется в float для арифметики.
- `cardImage: null` → placeholder.
- Resolve 503 → отдельное временное error state и Retry.
- Empty v2 + empty v1.
- Смешанный v1/v2 — две отдельные секции.

### Legacy

- Fixture ID не разрешается и не маппится.
- UUID-похожий legacy ID не мигрирует.
- Одинаковые SKU остаются отдельными legacy rows.
- Удаление одной строки удаляет только её, сохраняя остальные и порядок.
- Malformed/unknown v1 — remove disabled, исходные bytes не меняются.
- Storage write failure — исходное значение не теряется и UI не показывает ложный success.
- Ни один legacy item не отправляется в submit.

### Store / guards / regression

- v2 corrupt и v1 corrupt состояния не выглядят пустыми.
- storage unavailable отображается честно.
- SSR не обращается к localStorage.
- Product/Cart action guards остаются disabled.
- Solutions guard остаётся disabled и не вызывает enquiry store.
- Contact/Catalogue Enquiry tests остаются зелёными.
- Вызовов `submitEnquiry` для Product/Cart не появляется.

### Build

- Focused tests.
- Все релевантные frontend regression suites.
- Typecheck.
- Production build с `NODE_ENV=production`, если это предписано текущим Compose setup/AGENTS.md.
- `git diff --check`.
