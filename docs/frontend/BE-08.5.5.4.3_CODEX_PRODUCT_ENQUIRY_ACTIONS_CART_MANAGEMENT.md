# BE-08.5.5.4.3 — Product Enquiry Actions & Cart Management

**Тип этапа:** frontend Product Enquiry actions and UUID Cart v2 management  
**Статус:** ТЗ подготовлено; реализация не начиналась  
**Проект:** Pots & Planters 2.0  
**Язык:** русский

## 1. Цель

Восстановить пользовательский сценарий добавления реальных товаров в Enquiry Cart и управления UUID-позициями v2:

- Add to Enquiry на Product details;
- Add to Enquiry на тех Product cards, где такое действие существовало до отключения и его восстановление не меняет публичный дизайн;
- увеличение количества при повторном добавлении того же UUID;
- изменение quantity и удаление позиции в `/cart`;
- корректная обработка недоступных товаров, ошибок API, corrupt storage и storage write failures.

Корзина должна использовать исключительно Product `public_id` UUID и существующий `potsandplanters.enquiry.v2`.

**Отправка Product Enquiry и Cart Enquiry в этом этапе НЕ реализуется и НЕ включается.** Submit CTA, формы и вызовы submit endpoint остаются отключёнными. Этот этап восстанавливает сбор и редактирование корзины, но не отправку заявки.

## 3. Границы и feature gating

### 3.1. Разрешённая активация

На этом этапе разрешено включить **только добавление и редактирование Product Enquiry Cart в локальной dev-среде** после аудита существующих feature flags.

- Использовать отдельный Product/Cart frontend flag, если он уже существует.
- Если отдельного флага нет, добавить явный `NEXT_PUBLIC_PRODUCT_ENQUIRIES_ENABLED`, по умолчанию `false`, и включить его только в локальном `compose.dev.yaml`/утверждённой dev-конфигурации проекта.
- Не переиспользовать общий `NEXT_PUBLIC_ENQUIRIES_ENABLED`, если он включает Contact/Catalogue Download.
- Не менять staging/production env, Dokploy или deployment configuration.
- Если репозиторий не позволяет надёжно разделить local dev и production flag, остановиться и запросить решение владельца.

### 3.2. Что остаётся выключенным

- Backend `product_enquiry` и `cart_enquiry` flags остаются `false`.
- Product Enquiry submit и Cart Enquiry submit не подключать.
- Не показывать активную Submit Enquiry/Send Request кнопку.
- Не вызывать `POST /api/v1/enquiries` из Product/Cart UI.
- Не менять Contact/Catalogue Enquiry и их работающий submit.
- Не активировать Product/Cart backend endpoint через конфигурацию или тестовые shortcuts.

Feature gate этого этапа разрешает только локальное добавление и редактирование позиций. Это не разрешение на отправку заявки.

## 4. Идентификатор и storage contract

Использовать только утверждённую v2 schema:

- key: `potsandplanters.enquiry.v2`;
- envelope: `{ "version": 2, "items": [{ "productId": "<public UUID>", "quantity": 1 }] }`;
- максимум 100 уникальных UUID;
- quantity: integer от 1 до 999999;
- дедупликация только по UUID;
- повторное добавление того же UUID увеличивает quantity;
- одинаковый SKU у разных UUID — разные позиции.

Не менять v2 schema без отдельного согласования.

Legacy v1:
- остаётся отдельной unresolved секцией;
- не переносится автоматически;
- не добавляется в submit;
- существующее точечное ручное удаление, принятое в BE-08.5.5.4.2, сохраняется;
- add/update/remove v2 не изменяют v1.

## 5. Add to Enquiry — Product details и карточки

### 5.1. Источник UUID

Использовать `public_id`, возвращаемый текущим Laravel Product API DTO. Проверить точное поле в исходниках; не предполагать, что поле называется `id`, если DTO/type использует другое имя.

Запрещено:
- использовать slug или SKU как cart identity;
- брать ID из mock fixtures;
- преобразовывать legacy IDs;
- обращаться к старому `catalog.mock.ts`/`catalogRepository` для разрешения Product.

### 5.2. Предварительная проверка доступности

Перед добавлением:
- проверить, что Product API DTO содержит корректный UUID;
- использовать текущие достоверные API данные страницы/карточки;
- если данные потенциально устарели, выполнить `POST /api/v1/products/resolve` для UUID и добавить только при `status: available`;
- не выполнять отдельный resolve для каждого Product card при первоначальной загрузке каталога;
- не создавать N+1 API requests;
- для уже имеющегося в Cart UUID повторное добавление увеличивает quantity, не создаёт дубликат.

Правило выбора момента resolve определить по фактической свежести DTO и текущей архитектуре; зафиксировать в отчёте. Нельзя добавлять позицию по stale/fixture data.

### 5.3. UI поведение

- Восстановить Add to Enquiry только на тех Product detail/card поверхностях, где действие было предусмотрено до временного отключения.
- Не менять визуальную композицию, размеры, типографику и публичный дизайн.
- Использовать существующие кнопки, feedback и notification conventions.
- После успешного добавления показать краткое подтверждение и актуализировать Cart badge.
- При повторном добавлении показать понятное подтверждение обновлённого quantity.
- Во время операции блокировать повторный click, чтобы избежать двойного add из-за одного пользовательского действия.
- Не скрывать ошибки API/storage и не показывать ложный success.
- Если Product unavailable, не добавлять его; показать понятное сообщение и сохранить текущую корзину.

На Product cards не добавлять новые CTA, если в текущем дизайне/исходном поведении их не было. Восстановить только существовавшие действия.

## 6. Cart management

Подключить к `/cart` controls для UUID v2 rows:

- увеличить quantity;
- уменьшить quantity, но не ниже 1;
- ввести quantity вручную только если существующий UI уже предусматривает такой control; иначе использовать текущие controls;
- удалить конкретную UUID позицию;
- сохранять порядок остальных позиций;
- обновлять header Cart badge/preview без перезагрузки.

Для `unavailable` позиции:
- сохранять строку в storage;
- показывать её явно;
- разрешать удалить;
- quantity management может быть отключён, если товар недоступен;
- не удалять автоматически.

Для `resolve_error`:
- сохранять всю корзину;
- оставить Retry;
- не позволять ошибке API превратиться в unavailable или empty cart;
- изменение quantity/removal можно разрешить только если v2 store hydrated, валиден и write path надёжен; если storage unavailable/corrupt — все destructive/edit actions блокировать с понятным сообщением.

Для legacy v1:
- сохранить существующее отображение и точечное удаление;
- не показывать controls изменения quantity, если это потребует небезопасной модификации v1;
- не объединять с v2;
- не разрешать legacy items участвовать в Product/Cart submission.

### 6.1. Лимиты и ошибки

- Максимум 100 уникальных UUID.
- Quantity 1..999999.
- При добавлении 101-го уникального товара показать понятную ошибку, не менять storage.
- При quantity overflow не менять storage.
- Remove неизвестного UUID возвращает typed failure/безопасный no-op, без удаления другой позиции.
- При `corrupt` или `storage_unavailable` не заявлять об успешном изменении.
- Ошибки `setItem`, read-back mismatch и stale snapshot показывать через существующий feedback pattern.
- Не очищать корзину после любого сбоя.

## 7. Cart badge и header preview

Переиспользовать текущую реализацию BE-08.5.5.4.2.

- Badge считает число уникальных UUID строк v2 либо суммарное quantity — сохранить фактическую принятую семантику текущего UI, не менять её без необходимости.
- Не включать legacy v1 позиции в v2 count, если это ранее не было явно согласовано.
- Header preview не должен резолвить товары через mock.
- После add/update/remove синхронизировать страницу Cart и Header без полной перезагрузки.
- Корректно обрабатывать `storage` event между вкладками.
- Не запускать дублирующий resolve при каждом quantity change; resolve зависит от набора UUID, а не от quantity.

## 9. Тестирование

Запускать frontend workflow через Docker Compose согласно `AGENTS.md`.

### Store operations

- add UUID;
- повторный add того же UUID увеличивает quantity;
- одинаковый SKU у разных UUID не объединяет позиции;
- set/increment/decrement quantity;
- нижняя и верхняя границы quantity;
- remove удаляет только выбранный UUID;
- max 100 уникальных строк;
- corrupt/storage unavailable блокируют изменение;
- storage write/read-back failures не дают ложного success;
- v1 bytes и содержимое не меняются при v2 operations.

### Product actions

- Product details add использует реальный UUID;
- card add (только если существовал ранее) использует UUID;
- stale/unavailable Product не добавляется;
- repeated click не удваивает одну операцию;
- repeated deliberate add обновляет quantity;
- API/storage failure показывает ошибку;
- Cart badge обновляется;
- нет SKU/slug/mock lookup;
- нет N+1 resolve requests.

### Cart management

- available line quantity update/remove;
- unavailable line остаётся и может быть удалена вручную;
- resolve_error сохраняет строки;
- retry не меняет storage;
- две вкладки синхронизируются;
- v1 legacy остаётся отдельно и нетронутым, кроме ранее принятого точечного remove;
- corrupt/storage unavailable не выглядят как пустая корзина.

### Regression and safety

- Product action guard обновлён только для локального Product/Cart add feature gate.
- Solutions guard остаётся выключенным.
- Product/Cart submit guard остаётся выключенным.
- Contact/Catalogue submit regressions проходят.
- Нет новых Product/Cart вызовов `submitEnquiry` или `POST /api/v1/enquiries`.
- Нет SSR обращений к localStorage.
- Нет runtime mock fallback.
- Typecheck, frontend regression suites, production build и `git diff --check` проходят.
