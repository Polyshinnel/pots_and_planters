# BE-08.5.5.5.1 — Product/Cart Enquiry Submit Integration Audit

**Тип этапа:** read-only contract and integration audit  
**Статус:** ТЗ подготовлено; аудит не начинался  
**Проект:** Pots & Planters 2.0  
**Язык:** русский

## 1. Цель

Подготовить точный план подключения frontend Product Enquiry и Cart Enquiry к уже реализованному Laravel Enquiry API v2.

Backend v2 был реализован в BE-08.5.5.3:
- Product Enquiry — одна позиция Product по UUID;
- Cart Enquiry — массив Product UUID + quantity;
- серверная повторная проверка публичной доступности;
- серверные неизменяемые Product snapshots;
- idempotency;
- outbox для Telegram;
- Contact/Catalogue Enquiry v1 сохранены.

Frontend Cart v2 и пользовательские действия приняты после ручной проверки в BE-08.5.5.4.3. Сейчас пользователь может добавлять товары и управлять корзиной, но отправка заявки ещё недоступна.

Цель этого этапа — **только аудит и окончательное согласование frontend submit contract**. Код не менять.

## 3. Что необходимо подтвердить в фактическом контракте

### 3.1. Product Enquiry v2

Установить точный request schema:
- endpoint и HTTP method;
- обязательные contact fields;
- Product UUID field и quantity;
- project/message/notes поля, если поддерживаются;
- idempotency key header/field и формат;
- успешный response schema;
- field validation errors;
- error envelope и requestId;
- rate limits;
- backend feature flag behavior.

Проверить, что frontend отправляет только UUID и quantity как идентификатор/состав заявки. SKU, name, brand, price и image не должны быть источником истины или обязательным клиентским snapshot: Laravel самостоятельно повторно разрешает товар и создаёт snapshot.

### 3.2. Cart Enquiry v2

Подтвердить:
- точную структуру `items`;
- ограничения количества строк и quantity;
- обработку duplicate UUID;
- атомарную проверку всех товаров;
- поведение, если один товар unavailable;
- поведение, если несколько товаров unavailable;
- гарантии, что при отказе не создаётся частичная заявка;
- idempotency и повторный submit.

Нельзя предполагать, что Cart Enquiry может отправить частично доступные позиции. Сверить с кодом и тестами; если это не зафиксировано, вынести вопрос владельцу.

### 3.3. Frontend form contract

Проверить текущую форму Product/Cart Enquiry и утвердить:
- какие contact fields обязательны;
- формат email/phone;
- согласие/consent, если предусмотрено;
- project details/message;
- frontend validation и соответствие Laravel validation;
- loading, success, validation error, unavailable item и network error states;
- доступность формы на Product details и Cart;
- поведение после успешной отправки;
- сохранение корзины при ошибке;
- очистку корзины после успешной отправки (не предполагать автоматически).

### 3.4. Idempotency и повторные попытки

Установить:
- когда создаётся idempotency key;
- как долго и где он хранится;
- должен ли один key повторно использоваться при network timeout;
- когда создаётся новый key;
- как UI различает «запрос не дошёл» и «заявка принята, но ответ потерян».

Ключевое требование: повторный клик или сетевой retry не должен создавать дублирующие Enquiries.

### 3.5. Snapshots, Filament и Telegram

Сверить фактический snapshot:
- product UUID;
- name, brand, SKU;
- price/currency;
- quantity;
- category и другие сохранённые поля;
- nullable price behavior.

Подтвердить, что Filament и Telegram используют snapshot, а не текущий Product relation для исторических данных. Установить, какие проверки доставки и админского отображения уже прошли и какие требуют ручного smoke.

## 4. Feature flags и среда

Фактические значения проверить read-only, ничего не меняя.

Ожидаемое текущее состояние:
- `NEXT_PUBLIC_PRODUCT_ENQUIRIES_ENABLED` может быть включён только в локальном Compose для add/manage;
- frontend submit пока отключён;
- backend `product_enabled=false`;
- backend `cart_enabled=false`;
- Contact/Catalogue Enquiry продолжает работать независимо.

Предложить отдельное разделение:
1. Product/Cart add & manage;
2. Product/Cart submit UI;
3. backend Product/Cart submit acceptance.

Не включать flags в рамках аудита. Не менять `.env`, Compose, deployment или runtime configuration.

## 6. Строгие ограничения

- Read-only: не менять application code, tests, migrations, config, env, Compose или docs, кроме нового audit report.
- Не запускать миграции и не создавать Enquiry records.
- Не вызывать реальные submit endpoints.
- Не включать frontend/backend feature flags.
- Не менять Contact/Catalogue Enquiry.
- Не менять Solutions.
- Не выполнять production/staging операции.
- Не запускать тесты, требующие записи в БД или реальной Telegram доставки. Для аудита достаточно прочитать существующие тесты; любые дополнительные read-only проверки описать отдельно и согласовать.
