## 2. Подтверждённые API contracts

| Сценарий | Request | Success | Контрактные ограничения |
|---|---|---|---|
| Product v2 | `POST /api/v1/enquiries`, JSON: `type: "product_enquiry"`, `apiVersion: 2`, `product: {productId: <public UUID>, quantity: integer}`, `name`, `phone`, `email`; optional `company`, nullable/optional `message`, `source: {pagePath?, placement?}`. Header `Idempotency-Key`. | Новый: HTTP 201; replay: HTTP 200. `data: {status:"persisted", enquiryId:<UUID>, notificationStatus:<string>}`; `Cache-Control: no-store`. | Product object разрешает только `productId,quantity`. Количество 1..999999. Никаких SKU/name/brand/price/image/attributes от клиента. Неизвестные поля отклоняются 422. |
| Cart v2 | Тот же endpoint/common fields и header; `type: "cart_enquiry"`, `apiVersion: 2`, `items: [{productId:<public UUID>, quantity: integer}, ...]`. | Тот же success envelope и коды статусов. | 1..100 строк; UUID обязателен и уникален без учёта регистра; quantity 1..999999. Каждый item разрешает только UUID и quantity. SKU может совпадать у разных UUID и не является идентификатором. |

Общие правила Laravel: `name` required string max 200; `phone` required string max 64 (форматного серверного правила нет); `email` required `email:rfc`, max 254; `company` optional nullable string max 200; `message` для Product/Cart optional nullable string max 5000 (для `contact` required); `source.pagePath` optional path от одного `/`, max 2048, без query/hash; `source.placement` optional string max 200. `website` — honeypot: заполненное значение отклоняется. Contact и Catalogue v1 остаются на тех же endpoint и валидации.

`Idempotency-Key` обязателен в header, regex `^[A-Za-z0-9._:-]{16,128}$`. Успех хранит hash ключа и канонического payload hash; срок — 24 часа. Тот же ключ + тот же payload replay-ит ту же заявку без новых enquiry/item/outbox rows; тот же ключ с другим payload даёт HTTP 409 `idempotency_conflict`. После истечения запись ключа может быть заменена. Ошибки SQL при сохранении дают 503 `persistence_unavailable` с указанием повторить с тем же ключом.

Ошибки API имеют envelope `error: {code, message, requestId, ...}`. Laravel validation даёт 422 `validation_failed` с `error.fields` (mapping field → массив сообщений); rate limit — 429 `rate_limited`; выключенный Product/Cart backend gate — 404 `feature_unavailable`; недоступный товар — 422 `products_unavailable` и `error.products` UUIDs; idempotency conflict — 409; persistence — 503. JSON body обязателен, максимальный body 65536 bytes (`400 json_required`, `400 invalid_json`, `413 payload_too_large`). Enquiry throttle — 5/min и 30/hour на IP; Product resolve — 60/min на IP.

## 3. Availability, atomicity и snapshots

Перед snapshot service в одной транзакции блокирует Product rows в упорядоченном по UUID порядке, затем Brand, Supplier и primary Category rows. Проверяет Product `published`, существующий Brand, Supplier `is_active`, опубликованную primary Category. Inventory/stock поле не проверяется; «available» здесь означает публичную доступность сайта, не остаток на складе.

Неизвестный UUID и скрытые/архивные товары маскируются одинаково как unavailable. Для Cart при одной или нескольких недоступных позициях весь submit отклоняется 422 `products_unavailable`; в `error.products` перечисляются недоступные входные UUID без дубликатов. Транзакция не создаёт частичную заявку, items или outbox. Существующие тесты прямо подтверждают этот случай. При гонке после frontend resolve submit остаётся окончательным авторитетом; серверные блокировки и проверка повторяются перед записью.

В `enquiry_items` сохраняются UUID Product и Brand, SKU, Brand name, quantity, nullable decimal `unit_price_aed` (DECIMAL(15,4), string без float-преобразования), `currency=AED`, availability boolean, `snapshot_at` и JSON `product_snapshot` из разрешённого `ProductListData`. В JSON входят публичные Product поля: id/UUID, slug, SKU, name, Brand, nullable price, currency, category IDs, primary category/path, canonical path, изображение и выбранные карточные спецификации. Цена null остаётся null; отображается `Price on enquiry`. Новые колонки nullable, старые строки не backfill-ятся.

В транзакции с Enquiry и snapshots создаются outbox event, recipient delivery snapshots и idempotency row. При выключенных Telegram notifications событие сохраняется как `skipped_disabled`; включённые notifications без recipients остаются `pending_no_recipients`. Dispatcher и job доставляют асинхронно через Redis; повторные попытки и состояние доставки хранятся отдельно. Telegram formatter строит текст из `product_snapshot`, `sku_snapshot`, `brand_name_snapshot`, quantity и сохранённой цены, не загружая актуальный Product. Filament Enquiry resource также читает item snapshots, показывает исторические имя/бренд/SKU/quantity и `Price on enquiry` для null цены. Существующие API, Admin и Delivery tests это подтверждают.

Автотесты подтверждают функциональные сценарии; конкурентный stress test не запускался. В отчёте BE-08.5.5.3 указано: EnquiriesApi 18/108, API+Filament+Telegram/outbox 29/176; полный Laravel suite имел 202 passed и один воспроизводимый ранее media transparency failure. Реальная Telegram доставка не была частью тех тестов. Filament browser/manual smoke и реальная отправка Telegram требуют отдельной ручной приёмки.

## 4. Frontend и расхождения

### Contact/Product форма

Product modal (`ProductEnquiryForm`) показывает обязательные Name, Phone, Email; Company скрыта; Message необязателен; есть Privacy Policy notice, но отдельного consent checkbox нет. UI validator требует имя, проверяет phone как 7–15 цифр и допускает только `+`, digits, spaces, parentheses, dot, dash; email проверяется простым `local@domain.tld` regex. Client limits: name 200, phone 60, email 254, company 200, message 5000. Это в целом укладывается в backend limits, но frontend phone-format policy строже (backend принимает произвольную строку до 64), а email parser не эквивалентен RFC validator. Это нужно учесть в общей проверке 422 и не объявлять валидаторы идентичными.

Сейчас Product form передаёт старый объект `{type, name, phone, email, productId, sku, quantity, message?}` через generic Lead adapter. Он не содержит `apiVersion:2` и вложенного `product`; SKU не разрешён бекендом. Submit button отключён явным guard и текст прямо говорит, что онлайн отправка недоступна. Product Add action включает только local cart add/manage и resolve; это не submit gate.

### Cart форма и v2 store

Фактическая `/cart` страница использует `EnquiryCartLayout` + `ResolvedCart` и отдельный UUID-only store `potsandplanters.enquiry.v2`: envelope version 2, items `{productId, quantity}`, 100 строк максимум, quantity 1..999999. Перед отображением строк вызывается существующий `POST /api/v1/products/resolve`; порядок входа сохраняется, доступные записи возвращают ProductList DTO, неизвестные/непубличные — только `{id,status:"unavailable"}`. Resolve ошибки не очищают localStorage. Старый v1 state отображается отдельными legacy строками и не конвертируется автоматически; corrupt/unknown state блокирует изменения.

Cart checkout сейчас содержит disabled-поля Name, Phone, Email, Company/Project name и Comments (все без validation wiring); отправляющая кнопка disabled. В целевой backend DTO `comments` следует отправлять как `message`. Ранее существующий модуль `lib/enquiry/submission.ts` строит v1 payload с `version:1`, contact object и строками с lineKey/SKU/name/attributes/price; он опирается на legacy SKU identity/mock line resolver и не вызывается актуальным `/cart` экраном. Нельзя подключать его напрямую к v2 API.

Product modal frontend phone maxLength 60; Cart placeholder сейчас не ограничивает ввод. Сервер принимает `phone` max64 без формата. Требуется единое решение validation UX и сообщения по `error.fields`; не переносить клиентские Product display данные в submit.

### Общий submit adapter / idempotency

Contact и Catalogue используют `frontend/src/lib/forms/enquiries.client.ts` → `POST /api/v1/enquiries`; adapter добавляет Idempotency-Key, проверяет persisted response и разбирает backend `error.fields`. `useLeadForm` формирует ключ при первой фактической отправке; хранит его только в памяти компонента вместе с JSON fingerprint payload. Неопределённый network/5xx retry с неизменным payload при живом компоненте сохраняет тот же key; изменённый payload создаёт другой; 409 сбрасывает старый key. Срок backend ключа — 24 часа. После успешного persisted форма завершается. Перезагрузка страницы/размонтирование стирает frontend key, поэтому повтор после потери ответа и reload уже не гарантирован этим механизмом от дубля. Для Product/Cart нужно решить и реализовать durable попытку или UI, который сохраняет идентичность attempt при reload в допустимом scope; ключ должен быть привязан к неизменному payload и использоваться повторно после timeout. Нельзя выдавать network timeout за доказательство, что заявка не принята.

Текущий `submitEnquiry` общий gate `NEXT_PUBLIC_ENQUIRIES_ENABLED` подходит Contact/Catalogue; Product component дополнительно hard-disables UI. Нет frontend отдельного Product submit и Cart submit gate. Product add/manage flag `NEXT_PUBLIC_PRODUCT_ENQUIRIES_ENABLED` не разрешает submit. Backend gates независимы: `PRODUCT_ENQUIRIES_ENABLED` и `CART_ENQUIRIES_ENABLED`, оба default false; Compose env их не устанавливает. В `compose.dev.yaml` Product add/manage flag установлен true, а `NEXT_PUBLIC_ENQUIRIES_ENABLED=true` позволяет существующие Contact/Catalogue формы. В локальном `.env` также виден `NEXT_PUBLIC_ENQUIRIES_ENABLED=true`. Отдельного frontend Cart flag нет. Это read-only конфигурация; значения не менялись. Значение runtime backend `.env` в отчёт не раскрывалось: исходник/config default и Compose отсутствие переменных подтверждают только конфигурационный default; фактический контейнерный runtime env этим аудитом не запрашивался. Production/staging не исследовались.

## 5. Несовместимости/решения перед реализацией

1. Product UI payload должен быть переведён на `apiVersion:2` + top-level `product:{productId,quantity}`. Удалить SKU и прочие display fields с границы запроса; отправлять common contact поля и опциональный `message`/`source`.
2. Cart должен строить новый payload непосредственно из UUID v2 store: `type,apiVersion,name,phone,email,company?,message?,source?,items:[{productId,quantity}]`. Удалить dependency на SKU uniqueness, mock line snapshots и `version:1` payload из submit path.
3. Перед submit cart повторно resolve всех UUID; при resolve error/unavailable блокировать submit, оставлять строки и давать удалить/повторить. В любом случае backend повторяет atomic validation. Product submit также должен проверить доступность текущего UUID для UX.
4. Нужно сопоставить contact field limits и фронтенд/server validation, задать Cart validation/error display, `message` mapping, pending/disabled/success/failure states и решить форму/политику согласия. Текущий policy notice не означает пользовательского consent.
5. Идемпотентность Contact/Catalogue adapter годится как модель, но ее in-memory lifecycle после reload не даёт гарантии повторного ключа для uncertain Product/Cart attempt. Надо определить safe persistent attempt identity и reset conditions (успех, осознанное изменение содержимого, 409 после показа пользователю).
6. Success не очищает Cart автоматически. Бэкенд отвечает только persisted/enquiryId/status; frontend должен показать результат, сохранить корзину при всех ошибках и согласовать отдельную кнопку очистки/правило после успеха. Сейчас нет реализованного поведения.
7. Решить gates: отдельные frontend add/manage, Product submit, Cart submit; backend acceptance gates Product и Cart остаются независимы. Общий Contact/Catalogue gate не должен активировать их. Никакие flags не включать до отдельного решения.

## 8. Вопросы владельцу

1. Утвердить Cart `comments → message` и Product optional message, либо определить отдельный project/details field (backend сейчас хранит только `message`).
2. Оставить текущую строгую frontend phone policy 7–15 digits, согласовать общий формат и max 60 vs server 64; определить отображение backend validation errors.
3. Требуется ли явный consent checkbox или достаточно Privacy Policy notice? Текущий backend не принимает/не хранит consent field.
4. Как восстанавливать uncertain submit после reload: хранить key+payload fingerprint/черновик в sessionStorage/localStorage, или просить владельца пользователя начать новую попытку после объяснения риска? Какой срок локального хранения приемлем?
5. После persisted success корзина остаётся; нужна ли явная кнопка очистить, автоматическая очистка или сохранение выбора? Рекомендация аудита: не очищать автоматически, пока пользователь не подтвердил/не выбрал clear.
6. Подтвердить отдельные gates: frontend Product add/manage (уже есть), Product submit, Cart submit; backend Product submit, Cart submit. Разрешать их включение только отдельным чекпоинтом?
7. Подтвердить ручной smoke scope: можно ли создать/удалить тестовую заявку в локальной dev среде на изолированной test DB после реализации; Telegram smoke только fake/без реальной отправки?
