**Проект:** Pots & Planters 2.0

## 1. Цель

Подготовить общий frontend-инфраструктурный слой для Product Enquiry v2 и Cart Enquiry v2:
- строго типизированные request/response DTO;
- отдельные Product и Cart v2 adapter methods;
- единая обработка success/error envelope;
- отображение field errors и requestId в типизированном результате;
- устойчивый idempotency attempt lifecycle с `sessionStorage`, переживающий reload той же вкладки;
- contract/unit tests, подтверждающие соответствие Laravel.

На этом этапе **не подключать ProductEnquiryForm или Cart checkout к adapter**. Не включать отправку заявок и не менять пользовательское поведение. Submit gates остаются выключенными. Это инфраструктурный этап, следующий этап подключит Product UI.

## 3. Точный контракт

Endpoint обоих методов:

`POST /api/v1/enquiries`

Header:

`Idempotency-Key: <valid key>`

### 3.1. Product request

```ts
type ProductEnquiryV2Request = {
  type: "product_enquiry";
  apiVersion: 2;
  product: {
    productId: string; // Product public UUID
    quantity: number; // integer 1..999999
  };
  name: string;
  phone: string;
  email: string;
  company?: string | null;
  message?: string | null;
  source?: {
    pagePath?: string;
    placement?: string;
  };
};
```

### 3.2. Cart request

```ts
type CartEnquiryV2Request = {
  type: "cart_enquiry";
  apiVersion: 2;
  items: Array<{
    productId: string; // unique Product public UUID
    quantity: number; // integer 1..999999
  }>; // 1..100
  name: string;
  phone: string;
  email: string;
  company?: string | null;
  message?: string | null;
  source?: {
    pagePath?: string;
    placement?: string;
  };
};
```

Не отправлять SKU, name/brand/price/image/specifications Product, local display snapshots, legacy line IDs или внутренние DB IDs.

### 3.3. Response

Успех:
- 201 — новая Enquiry;
- 200 — replay;
- `data.status === "persisted"`;
- `data.enquiryId` UUID;
- `data.notificationStatus` string;
- `Cache-Control: no-store`.

Ошибки:
- 422 `validation_failed` + `error.fields`;
- 422 `products_unavailable` + `error.products`;
- 409 `idempotency_conflict`;
- 429 `rate_limited`;
- 404 `feature_unavailable`;
- 503 `persistence_unavailable`;
- malformed/unknown response — отдельная transport/protocol failure, не success.

Общий envelope содержит `error.code`, `error.message`, `error.requestId`, опционально `error.fields` и `error.products`.

### 3.4. Backend validation boundaries

- name required, max 200;
- phone required, max 64;
- email required RFC, max 254;
- company optional nullable max 200;
- message optional nullable max 5000;
- source.pagePath optional, starts with one `/`, max 2048, no query/hash;
- source.placement optional max 200;
- body max 65536;
- Product/Cart reject unknown fields;
- idempotency header regex `^[A-Za-z0-9._:-]{16,128}$`;
- Cart 1..100 unique UUID rows, quantity 1..999999.

Frontend shared adapter должен валидировать типы/shape до отправки, но не подменять Laravel validation.

## 4. Shared adapter architecture

Использовать существующий API client/fetch conventions и error parsing из `enquiries.client.ts`, не ломая Contact/Catalogue flow.

Добавить отдельные методы, например:
- `submitProductEnquiryV2(payload, idempotencyKey)`;
- `submitCartEnquiryV2(payload, idempotencyKey)`.

Имена адаптировать к текущим conventions.

Требования:
1. Один endpoint и единый общий transport.
2. Product/Cart DTO — discriminated types, не generic loose object.
3. `Idempotency-Key` обязателен; adapter не должен сам незаметно создавать новый ключ при retry.
4. Сериализовать только разрешённые поля.
5. Не отправлять `undefined` как некорректные поля; optional fields либо отсутствуют, либо соответствуют фактическому nullable contract.
6. Разбирать 200/201 только если `data.status === "persisted"` и `enquiryId` корректен.
7. Сохранять `notificationStatus`, но не трактовать `skipped_disabled`/`pending_no_recipients` как неуспешную persistence.
8. Для 422 вернуть field errors и unavailable UUIDs типизированно.
9. Для 409 вернуть отдельный `idempotency_conflict`.
10. Для 429/503/network/timeout вернуть retryable/uncertain outcome с requestId, если он получен.
11. Не трактовать timeout как доказательство, что Enquiry не создана.
12. Не менять существующие Contact/Catalogue adapter semantics и tests.

Adapter не должен обращаться к localStorage/sessionStorage. Idempotency lifecycle находится в отдельном модуле.

## 5. Idempotency attempt manager

Реализовать чистый доменный менеджер + узкую sessionStorage abstraction.

### 5.1. Session storage record

Использовать отдельный namespace/key, например:

`potsandplanters.enquiry.submit-attempt.v2`

Record содержит только:
- `version: 1`;
- `attempts`: изолированные записи по `product_enquiry` и `cart_enquiry`;
- `key`;
- `payloadFingerprint`;
- `createdAt` (Unix ms или ISO, единый формат);
- `status`: `pending | uncertain | persisted`;
- для persisted — `enquiryId` и `persistedAt`, если нужно для UI recovery.

**Запрещено сохранять** name, phone, email, company, message, полный payload, Product DTO, SKU, цены, изображения или иные PII/display data.

### 5.2. Fingerprint

- Fingerprint вычисляется от канонического JSON payload, который будет отправлен backend.
- Включает все поля, влияющие на payload hash: type, apiVersion, Product UUID/quantity или Cart items, contact fields, message/company/source.
- Не включает Idempotency-Key.
- Канонизация должна быть детерминированной: стабильный порядок object keys; для Cart сохранять семантический порядок items, не сортировать позиции, если backend hash учитывает порядок.
- Использовать Web Crypto SHA-256 в browser runtime, если совместимо с существующей поддержкой браузеров; иначе остановиться и согласовать безопасный механизм. Не использовать слабый/самодельный hash.
- Не выполнять fingerprint с доступом к browser APIs при SSR/module initialization.

### 5.3. Создание и reuse попытки

Менеджер получает `kind` и fingerprint:
- нет attempt → создать cryptographically strong key, сохранить до fetch, вернуть attempt;
- существующий `pending/uncertain`, fingerprint тот же, возраст <24h → вернуть тот же key;
- существующий attempt с другим fingerprint → вернуть typed `payload_changed_requires_confirmation`, не заменять автоматически;
- attempt старше 24h и outcome не persisted → `attempt_expired_unknown_outcome`, не retry старым ключом и не создавать новый молча;
- persisted attempt для того же fingerprint → `already_persisted`, не отправлять повторно;
- persisted attempt для другого fingerprint → разрешить подготовить новую попытку только через явное действие `startNewAttempt`, с подтверждением пользователя на уровне будущего UI.

### 5.4. Статусы

- Перед сетевым запросом записать `pending` в sessionStorage и убедиться, что запись прошла.
- После network error, timeout, 5xx, 429 или неизвестного transport outcome отметить `uncertain`; сохранить тот же key.
- Для 422 validation или products_unavailable исход известен как rejected; попытка не persisted. При исправлении payload fingerprint меняется — менеджер требует явного start new attempt.
- Для 409 сохранить диагностический статус conflict и вернуть typed result; новый key разрешать только через явное `startNewAttempt`.
- Для подтверждённого 200/201 persisted сохранить `persisted` + enquiryId прежде чем UI сможет показать success.
- Если sessionStorage недоступен, не отправлять Product/Cart submit: иначе невозможно гарантировать key reuse после reload. Вернуть `attempt_storage_unavailable`.
- Если запись/read-back attempt metadata не удалась, не отправлять запрос.
- Не удалять attempt сразу после success; сохранить persisted marker в sessionStorage, чтобы reload не привёл к повторной отправке. Допускается очистка старых persisted records по сроку после 24h при следующем безопасном чтении.
- Product и Cart attempt slots независимы.

### 5.5. Явные операции

Предоставить typed operations, например:
- `getAttempt(kind, fingerprint)`;
- `prepareAttempt(kind, fingerprint)`;
- `markUncertain(kind, key)`;
- `markRejected(kind, key, reason)`;
- `markPersisted(kind, key, enquiryId)`;
- `startNewAttempt(kind, fingerprint, explicitConfirmation)`.

Не предоставлять callback, который автоматически меняет key при любом исключении. Никаких автоматических бесконечных retries.

Для `payload_changed_requires_confirmation`, `attempt_expired_unknown_outcome`, `idempotency_conflict` — только typed failure, UI подключится в следующем этапе.

## 8. Тестирование

Использовать Docker Compose workflow из `AGENTS.md`.

### DTO/adapter tests
- Product payload сериализуется точно и содержит `apiVersion:2`, вложенный `product`.
- Cart payload сериализуется точно и содержит `apiVersion:2`, `items`.
- SKU/name/brand/price/image/specs/client snapshots не отправляются.
- 200/201 persisted success принимаются.
- 200/201 без корректного persisted envelope — protocol error.
- 422 validation maps `error.fields`.
- 422 products_unavailable maps UUID list.
- 409 conflict отдельный.
- 429/503/network/timeout не трактуются как success.
- Contact/Catalogue adapter regression зелёный.

### Attempt manager tests
- key соответствует regex и имеет криптографическую случайность через mock Web Crypto.
- запись выполняется до сетевого запроса (adapter orchestration contract).
- тот же fingerprint <24h повторно использует key.
- другой fingerprint требует explicit confirmation.
- timeout/network/5xx сохраняет key и помечает uncertain.
- reload simulation читает тот же key из sessionStorage.
- persisted marker после reload блокирует повторный submit.
- 409 требует явного startNewAttempt.
- expired unknown attempt не переиспользуется и не заменяется молча.
- sessionStorage disabled/quota/security/read-back mismatch блокируют submit.
- PII и полный payload не появляются в sessionStorage.
- Product и Cart attempt records независимы.
- SSR import не обращается к browser APIs.
- канонический fingerprint стабилен; порядок Cart items сохраняется.
- SHA-256 Web Crypto tests используют deterministic mock.

### Regression/build
- Product add/manage и Cart management остаются рабочими.
- Product/Cart submit controls по-прежнему disabled.
- Solutions guard остаётся disabled.
- Contact/Catalogue submissions не меняют поведение.

- Typecheck, relevant frontend regression suites, production build и `git diff --check` проходят.
