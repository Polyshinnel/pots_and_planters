# BE-08.5.5.5.3 — Product Enquiry Form Integration

**Тип этапа:** frontend Product Enquiry v2 integration  
**Статус:** ТЗ подготовлено; реализация не начиналась  
**Проект:** Pots & Planters 2.0  
**Язык:** русский

## 1. Цель

Подключить существующую Product Enquiry Form на странице товара к реализованному Laravel Product Enquiry v2 через `submit-v2.ts`.

Клиент отправляет заявку на получение персональной цены (*Personal Prices*). Это обычная Product Enquiry, а не заказ и не покупка. Не добавлять оплату, checkout или подтверждение цены.

В этом этапе реализовать только отправку заявки с Product details. Cart Enquiry остаётся следующим отдельным этапом.

## 2. Утверждённый контракт

Использовать:
- `docs/frontend/BE-08.5.5.5_APPROVED_SUBMIT_CONTRACT_ADDENDUM.md`;
- `docs/frontend/BE-08.5.5.5.2_IMPLEMENTATION_REPORT.md`;
- актуальный `frontend/src/lib/enquiry/submit-v2.ts`;
- фактический Laravel request/response contract.

Product request:
- `type: "product_enquiry"`;
- `apiVersion: 2`;
- `product.productId` — только Product public UUID;
- `product.quantity` — целое число 1..999999;
- `name`, `phone`, `email`;
- optional `company`, `message`, `source`.

Endpoint: `POST /api/v1/enquiries`.

Header: `Idempotency-Key`.

Не отправлять SKU, slug, internal DB ID, product name, brand, price, image или client-side snapshot. Laravel самостоятельно повторно проверяет доступность товара и формирует snapshot.

## 4. Подключение Product Enquiry Form

### 4.1. Использовать существующий UI

- Подключить существующую `ProductEnquiryForm` к shared v2 adapter.
- Сохранить текущий публичный дизайн, композицию, тексты и расположение формы, насколько это возможно.
- Не делать редизайн и не добавлять новые поля без необходимости.
- Не менять Product cards, Cart UI, Solutions или Contact/Catalogue forms.
- Не создавать отдельную альтернативную форму, если существующую можно подключить.

### 4.2. Payload

Формировать Product Enquiry v2 payload:
- Product UUID из авторитетного Product API DTO;
- quantity из существующего quantity control, если он есть; иначе `1`;
- name, phone, email;
- company и message только если эти поля уже есть в текущей форме;
- `source.pagePath` — текущий pathname без query/hash;
- `source.placement: "product_detail"`.

Не включать пустые необязательные поля, если Laravel contract ожидает omission; не отправлять неизвестные поля.

### 4.3. Валидация

Использовать утверждённые правила:
- name required, max 200;
- phone max 64; допустимы `+`, цифры, пробелы, скобки, точка и дефис; после удаления форматирующих символов 7–15 цифр;
- email required, max 254, клиентская проверка формата;
- company optional max 200;
- message optional max 5000.

Laravel остаётся авторитетной стороной валидации. Отображать `422 validation_failed` рядом с соответствующими полями. Не дублировать противоречащие друг другу правила в нескольких местах.

Privacy Policy notice сохранить. Не добавлять consent checkbox или consent payload: backend не принимает и не сохраняет юридически значимое согласие.

### 4.4. Submit lifecycle

Подключить `submit-v2.ts`:
1. Перед запросом подготовить/reuse Product attempt через Idempotency Attempt Manager.
2. Убедиться, что attempt metadata успешно сохранена в `sessionStorage` до сетевого запроса.
3. Отправить Product v2 request с `Idempotency-Key`.
4. Блокировать повторный submit во время активного запроса.
5. Не генерировать новый key при timeout/network/5xx/429.
6. При reload и неизменённом payload восстановить существующую попытку и использовать тот же key.
7. При изменённом payload, 409 или expired unknown attempt показать понятное сообщение и потребовать явного действия пользователя для новой попытки.
8. Не выполнять автоматические бесконечные retry.
9. При storage unavailable не отправлять заявку и объяснить пользователю, что безопасная отправка сейчас невозможна.

### 4.5. UI states

Реализовать понятные состояния:
- idle;
- submitting;
- persisted success;
- validation error;
- product unavailable;
- rate limited;
- temporary service/network error / uncertain outcome;
- idempotency conflict;
- attempt expired / payload changed;
- attempt storage unavailable.

Success показывать только при корректном API response:
- HTTP 200/201;
- `data.status === "persisted"`;
- корректный `data.enquiryId`.

Показать подтверждение, что запрос на персональную цену отправлен, и reference/enquiry ID. Не утверждать, что цена уже рассчитана или заказ подтверждён. `notificationStatus` не должен менять статус persistence: сохранённая заявка остаётся успешной даже при отложенной Telegram доставке.

После persisted success:
- заблокировать повторную отправку того же Product payload;
- показать подтверждение и номер заявки;
- позволить пользователю явно начать новую заявку, если это предусмотрено текущим UX;
- не очищать и не менять Cart v2 или legacy v1.

Для `422 products_unavailable`:
- показать, что товар сейчас недоступен для запроса;
- не удалять товар из Cart;
- не подменять его другим;
- предложить вернуться к каталогу/обновить страницу, используя существующие UI conventions.

Для network/timeout/5xx:
- явно объяснить, что результат отправки пока неизвестен;
- предложить повторить проверку/отправку с тем же сохранённым ключом;
- не сообщать, что заявка точно не создана.

## 5. Feature flags и локальная активация

Владелец разрешил подключить и включить Product Enquiry Form для локальной проверки.

Разрешено:
- добавить/использовать отдельный `NEXT_PUBLIC_PRODUCT_ENQUIRY_SUBMIT_ENABLED`;
- включить его только в локальной dev Compose configuration;
- включить backend `PRODUCT_ENQUIRIES_ENABLED` только в локальной dev/test среде, необходимой для проверки Product Enquiry;
- использовать `potsandplanters_test` для тестов/изолированного smoke, если требуется создание тестовой Enquiry.

Обязательные ограничения:
- Cart frontend submit flag остаётся OFF;
- backend `CART_ENQUIRIES_ENABLED` остаётся OFF;
- Product add/manage flag сохраняет текущее поведение;
- общий Enquiry flag не использовать как замену отдельному Product submit flag;
- Contact/Catalogue flow не менять;
- Solutions не менять;
- staging/production flags, env, deployment и БД не менять;
- не включать реальные Telegram notifications. Использовать существующий безопасный disabled/test transport и подтвердить фактическую конфигурацию до тестового submit.

Если локальный backend flag нельзя включить независимо от Cart/Contact или невозможно исключить реальную Telegram доставку в тесте, остановиться и сообщить блокер, не расширяя активацию.

## 7. Тестирование

Выполнить frontend tests через Docker Compose.

### Component/form tests
- форма использует Product UUID, не SKU/slug/internal ID;
- точный Product v2 payload и `apiVersion: 2`;
- quantity по существующему control или 1;
- required и optional fields;
- phone/email validation;
- field errors отображаются корректно;
- Privacy notice без consent checkbox;
- submit disabled во время запроса;
- success отображается только для persisted response;
- notification status не превращает persisted success в failure.

### Adapter/idempotency integration
- key и metadata записываются до fetch;
- повторный submit с тем же payload использует тот же key;
- reload восстанавливает key;
- timeout/network/429/5xx сохраняют uncertain attempt;
- 422 unavailable не очищает Cart и не создаёт ложный success;
- 409 требует явного действия;
- storage failure блокирует отправку;
- повторный click не создаёт второй запрос.

### Regression/safety
- Cart submit controls остаются выключенными;
- backend Cart flag остаётся OFF;
- Solutions guard остаётся выключенным;
- Contact/Catalogue flows не меняются;
- Product add/manage и Cart management продолжают работать;
- нет mock fallback;
- нет SKU/slug identity;
- нет PII в sessionStorage;
- нет SSR обращений к browser APIs;
- typecheck, соответствующие frontend regression suites, production build и `git diff --check` проходят.

### Локальный API smoke

Если безопасная локальная конфигурация подтверждена:
- использовать только изолированную `potsandplanters_test`;
- отправить одну тестовую Product Enquiry с тестовыми контактными данными;
- проверить 201 и persisted enquiry ID;
- проверить replay с тем же key возвращает ту же Enquiry;
- проверить, что повтор не создаёт дубль;
- проверить, что Telegram не отправляет реальное сообщение;
- не использовать production/staging и реальные персональные данные.

Если API smoke требует изменения данных в обычной dev БД или может отправить реальное сообщение, пропустить его и зафиксировать причину.
