## Изменения

- Подключена существующая ProductEnquiryForm в `frontend/src/components/forms/ProductEnquiryForm.tsx` через `submitWithAttempt` и Idempotency Attempt Manager.
- Запрос: `POST /api/v1/enquiries`, `type: product_enquiry`, `apiVersion: 2`, `product: { productId, quantity }`, `name`, `phone`, `email`, непустое `message` и `source: { pagePath, placement: product_detail }`. `productId` — UUID из Laravel Product DTO (`id`), подтверждаемый Product Resolve adapter. SKU, slug, имя товара и snapshots в запрос не входят. В форме нет поля Company, поэтому оно не добавляется.
- Успех принимается shared adapter только для HTTP 200/201 и валидного `data.status=persisted`, UUID `data.enquiryId` и строки `notificationStatus`. UI показывает номер заявки; состояние уведомления не переопределяет persisted success. Сохранённый success восстанавливает reference и блокирует повторное создание той же заявки после reload.
- Pending attempt сохраняется и проверяется в `sessionStorage` до fetch; персональные данные и полный payload туда не пишутся. Повтор после reload/неопределённого сетевого результата использует прежний ключ. Storage failure блокирует запрос. Повторный submit блокируется до завершения текущего.
- Добавлена явная кнопка новой попытки после изменённого payload, истечения срока неизвестной попытки или idempotency conflict. Показаны состояния валидации, unavailable product, rate limit, uncertain network/server outcome и storage failure.
- Для Product формы применено правило phone max 64 и 7–15 цифр; Contact/Catalogue ограничение осталось прежним. Privacy notice сохранён без consent checkbox.
- Поля контакта и комментария на `/cart` доступны для ввода. Кнопка отправки Cart остаётся выключенной, Cart submit не подключён; пояснение сообщает, что контактные данные не отправляются.
- Добавлен локальный gate `NEXT_PUBLIC_PRODUCT_ENQUIRY_SUBMIT_ENABLED`. В `compose.dev.yaml` Product submit включён, Cart submit выключен. Локальный backend Product gate включён независимо от Cart gate. Добавлен тест интеграционного gate/payload.

## API smoke

Локальный API smoke пропущен. Фактический backend контейнер обслуживает обычную локальную `potsandplanters`, а не `potsandplanters_test`; в обычной dev БД обнаружены включённые Telegram notifications и token. Horizon запущен. `potsandplanters_test` не содержит строки Telegram settings, но API процесс не направлен на эту БД. Поэтому submit через работающий API мог бы создать заявку в обычной dev БД и попасть в реальную доставку. Изолированный API smoke без изменения runtime DB/очереди безопасно выполнить нельзя. Реальных заявок и Telegram сообщений в рамках этапа не создавалось.
