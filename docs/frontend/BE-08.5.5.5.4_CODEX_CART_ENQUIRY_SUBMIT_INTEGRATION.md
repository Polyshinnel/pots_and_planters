## 1. Цель

Подключить существующую форму отправки на `/cart` к Laravel Cart Enquiry v2 через уже реализованные:
- `frontend/src/lib/enquiry/submit-v2.ts`;
- общий Product/Cart v2 adapter и Idempotency Attempt Manager;
- UUID-only Product Enquiry Cart store;
- Product Resolve API;
- существующий Cart UI.

Клиент отправляет заявку на получение персональных цен по нескольким товарам. Это enquiry, не заказ и не покупка.

**Не переписывать shared adapter или Idempotency Manager.** Переиспользовать готовые Product/Cart DTO и отдельный Cart attempt slot. Product Enquiry, принятая в BE-08.5.5.5.3, должна продолжить работать без регрессий.

## 4. Утверждённый Cart Enquiry v2 contract

Endpoint: `POST /api/v1/enquiries`

Header: `Idempotency-Key`

Payload:

```json
{
  "type": "cart_enquiry",
  "apiVersion": 2,
  "items": [
    {
      "productId": "<Product public UUID>",
      "quantity": 2
    }
  ],
  "name": "Customer name",
  "phone": "+971 50 123 4567",
  "email": "customer@example.com",
  "company": "Company / Project name",
  "message": "Optional comments",
  "source": {
    "pagePath": "/cart",
    "placement": "cart"
  }
}
```

Rules:
- `items`: 1..100 уникальных Product public UUID;
- `quantity`: integer 1..999999;
- `name`: required, max 200;
- `phone`: required, max 64; frontend policy 7–15 digits after removing formatting characters;
- `email`: required, max 254, Laravel RFC validation authoritative;
- `company`: optional nullable, max 200;
- `message`: optional nullable, max 5000;
- `source.pagePath`: `/cart`, без query/hash;
- `source.placement`: `cart`.

Не отправлять SKU, slug, internal DB ID, Product name/brand/price/image/specifications, snapshots, mock identifiers или client-side Product display data. Не отправлять `version: 1`.

`company` берётся из существующего поля Company / Project name. `message` берётся из существующего поля Comments. Не добавлять новые поля и не менять публичный дизайн без отдельного запроса.

## 5. Единственный источник корзины — UUID store

### 5.1. Состав заявки

Состав Cart submit строится только из актуального UUID-only Product Enquiry Cart store:
- `productId` — Product public UUID;
- `quantity` — сохранённое quantity.

Mock fixtures и mock seed data не являются источником данных для Cart. Удалить mock seeding/fallback, если он ещё используется в пользовательском Cart flow. Не подменять ошибки API mock-данными.

Не отправлять позиции, которые не имеют валидного Product public UUID. Если store содержит повреждённую или неизвестную запись:
- не отправлять её;
- не удалять автоматически;
- показать понятное состояние ошибки и зафиксировать конкретную запись/причину в отчёте;
- не добавлять compatibility layer.

Не отправлять Cart payload с пустым списком, повторяющимися UUID, невалидным quantity или более чем 100 строками.

### 5.2. Снимок состава при отправке

На submit создать immutable in-memory snapshot UUID/quantity из hydrated UUID store. Payload fingerprint и Idempotency Manager должны относиться именно к отправляемому snapshot.

Пока запрос выполняется:
- блокировать повторный submit;
- не допускать незаметного изменения состава, который будет отправлен;
- если Cart state меняется в другой вкладке, не менять текущий in-flight payload;
- после ответа сравнить актуальный store с отправленным snapshot.

Не очищать и не перезаписывать изменённую после отправки корзину.

### 5.3. Product Resolve перед submit

Перед отправкой использовать существующий batch Product Resolve:
- одним запросом для всех UUID;
- не делать N+1;
- проверить, что каждая позиция имеет `status: available`;
- не использовать SKU или slug;
- при resolve network/503/error — остановить submit, сохранить Cart, показать Retry;
- если есть unavailable UUID — остановить submit, сохранить все строки, явно обозначить недоступные товары и дать пользователю удалить их вручную или повторить resolve.

Resolve — предварительная UX-проверка, не гарантия доступности. Laravel повторно проверяет все Product под блокировками при submit. Если между resolve и submit товар стал unavailable, backend отклонит весь Cart request с 422 `products_unavailable`; UI должен сопоставить UUID с Cart rows и сохранить весь Cart.

## 7. Submit lifecycle и Idempotency

Использовать `submit-v2.ts` и отдельный `cart_enquiry` attempt slot.

Обязательно:
1. Подготовить fingerprint точного Cart payload.
2. До fetch сохранить pending attempt metadata в sessionStorage и проверить read-back.
3. При неизменном payload после timeout/network/5xx/429/reload использовать тот же key.
4. Не генерировать новый key автоматически после неопределённого результата.
5. При изменении items, quantity или contact fields требовать явного действия пользователя для новой попытки, если предыдущая имеет uncertain outcome.
6. При 409 показать понятное сообщение и предложить осознанно начать новую попытку.
7. При persisted success восстановить reference после reload и блокировать повторную отправку того же payload.
8. Если sessionStorage недоступен/не прошёл read-back, не отправлять заявку.
9. Не сохранять PII или полный payload в sessionStorage.
10. Не смешивать Cart attempt с Product attempt.

Не переписывать и не ослаблять общий Idempotency Manager ради Cart. Если обнаружен дефект в shared module, добавить узкий regression test и исправить только необходимую часть, сохранив Product behavior.

## 8. Ошибки и UI states

Обработать:
- idle;
- submitting;
- persisted success;
- field validation errors (422 `validation_failed`);
- unavailable Product list (422 `products_unavailable`);
- 409 idempotency conflict;
- 429 rate limit;
- network/timeout/5xx uncertain outcome;
- sessionStorage unavailable;
- payload changed / expired attempt;
- invalid/corrupt Cart state;
- Product Resolve error.

Success только если adapter подтвердил HTTP 200/201, `data.status=persisted`, корректный `enquiryId` UUID и `notificationStatus`.

После success:
- показать подтверждение отправки и reference/enquiry ID;
- не говорить, что заказ оформлен или цена рассчитана;
- Cart автоматически НЕ очищать;
- показать отдельное действие Clear Cart только если оно уже существует в текущем UI; если нет, не добавлять новое без необходимости;
- заблокировать повторную отправку того же snapshot через persisted attempt marker;
- если Cart был изменён после отправки, не очищать новые/изменённые позиции и не подменять success state.

`notificationStatus` не переопределяет persisted success. Успешное сохранение заявки не означает, что Telegram уже доставлен.

При unavailable items:
- сохранить все UUID rows;
- показать недоступные позиции;
- разрешить ручное удаление/Retry resolve;
- не отправлять частичную заявку автоматически;
- не удалять строки автоматически.

При network/timeout/5xx:
- результат неизвестен;
- Cart остаётся без изменений;
- повтор с тем же payload использует тот же Idempotency-Key;
- UI не должен утверждать, что заявка точно не создана.

Staging/production:
- frontend/backend flags не менять;

- не выполнять миграции и production операции.
