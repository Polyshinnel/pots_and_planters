# BE-08.5.5.5 — Утверждённое дополнение к Product/Cart Enquiry v2 Contract

**Статус:** утверждено владельцем  
**Дата:** 10 ноября 2026  
**Основание:** BE-08.5.5.5.1 Submit Integration Audit и решения владельца по всем семи вопросам  
**Область:** frontend ↔ Laravel Product/Cart Enquiry v2

Это дополнение фиксирует согласованные решения поверх существующего backend-контракта. Оно не заменяет фактические Laravel validators/DTO и не разрешает менять backend без отдельного задания.

## 1. Неизменяемая основа API

Endpoint для обоих сценариев:

`POST /api/v1/enquiries`

Обязательный header:

`Idempotency-Key: <16..128 chars matching ^[A-Za-z0-9._:-]+$>`

### 1.1. Product Enquiry v2

```json
{
  "type": "product_enquiry",
  "apiVersion": 2,
  "product": {
    "productId": "<Product public UUID>",
    "quantity": 1
  },
  "name": "Customer name",
  "phone": "+971 50 123 4567",
  "email": "customer@example.com",
  "message": "Optional message",
  "source": {
    "pagePath": "/shop/category/product",
    "placement": "product_detail"
  }
}
```

`company` optional nullable. `message` optional nullable. `source` и его поля optional. Не отправлять SKU, name/brand/price/image/specifications товара или клиентские snapshots. Product идентифицируется только public UUID.

### 1.2. Cart Enquiry v2

```json
{
  "type": "cart_enquiry",
  "apiVersion": 2,
  "items": [
    {
      "productId": "<Product public UUID>",
      "quantity": 1
    }
  ],
  "name": "Customer name",
  "phone": "+971 50 123 4567",
  "email": "customer@example.com",
  "company": "Optional company",
  "message": "Optional comments",
  "source": {
    "pagePath": "/cart",
    "placement": "cart"
  }
}
```

`items`: 1–100 уникальных Product UUID; каждый quantity — integer 1..999999. SKU не является идентификатором. `company`, `message`, `source` optional nullable согласно фактическому Laravel request contract.

### 1.3. Общие backend validation rules

- `name`: required string, max 200.
- `phone`: required string, max 64; backend не задаёт форматный regex.
- `email`: required `email:rfc`, max 254.
- `company`: optional nullable string, max 200.
- `message`: optional nullable string, max 5000 для Product/Cart.
- `source.pagePath`: optional path, начинается с одного `/`, max 2048, без query/hash.
- `source.placement`: optional string, max 200.
- `website`: honeypot; заполненное значение отклоняется.
- Неизвестные/лишние поля Product/Cart payload отклоняются.
- Request body max 65536 bytes.

Frontend phone policy, утверждённая владельцем:
- разрешены `+`, цифры, пробелы, скобки, точка и дефис;
- после удаления форматирующих символов должно оставаться 7–15 цифр;
- input maxLength — 64 символа;
- frontend policy намеренно строже backend max-length-only validation. Backend остаётся дополнительной проверкой.

Frontend email validation должна давать понятную обратную связь; окончательное решение принимает Laravel RFC validator. Ошибки `error.fields` отображаются у соответствующих полей.

### 1.4. Privacy notice

Оставить существующий Privacy Policy notice без обязательного consent checkbox.

Не добавлять фиктивное согласие, не отправлять consent field и не утверждать, что согласие записано. Текущий backend не принимает и не хранит consent. Если потребуется юридически значимое consent, это будет отдельное изменение backend contract и политики.

## 2. Ответы API и ошибки

Успешное создание:
- HTTP 201 для новой заявки;
- HTTP 200 для idempotent replay;
- `data.status = "persisted"`;
- `data.enquiryId` — UUID созданной заявки;
- `data.notificationStatus` — состояние notification/outbox;
- `Cache-Control: no-store`.

Ошибки:
- 422 `validation_failed` с `error.fields`;
- 422 `products_unavailable` с `error.products` UUID;
- 409 `idempotency_conflict`;
- 429 `rate_limited`;
- 404 `feature_unavailable`, если соответствующий backend gate выключен;
- 503 `persistence_unavailable`;
- общий error envelope содержит `code`, `message`, `requestId`, а при наличии — `fields`/`products`.

Cart submit атомарен: если хотя бы один Product неизвестен или недоступен, весь запрос отклоняется `422 products_unavailable`; частичная Enquiry, items или outbox запись не создаются. Frontend не должен самостоятельно считать предварительный resolve окончательным: Laravel повторно проверяет доступность при submit.

## 3. Idempotency — утверждённый frontend lifecycle

Backend:
- `Idempotency-Key` обязателен;
- допустимый формат: `^[A-Za-z0-9._:-]{16,128}$`;
- TTL записи — 24 часа;
- тот же key + тот же canonical payload возвращает ту же Enquiry без новых записей;
- тот же key + другой payload возвращает 409 `idempotency_conflict`;
- persistence failure возвращает 503; повторять следует с тем же ключом.

Frontend:
1. Перед первым сетевым запросом создать idempotency key и сохранить attempt в `sessionStorage`.
2. Attempt содержит только:
   - key;
   - fingerprint канонического payload;
   - тип сценария (`product_enquiry`/`cart_enquiry`);
   - createdAt;
   - состояние попытки, необходимое для восстановления (`pending`/`uncertain`/`persisted`).
3. Не сохранять в `sessionStorage` имя, телефон, email, company, message, Product DTO или полный payload.
4. Fingerprint вычислять от канонического payload, включая все поля, влияющие на backend payload hash. Не включать сам idempotency key.
5. Для того же неизменённого payload после network error, timeout, 5xx или reload использовать тот же key в пределах backend TTL.
6. При осознанном изменении payload fingerprint меняется — создать новую попытку с новым key. Если предыдущая попытка имела неопределённый исход, до начала новой попытки показать предупреждение: предыдущая заявка могла быть принята; новый payload может создать отдельную заявку. Требовать явного действия пользователя.
7. При 409 показать понятное сообщение о конфликте и предложить осознанно начать новую попытку с новым key. Не делать бесконечный автоматический retry.
8. При подтверждённом persisted success пометить attempt завершённым и запретить повторную отправку того же сценария/того же payload как новой заявки. Удаление/очистка attempt metadata допустимы только после надёжного сохранения success state, не до него.
9. TTL frontend attempt не должен превышать 24 часа. По истечении срока нельзя слепо повторять старый key; показать пользователю, что исход предыдущей попытки неизвестен и требуется осознанное новое действие.
10. Product и Cart attempts должны быть изолированы друг от друга. Разные payloads не должны случайно использовать общий key.
11. `sessionStorage` выбран намеренно: попытка переживает reload в той же вкладке, но не переносит персональные данные и attempt identity в постоянный localStorage. Поведение в новой вкладке — отдельная новая попытка; UI не должен обещать межвкладочную idempotency.

## 4. Cart после успешной отправки

- Не очищать v2 Cart автоматически.
- Не удалять legacy v1 позиции.
- После persisted success показать подтверждение и `enquiryId`/reference.
- Показать явное действие `Clear Cart` (или существующее эквивалентное действие) отдельно от подтверждения.
- До явного решения пользователя не очищать Cart.
- После success блокировать повторную отправку того же сохранённого содержимого как новой заявки из текущего success state.
- Если пользователь явно начинает новую заявку с тем же Cart, показать предупреждение, что это создаст новую Enquiry.
- Ошибки любого вида не очищают и не изменяют Cart.

## 5. Feature gates — утверждённая матрица

| Назначение | Frontend gate | Backend gate | Состояние до отдельной активации |
|---|---|---|---|
| Product add/manage | `NEXT_PUBLIC_PRODUCT_ENQUIRIES_ENABLED` | не требуется для локального store action; Product Resolve API работает отдельно | уже включён только в local dev согласно текущей конфигурации |
| Product submit | отдельный `NEXT_PUBLIC_PRODUCT_ENQUIRY_SUBMIT_ENABLED` | `PRODUCT_ENQUIRIES_ENABLED` | OFF |
| Cart submit | отдельный `NEXT_PUBLIC_CART_ENQUIRY_SUBMIT_ENABLED` | `CART_ENQUIRIES_ENABLED` | OFF |
| Contact/Catalogue submit | существующий общий gate | существующий backend flow | не менять |

Нельзя использовать общий `NEXT_PUBLIC_ENQUIRIES_ENABLED` как Product/Cart submit gate. Product/Cart submit gates должны быть независимы. Добавление gate definitions допустимо в соответствующем frontend implementation этапe, но значения остаются false/не заданными. Backend flags не менять. Не включать gates в Compose, `.env`, deployment или runtime.

## 6. Snapshot, Filament и outbox — подтверждённая backend ответственность

- Frontend отправляет только Product UUID + quantity и общие contact/message/source поля.
- Laravel повторно проверяет доступность и формирует immutable snapshots в транзакции.
- При Cart unavailable хотя бы одного Product весь submit отклоняется атомарно.
- Filament и Telegram formatter читают исторические snapshots, а не текущие Product relations.
- Outbox/Telegram delivery асинхронны; persisted Enquiry не означает, что Telegram уже доставлен.
- UI success означает только `data.status=persisted`; `notificationStatus` отображается только если это полезно и не должно трактоваться как неуспешное сохранение заявки.

## 8. Что остаётся выключенным

До отдельного решения владельца:
- Product frontend submit gate OFF;
- Cart frontend submit gate OFF;
- backend Product gate OFF;
- backend Cart gate OFF;
- production/staging не затрагиваются;
- реальные Telegram сообщения не отправляются в тестах.

Это дополнение утверждает контракт и правила, но само по себе не разрешает включение submit или production deployment.
