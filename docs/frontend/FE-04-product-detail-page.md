# FE-04 — Product Detail Page

**Проект:** Pots & Planters 2.0  
**Этап:** Frontend, после принятого FE-03  
**Стек:** существующие Next.js + TypeScript + Mantine + Tabler Icons + Swiper + Fancybox  
**Статус:** ТЗ для Codex

## 1. Цель и границы

Реализовать полноценную адаптивную страницу товара, органично продолжающую согласованные Layout, главную страницу и каталог. Сохранить премиальный характер старой темы и сделать страницу удобной для архитекторов, дизайнеров, отелей, подрядчиков и других B2B-клиентов UAE, не исключая розничных покупателей.

На этом этапе **не реализовывать** Laravel API, Filament-модели, отправку заявок, Telegram, оплату, checkout, поиск или SEO-микроразметку. Использовать существующий mock/data-access слой и подготовить контракты для следующих этапов.

## 2. Сначала изучить проект

1. Прочитать текущие компоненты, маршруты и типы FE-03; использовать фактические имена файлов и соглашения проекта, не создавать дубли.
2. Изучить `references/opencart/` и скриншоты `product` для desktop/mobile из `references/screenshots/`.
3. Зафиксировать, какие элементы старой страницы стоит сохранить, а какие ухудшали UX (громоздкие характеристики, удалённая от товара форма, мобильная читаемость).
4. Учитывать все ручные изменения после FE-01–FE-03. Не откатывать их и не заменять готовую дизайн-систему.
5. Если данные отсутствуют, отобразить корректное состояние; не придумывать реальные цены, сроки доставки, наличие, отделки, размеры или проекты.

## 3. Маршруты и загрузка данных

- Использовать **уже принятый в FE-03 формат URL товара**. Не менять существующие ссылки из карточек и не вводить новый маршрут без необходимости.
- Серверная загрузка mock-данных по `slug`/другому уже используемому идентификатору через общий data-access слой.
- Для неизвестного или неопубликованного товара — штатный `notFound()` / 404.
- Страница должна корректно работать при прямом открытии URL и перезагрузке.
- Данные продукта должны быть доступны в серверном HTML; интерактивные компоненты выделить в client components, не переводя всю страницу без необходимости в client-only.
- Предусмотреть `generateMetadata` из реальных полей товара или безопасных fallback, без полноценного SEO-этапа и JSON-LD.

## 4. Состав страницы

### FE-04.1 — Breadcrumbs и верхняя композиция

- Breadcrumbs: Home → подходящая категория → товар; ссылки рабочие.
- Если товар входит в несколько категорий, использовать детерминированную primary category из модели либо существующее правило FE-03; не выбирать случайно.
- Desktop: двухколоночная композиция «галерея / сведения и действия»; mobile: одна колонка с логичным порядком.
- Не добавлять гигантские пустые отступы перед основной информацией.

### FE-04.2 — Галерея

- Главное изображение + миниатюры, поддержка нескольких изображений.
- Использовать уже установленные Swiper и Fancybox, без второй библиотеки галерей.
- На mobile — свайп; на desktop — переключение по миниатюрам; открытие увеличенного изображения.
- Не ломать клавиатурную навигацию, видимый фокус, alt-тексты и закрытие lightbox.
- При одном изображении скрывать лишние элементы управления; при отсутствии изображения использовать согласованный placeholder без ложной фотографии.
- Не допускать CLS из-за загрузки изображений; использовать оптимизированную загрузку Next.js, где совместимо с существующим проектом.

### FE-04.3 — Название, артикул, цена, характеристики

Информационная иерархия:

1. Артикул / Model / SKU — небольшая второстепенная строка.
2. **Название модели** — H1; без дублирования размеров и отделки в заголовке, если они уже структурированы.
3. Ключевые характеристики конкретного SKU: размер, материал, отделка, назначение и др. — только если они реально есть.
4. Цена в AED — только если известна; иначе согласованное `Price on enquiry`.
5. Выбор количества и основные действия.

Пример **формата**, не данных для массового заполнения:

- `Model: 25526`
- `Coral Planter`
- `Ø 67 × H 67 cm · Bronze patina`
- `AED 1,462`

Не превращать характеристики в длинный технический заголовок. Для полного списка использовать семантический `dl` или аккуратную таблицу, адаптированную под узкий экран. Не выводить пустые поля, `undefined`, технические ключи или повторяющиеся значения.

### FE-04.4 — B2B-действия

- Количество: целое число от 1, удобные +/- и доступное поле ввода; исключить 0, отрицательные и некорректные значения.
- Основное действие: **Add to Enquiry** — добавить выбранный SKU и количество в корзину-заявку.
- Дополнительное: **Request a Quote** — использовать **тот же** механизм корзины-заявки; после добавления перейти к существующему или будущему маршруту корзины/заявки, согласованному с FE-05. Не создавать параллельную форму и не имитировать успешную отправку на сервер.
- Если FE-05 ещё не реализован, сделать минимальный устойчивый фронтенд-контракт корзины и явно обозначить временную навигацию; не создавать полноценный checkout.
- WhatsApp: прямой `wa.me` с URL-кодированным контекстом товара (название, SKU, при необходимости количество и абсолютный URL); номер брать из существующей конфигурации контактов, не хардкодить в компоненте. При отсутствии номера скрыть или корректно отключить действие.
- Не обещать наличие, сроки доставки, скидки, «fast delivery» или услуги без подтверждённых данных.
- Все действия должны иметь понятную обратную связь, но не показывать «заявка отправлена», если ничего не отправлялось.

### FE-04.5 — Единый контракт корзины-заявки

Использовать существующий механизм корзины, если он уже появился в проекте; иначе ввести **один** переиспользуемый клиентский store/context с минимальным API:

- `addItem(productId, sku, quantity)` (или эквивалент по текущим соглашениям);
- `getItems()` / селектор состояния;
- `getTotalQuantity()` для счётчика в Header;
- повторное добавление того же SKU увеличивает количество, не создаёт случайных дублей;
- хранение между переходами и обновлением страницы (например, `localStorage`) с безопасной гидратацией в Next.js;
- единый идентификатор позиции — конкретный SKU/вариант, а не только название товара;
- безопасная обработка устаревших или повреждённых локальных данных.

Не делать в FE-04 форму отправки, backend endpoint, цены доставки или платёжный процесс. FE-05 расширит этот контракт для редактирования корзины и отправки заявки.

### FE-04.6 — Описание и спецификации

- Короткое описание, если есть; отдельный блок Specifications с читаемыми метками и значениями.
- Дополнительные варианты исполнения показывать только при наличии достоверных данных и существующего механизма выбора SKU; не делать фиктивные селекторы.
- Не дублировать одни и те же характеристики в нескольких больших текстовых блоках.
- Текст должен быть доступен без обязательного JavaScript и не скрыт за ненужными вкладками.

### FE-04.7 — Related Products

- Похожие опубликованные товары из соответствующих категорий; исключить текущий товар и дубли.
- Переиспользовать **готовый компонент карточки FE-03**, включая раздельное отображение названия, SKU и строки характеристик.
- Ограниченная подборка; при отсутствии подходящих товаров блок не показывать.
- На мобильном допустим Swiper, если это действительно улучшает использование; не вводить отдельный дизайн карточки.

## 5. Mock-модель и будущий API-контракт

Расширить существующую типизированную модель товара, а не создавать параллельный массив. Нужные поля по фактической структуре проекта:

- `id`, `slug`, `sku`, `name`, `published`;
- `primaryCategoryId` / `categoryIds`;
- `images[]` с `src`, `alt`, опциональным порядком;
- `price` (nullable), `currency` = AED;
- `description`;
- структурированные характеристики (размеры с единицами измерения, материал, отделка, использование и прочее);
- при наличии реальных вариантов — идентификатор SKU каждого варианта;
- опциональные SEO-поля для метаданных.

Поля nullable/optional там, где реальные исходные данные могут отсутствовать. Форматирование размеров и валюты — в переиспользуемых утилитах; не парсить характеристики из названия в JSX. Для старых mock-названий допустима **явная, проверяемая нормализация данных**, но не слепое regex-разделение, способное повредить модели.

## 6. Адаптивность и доступность

- Проверить desktop, tablet, 375 px и 320 px (iPhone SE).
- Нет горизонтального скролла, обрезанных кнопок, перекрытия floating actions и основной CTA.
- Изображения не растягиваются; длинные названия и значения характеристик корректно переносятся.
- Кнопки количества и покупки удобны для касания, видны состояния focus/disabled.
- Галерея управляется клавиатурой; у изображений осмысленные alt.
- Существующие WhatsApp/Catalogues floating actions не дублировать и не ломать.
